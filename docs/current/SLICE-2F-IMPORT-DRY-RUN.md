# Development slice 2f — controlled patient import with a dry run

30 September 2026 (IST). Builds on slices 1d (roster preview and apply), 2d (dry-run migration) and 2e. Synthetic data only; formal acceptance unchanged.

## What changed

- **Who may import.** An active member with a care or supervisor role who supervises the team, checked through the slice 1e helper: an organisation owner or supervisor in that team, or a clinician with a supervision delegation in force for it. Each row's team must be one the importer belongs to and may import into. ASHAs, clinicians without supervision, administrators (who have no patient access) and suspended members are refused.
- **The file.** A CSV with a header naming exactly `name, age, sex, village, programme, team` (any order, each once); RFC 4180 quoting; up to 100 rows and 16,000 characters. The team column takes a team id or name. The file travels only in request bodies; nothing is put in a URL.
- **Dry run.** `POST /api/patient-import` classifies each row as accepted, rejected with reasons (field count, name, age 0–120, sex, village, programme, unknown team, team outside the importer's scope), or a possible duplicate. Duplicates reuse the registration matcher (`patientMatches`, same normalised name, or similar name with the same locality and an age within two years) over the records the importer may see, and also compare each row with earlier accepted rows of the same file. It returns row numbers, team ids, candidate record ids and versions, counts and reasons, never names or localities, and stores nothing. The plan hash is bound to the parsed rows, their classification, the environment, the importer and the id and version of every permitted record in the named teams, so any change in those teams forces a new dry run.
- **Apply exactly the plan.** `patientImportApply` sends the same file, the plan hash and a reason. The server recomputes the dry run and refuses with a 409 unless the hash matches, or when nothing would be created. Only accepted rows are created: unassigned in their team, with a local identity review stating that no candidate was found at the dry run and that no national identity was verified, and an `imported` lineage entry (batch, row, time, importer, plan hash). The store writes one revision per created person with the reason; one audit event records the batch with its counts and plan hash and no names. The result lists row numbers and new person ids. Replays recheck the importer's authority under the current membership.
- **Environments (slice 6n).** In the synthetic and training environments, where fixtures are practice data, imported people are marked `synthetic: true`, so the slice 6n barrier keeps them away from destinations outside the synthetic environment. In staging and production they are not marked. A misconfigured environment refuses both the dry run and apply. The command is paused during maintenance like other writes.
- **Screen.** Organisation & team gains "Import people from a CSV file" for eligible members: choose or paste a file, run the dry run, read the per-row results, give a reason and create the accepted rows.

## Limits

- People only. Visits, programme enrolment episodes, household links, contact details, assignment to a named worker and identifiers such as ABHA are not imported. The programme column sets the person's programme list as registration does; no enrolment episode is created.
- Possible duplicates and rejected rows are never created by the import. They are listed for review; a reviewed duplicate is registered one at a time through the normal registration review. There is no rejection file download and no data-quality report beyond the counts and reasons.
- Duplicate detection sees only the records the importer may see and uses the same simple matcher as registration; it is not a national or cross-organisation identity check.
- There is no batch reversal. A created person is corrected, merged or marked wrong through the existing commands, each with its own revision.
- Files are limited to 100 rows and 16,000 characters per batch because they travel in the command body, which is bounded at 20,000 bytes; text in non-Latin scripts takes more bytes, so such a file can reach the byte bound first (refused with 413). Larger sources must be split.

## Correction — 30 September 2026 (slice 6q)

A second independent review found two errors in this slice. An owner holding the ASHA role could import, but duplicate matching covers only the records visible to the importer, so an existing team patient assigned to another ASHA came back `accepted` and would have been duplicated; slice 6q excludes the ASHA role from importing. And the 16,000-character file limit did not fit the 20,000-byte body limit for Devanagari text (3 bytes per letter); slice 6q states and checks the limit as 16,000 UTF-8 bytes. See [SLICE-6Q-SECOND-REVIEW-FIXES.md](SLICE-6Q-SECOND-REVIEW-FIXES.md). The text above is kept as written.
