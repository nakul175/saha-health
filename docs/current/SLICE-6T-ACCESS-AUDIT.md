# Development slice 6t — material-read audit, halting when the audit cannot be written, and a chain-head checkpoint

1 October 2026 (UTC). Builds on slices 6j (audit chain), 6p and 6q (export audit retry), 6a (exceptional access), 0b-3 (paged patient detail), 2b (visit media), 7a (ABDM mock) and 7c (FHIR document). Synthetic data only; formal acceptance unchanged. No route, command or migration is added; the route count stays 41 and certified patient commands stay 48.

## What changed

- **Material reads are audited.** These reads now record one audit event each, in the organisation's audit hash chain, before the content is returned:

  | Read | Route | Audit action | Detail recorded |
  | --- | --- | --- | --- |
  | Full patient record in a paged workspace | `GET /api/patients/detail` | `viewPatientRecord` | number of visits and referrals returned |
  | Revision history page | `GET /api/history` | `viewRecordHistory` | number of revisions, whether it was an older page |
  | Visit media (photo or voice note) | `GET /api/media/[id]` | `viewMedia` | media id, type and visit id |
  | ABDM view that lists received external records | `GET /api/abdm` | `viewExternalRecords` | number of received records (a view with none is not a material read and is not recorded) |
  | FHIR example or document download | `GET /api/fhir/[id]` | `downloadFhir` | format and visit id |

  Each event names the patient (`person_id`), the actor, the actor's role and the time. It holds identifiers and counts only: no facts, notes, names, media bytes or document text. When the viewer reaches the patient through an emergency-access grant rather than normal care scope, the detail ends "Through emergency access grant <id>." so a reviewer can find those reads. Data exits, audit-chain exports and operations exports were already audited (slices 6m, 6j, 6k with 6p) and are unchanged.
- **External requests are audited before they are sent.** An external AI request (`runAI` with an HTTP provider) and an EHR document retrieval (`retrieveEhrDocument`) now record an `externalRequest` event after their checks and before the first request leaves Saha. For AI the event is written by a `beforeSend` hook that `externalCall` runs immediately before `fetch`, so a request refused by the allowlist or credential checks records nothing. The outcome is recorded by the existing command event. MIS delivery, EHR publication, agent runs and evaluation cases already save a checkpoint with its audit event before calling out (unchanged).
- **One path, cheap.** `recordAccess` (`lib/saha/access-audit.ts`) writes the event through `persist`, so it is chained under the same unique `(org_id, seq)` rule and rebuilt on a new head after a lost race like every other event. It is an *access-audit commit* (command type `recordAccess`, not accepted at `/api/commands`): `persist` refuses it unless every row is an audit event, writes no command receipt (a read is not replayed), and takes the batch token with `UPDATE organisations SET last_command=? WHERE id=?` without moving the organisation or patient revision. A read therefore never makes a teammate's command conflict and never refreshes anyone's workspace. The diff runs over an organisation shell with no records, so its cost does not grow with the organisation. Measured in the contract (in-memory SQLite, a lower bound for D1): one chain-head read plus one batch of two statements per read, one row written, about 0.2 ms on average over 200 reads.
- **Fail closed when the audit cannot be written.** *Decision:* every audited read and external request is refused if its event cannot be written. The person sees 503 "Saha could not record this access in the audit log, so it was stopped: nothing was shown or sent. Try again; if this continues, tell your organisation owner." Fail-closed was chosen for every read, not only exports and emergency access, because the reads above return clinical content or leave Saha and the same rule is easier to verify; the cost is that a clinician cannot open history, media or a FHIR download while the audit store is failing (the workspace itself still loads). Exports already refused delivery when their event failed; they now say so clearly (503 "Saha could not record this export in the audit log, so the export was not delivered. …") instead of the generic "workspace is unavailable" message. Commands and privileged changes were already atomic with their audit rows (one D1 batch); with the audit store failing they are refused with the existing 503 and nothing is saved.
- **Chain-head checkpoint for external anchoring.** `GET /api/audit/chain?format=checkpoint` (owners and administrators, same route) returns the head of an intact chain — sequence number, hash and time — with `checkpointSha256` (SHA-256 of `JSON.stringify(['saha-audit-checkpoint-v1', organisationId, seq, hash, at, issuedAt])`) and instructions to keep it outside Saha. A chain that is not intact gets 409 and no checkpoint. Issuing one is recorded as `auditChainCheckpoint` (detail: sequence, hash, events verified, checkpoint digest) through the export audit helper, so it fails closed and is retried on a fresh read like an export. `GET /api/audit/chain?checkpoint=<seq>:<hash>` adds a `checkpoint` result to verification: `matches` (nothing up to the checkpoint has changed), `differs` (events up to it were changed, removed or replaced) or `not-reached`. Because every hash commits to everything before it, this detects a suffix rewritten with recomputed hashes, which verification alone reports as intact. The Audit chain panel has "Download head checkpoint" and a "Saved checkpoint" field (sequence:hash or the file's contents) with "Check checkpoint".
- **Activity log.** Access events appear in the existing Activity log under the same visibility rule as other patient-linked events (care-team members in scope; not administrators). Each is marked "Record access", and a "Show record access" checkbox hides or shows them among the loaded events. The heading now says the log includes record access.

## Evidence

- 35 contract assertions (`tests/access-audit-contract.mjs`, real migrations in SQLite through the D1 shim): one action list shared by server and screen; a read appends exactly one chained event with no receipt, no record revision and no revision change, and no clinical text; read cost one batch and at most three statements; an organisation-wide command and a patient-scoped command loaded before reads still commit; a read that loses the chain race is rebuilt on the new head with the chain intact; an access commit carrying any non-audit row is refused before any write; emergency-access reads are named and normal reads are not; **fault injection** (a trigger that aborts every audit insert for the organisation): a read, a clinical command, an organisation change, an export audit and an external request are each refused, the read and export with their clear messages, the external send counter stays at zero, and no row of any kind is written; after the trigger is removed reads and commands work and the chain verifies intact; source-order checks that each audited route records before it returns content and that `externalCall` runs the hook before `fetch` and EHR retrieval records before `transport`; average cost over 200 reads; the checkpoint digest recomputes offline, a checkpoint still matches after later events, a wrong hash differs and a later sequence is not reached, and after the checkpointed event and every later hash are rewritten consistently the chain still verifies intact while the checkpoint reports `differs`.
- 52 HTTP/D1 assertions (`tests/access-audit-smoke.mjs`, on a separate synthetic account's organisation so the injected fault touches no other suite): history, FHIR document, patient detail and media reads each add one chained event naming the patient, without the note text or the patient's name; the organisation revision is unchanged; no receipts; the owner's Activity log lists all four; the chain verifies intact; a non-member is refused and nothing is recorded; with a fault trigger on the local D1 database, history, FHIR and patient detail return 503 with the access message and no content, the audit-chain export returns 503 with the export message, a `createPerson` command returns 503 and no patient or event is written; after the trigger is dropped history works again and the chain is intact. Checkpoint: the head of the verified chain, its digest recomputed offline, one `auditChainCheckpoint` event chained right after it, `matches`, `differs` and `not-reached` results, a malformed checkpoint refused (422), a non-member refused (403), and with the fault trigger the checkpoint refused with the export message.
- `tests/ehr-execution.mjs` writes a stub `access-audit.js` beside its stub store (`ehr-execution.ts` now imports it); `tests/safe-logs-contract.mjs` lists the two new console calls, which log only a status or error class. Both pass unchanged in count.
- Browser check (headless Chromium, built Worker, synthetic owner): after one history read the Activity log showed "View Record History" marked "Record access"; "Show record access (1 loaded)" hid and restored it while keeping other events; no axe violations in the log section and no console errors (`tests/evidence/slice-6t/access-audit-browser.json`). A second check downloaded a head checkpoint from the Audit chain panel, pasted it back and saw Matches, saw Differs for a changed hash, and found the checkpoint event in the Activity log; no axe violations in the panel (`checkpoint-browser.json`).

## Limits

- The workspace snapshot (`GET /api/workspace`), which carries the whole permitted caseload to the screen, is not audited per load, and opening a patient in a workspace that is not paged happens in the browser without a server read. Only the reads in the table are material reads in this slice. Search results, lists, the exception queue and other aggregate views are not audited.
- One event per request: a voice note that a browser fetches more than once records more than one event; there is no deduplication window.
- The EHR capability probe (`probeEhr`, owner-only, no patient data) still calls the partner before its event is written; only its result is audited.
- Fail-closed reads trade availability for completeness. There is no emergency override for reads during an audit-store outage.
- The checkpoint is not signed and Saha does not publish it anywhere: anchoring depends on the owner keeping the file outside Saha. A checkpoint detects changes up to its own position, not later ones. Verification and checkpoints are on demand, not scheduled.
- BR-SEC-08 and NFR-10 stay partial.
