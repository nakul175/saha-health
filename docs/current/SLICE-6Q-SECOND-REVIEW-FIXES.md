# Development slice 6q — fixes from a second independent review

30 September 2026 (IST). Builds on slices 5f (shadow operation), 0b-3 (paged patient list), 6p (review fixes, export audit retry and delegation limit), 2f (patient import dry run) and 6l (safe logs). Synthetic data only; formal acceptance unchanged. No command or migration is added. One HTTP handler is added (`POST /api/patients`, search in the request body), so the route count goes from 40 to 41; certified patient commands are unchanged.

These defects were found by a second independent review, carried out by an agent that did not write the code, after slices 5f, 0b-3, 2f and 6p had been built, tested and recorded as passing. The earlier passing runs did not test these cases. Each defect was reproduced on the base (`e9b379d`) before it was fixed, with the reviewer's scripts (`shadow-scope.mjs`, `import-asha.mjs`) or with the new regression checks, which fail on the base and pass after the fix. The slice 5f, 0b-3, 2f and 6p documents carry a dated correction; their original text is kept.

## What the review found, and the fix

1. **Shadow operation reached teams and patients outside scope (high, slice 5f).** `authorizeShadow` only checked that one of the manager's teams overlapped the capability's teams. A shadow's teams were not limited to the capability revision's reviewed teams (an owner could start a shadow on a team the revision was never reviewed for, and a whole-organisation shadow took every team), and a clinician in team A could run or stop a shadow covering team B, processing team-B patients' notes.
   *Reproduction:* the reviewer's `shadow-scope.mjs` on the base printed `org shadow teamIds [ 'team', 'other' ] capability teamIds [ 'team' ]`, a team-only clinician's run storing results for the team-B patient, and an owner's teams shadow on `other`.
   *Fix (`lib/saha/shadow.ts`):* a shadow's teams are limited to the revision's own reviewed teams. Organisation scope is the overlap of the organisation's teams with the reviewed teams (422 if there is none); a teams shadow naming a team outside the reviewed teams is refused (422). Running and stopping need an owner or a member of every shadow team (403); this is in `authorizeShadow`, which the replay block in `lib/saha/server.ts` also calls. In any case, a run processes only visits of patients in the runner's normal care scope (`normallyAllowed`; owner authority does not widen it); the others are skipped, counted (`outsideCareScope` in the result, and a sentence in the audit detail) and left pending for a runner whose scope includes them. Shadows stored before this fix that name teams outside the reviewed teams no longer reach those teams (`eligibleVisits` applies the same limit).
2. **Patient names in URLs (medium, slice 0b-3).** The next-page cursor was `JSON.stringify([name, id])` and the directory panel sent the cursor and the search text `q` as GET query parameters, so patient names reached URLs and hosting request logs, against the slice 6l safe-logs rule. The 6l static check did not see it because the URL was built with `URLSearchParams`.
   *Fix:* the cursor is opaque and name-free: `after:<patient id>`. The server resolves the id to its sort position with the viewer's scope predicate; a cursor naming a patient outside that scope, or one that no longer exists, is refused (400, start again). Search text travels only in a POST body (`POST /api/patients`, JSON, at most 2,000 bytes, same-origin); `GET /api/patients` serves unsearched paging and refuses `q` (400). The panel always uses POST. The load-envelope script sends its search the same way.
   *Static check:* `tests/safe-logs-contract.mjs` now also flags free-text or search keys set on `URLSearchParams` (`.set('q', …)` and similar) and `q=`/`search=`/`query=` in client API URLs (the pre-6q panel line is asserted to be flagged), requires the panel to POST, and requires the cursor to carry no name.
3. **Export audit retry re-checked too little (medium, slice 6p).** On a 409 retry, the audit-chain export re-verified role and operator status only, and the operations export role and format authority only, not the care scope or (for the operations CSV) the reporting reach.
   *Fix:* two helpers in `lib/saha/export-audit.ts` (`sameCareScope`, `sameReach`) are called in the retry authority check: both exports refuse (409, no export delivered, "Export again") if the exporter's sorted team ids changed; the operations CSV also refuses if `reportingScope(...).teams` or the set of delegation ids changed. The data-exit route already checked role and teams.
4. **Patient import by an ASHA-role owner (medium, slice 2f).** An owner holding the ASHA role could import; duplicate matching covers only records visible to the importer, and an ASHA sees only her assigned patients, so an existing team patient assigned to another ASHA came back `accepted` and would have been duplicated.
   *Reproduction:* the reviewer's `import-asha.mjs` on the base: `mayImport(asha owner)= true`, `row status for existing team patient: accepted`.
   *Fix and decision:* the simpler safe option was taken: the ASHA role no longer imports, even as an owner (`importsInto` accepts clinician and supervisor roles only). Clinicians and supervisors see the whole team, so their duplicate matching covers it. Matching over the whole team for an ASHA would have meant reading records she may not see; it was not built. The refusal message now says "clinician or supervisor role".
5. **Delegation records unbounded (low, slice 6p).** Since 6p, ended and revoked delegations no longer count toward `MAX_RECORDS` (200 not ended or revoked), so the operations JSON row could grow without limit.
   *Fix:* a separate cap on total stored delegation records, `MAX_STORED` = 1,000, with a clear refusal (422, "Stored delegation record limit reached (1,000 records, kept as evidence) …"). No record is deleted; an archive policy is not built.
6. **Import file limit stated in characters (low, slice 2f).** `MAX_CSV` was 16,000 characters while the command and dry-run bodies are limited to 20,000 bytes; Devanagari letters are 3 bytes each in UTF-8, so a file under the stated limit could be refused as too large.
   *Fix:* the limit is stated and checked in UTF-8 bytes (16,000 bytes; `csvBytes`), in the schema, the dry run and the panel text. A file within 16,000 bytes whose JSON encoding still exceeds 20,000 bytes (for example, mostly quote characters, each escaped) is refused by the body limit (413); the body limit was not raised.

## Evidence

- Contract: `tests/shadow-contract.mjs` +9 checks (reviewed-team limit, owner outside the team skips and counts, a runner in scope then processes them, a stored wider shadow refused to a team-only clinician for run, stop and the replay authority check, and never reaching the unreviewed team). `tests/patient-directory-contract.mjs` +3 checks net (name-bearing cursor refused, opaque cursor, POST body parsing, invalid body type; one former check replaced). `tests/safe-logs-contract.mjs` +4 checks. `tests/review-fixes-contract.mjs` +8 checks (care scope and reach helpers, static check that both retry closures call them, stored delegation cap). `tests/patient-import-contract.mjs` +5 checks (ASHA-role owner refused for dry run and apply; Devanagari byte limit).
- HTTP: `tests/patient-directory-smoke.mjs` sends searches by POST and adds 6 checks that the cursor is `after:<id>` without the name, GET with `q` is refused, the pre-6q name cursor and a cursor naming an out-of-scope patient are refused, and POST search pages with the opaque cursor.
- One existing assertion encoded the defect and was replaced, not weakened: `tests/shadow-contract.mjs` expected a whole-organisation shadow to take every organisation team (`['team','other']`); it now expects the reviewed-team overlap (`['team']`). The 0b-3 contract assertion that parsed the name-bearing cursor into `['Anil','p01']` now asserts that this cursor is refused and that `after:p01` parses to `p01`. The 0b-3 contract `walk` helper reads the opaque cursor through `pageQuery` instead of `JSON.parse`.
- Full suite totals, first-run failures and reports: `VALIDATION.md` (slice 6q section) and `tests/evidence/slice-6q/`.

## Limits

- The shadow care-scope skip uses normal care scope; a clinician with an emergency-access grant does not process that patient's visits in shadow. Skipped visits stay pending and are counted; they are not recorded as not run.
- The opaque cursor is an id keyset. Patient ids still appear in URLs (as they did for `/api/patients/detail`); ids are not names. Paging with a cursor whose patient was deleted or moved out of scope restarts from the first page.
- The export retry checks compare team ids and delegation ids, not delegation contents or team membership of other members.
- ASHA-role owners must import through a clinician or supervisor. Stored delegations stop at 1,000 until an archive policy exists.
- These fixes have not been independently reviewed. BR-AI-04, BR-AI-10, BR-SEC-07, BR-OPS-07, NFR-22, BR-DATA-11 and BR-ID-02 stay partial; NFR-24 stays unverified.
