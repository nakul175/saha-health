## Product workflow

An owner opens **Connections → Programme MIS → Reviewed mapping revisions**, drafts a revision and selects **Review destination requirements and synthetic examples**. Each field declares its transformation, destination units and missing-value behavior. The owner names required destination fields and required code fields, declares explicit codes/states, and supplies named synthetic examples with exact expected destination output or expected rejection. The pending draft displays the complete contract and examples before review. Its impact displays per-field affected work and passing/failed examples. Failed examples or uncovered fields disable review and are refused on the server. Publication retains the existing effective-time, exact-impact/current-owner, connector suspension and metadata-probe rules.

Existing scalar legacy mapping workflows remain compatible and receive no new conformance claim. Extended semantics and code projections require the governed contract. Once a connection has adopted conformance, a later draft cannot drop it; content changes to requirements, examples, mapping semantics or terminology require a different source reference/version. Reapplying unchanged semantics with a new effective time remains possible. Returning to an ungoverned legacy baseline requires a new reviewed contract rather than a silent downgrade. The owner UI explains this; earlier history remains available. Rollback to a previously applied governed revision creates a new immutable draft and repeats current impact/examples/review/publication.

## Supported semantics

Mapping rows retain source/target/required and optionally declare `transformation`, `unit`, `nullSemantics`. Governed rows require all three explicitly. Rules are versioned as `saha-deterministic-mapping-v1` and permit identity, kilograms to grams or pounds, Celsius to Fahrenheit, and weeks to days. Source/unit combinations are closed and checked; arbitrary expressions, incompatible units, noncanonical numeric strings, nonfinite values and conversion results above the fixed bound are refused. Results use deterministic decimal rounding to eight places. These rules convert recorded canonical values; they do not infer a clinical concept, reinterpret an entered-unit history or invent a source observation.

Optional missing fields can be omitted, emitted as an empty string, emitted as null, or represented by the recorded response state (`unknown`, `not-asked`, `declined`, `not-applicable`). A missing required source still fails regardless of missing-value behavior. Absence never becomes zero or a negative finding. Nullable/empty wire fields are admitted only when the exact mapping explicitly permits them; the immediate envelope guard rejects mismatched missing semantics. Units are declared mapping metadata; no extra field is silently added to the outbound envelope.

The `terminologyCode` source projects the explicitly declared code for that destination target. Required code targets must be declared mandatory, mapped as required code fields and have an active explicit code. Optional unmapped codes project the literal `unmapped`; unmapped declarations cannot contain a code or replacement. Deprecated or ambiguous declarations refuse projection/review/publication. No nearest-code replacement occurs. An unresolved governed change that has reached its effective time blocks fresh approval/send paths even before review, preserving metadata-only unknown-outcome lookup. Future unresolved changes do not prematurely alter the current wire.

## Evidence and invariants

The optional immutable `conformance` manifest contains its matching declared source reference/version, rules version, mandatory target lists and bounded named examples. The server computes exact expected-output/rejection results, ensures every mapped destination field has a passing example, hashes the examples/results, and includes that result with the per-field impact in the material impact hash. Review events retain results/digests. Mapping, source, fixture, current selected work or material evidence changes require fresh impact/review. Fixture output comparison treats field object order as semantically irrelevant. Failed examples remain in immutable cancelled draft history.

Per-field impact reports each destination target/source, terminology state, changed/unmappable unsent work and changed pending plans, including removed targets. They contain configuration identifiers and counts, not selected patient IDs, clinical notes or payloads. The original organization/connector/person/consent/visit/capture hash binding remains. Sending/uncertain work stays lookup-only; terminal receipts are preserved. Current-role checks and durable organization CAS/audit/receipt atomicity use the existing six lifecycle commands. No command, table, provider grant or patient authority was added.

The queued body, hash, correction linkage, original mapping references and attempt history are never regenerated by a mapping publication or rollback. Actual HTTP checks retain the original queued scalar body, then create a new confirmed-plan/queued body with grams, explicit null, unknown state, active code and optional unmapped code. A synthetic uncertain state is injected locally without sending externally; publication and governed rollback leave that wire and attempt count unchanged. The existing `sendSubmission` route returns the unchanged uncertain result with HTTP200, rather than authorizing a blind retry. Evidence asserts that preserved state/history accurately.
