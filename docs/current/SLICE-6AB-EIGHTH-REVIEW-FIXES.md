# Development slice 6ab — fixes from an eighth independent review of slices 6z, 7e, 2i and 7d, and the round-5 integration limit

2 October 2026 (UTC). Builds on `int9-7g-aggregate-delivery` (`49ab4be`: rounds 1–5 of the overnight build). Synthetic data only; formal acceptance unchanged. No command, route or migration is added; the route count stays 49 and the certified patient command count stays 52.

These defects were found by an eighth independent review, carried out by an agent that did not write the code, of round-4 slices 6z (sixth-review fixes), 7e (adapter operation permissions), 2i (stated units and unusual-value overrides) and 7d (replay and timeout soak). That code had been built, tested and recorded as passing; the earlier runs did not test these cases. A seventh item is the limit recorded when round 5 was integrated: aggregate report delivery (7g) screened releases without the population check that 6aa added to indicator queries. Each product defect was reproduced on the base before it was fixed (the reviewer's script `selfconfirm.mjs` and the new regression checks); the new checks fail on the base and pass after the fix. The slice 2i, 6z, 7d, 7e and 7g documents carry a dated correction; their original text is kept.

## What the review found, and the fix

1. **A recorder could confirm their own unusual value (medium, slice 2i).** `confirmUnusualValue` refused only the person named on the *current* override. Clinician A records 320 kg with a reason; an ASHA rewords the reason (or re-enters the same value in pounds), which appends a new override credited to the ASHA while the weight's author stays A; A could then confirm A's own value.
   *Fix (`lib/saha/fact-verification.ts`):* the confirmer is also refused when they are the measurement's recorded author (`factAuthors`, blood pressure for systolic and diastolic) or the author of any override in the visit's history with the same field and value. The refusal text is unchanged.
2. **The neutral ABHA refusal was still an oracle (low-medium, slice 6z).** The mock gateway's one-time code is public (`123456`, shown in the ABDM catalogue), so a requester who enters it can tell the "neutral" refusal for a number held by an out-of-scope record from a successful link. Each probe also appended another steward review event, and the access action text said the event was recorded "on both records" although it is written on the holding record only.
   *Fix (`lib/saha/abdm.ts`, `lib/saha/server.ts`, `lib/saha/access-audit.ts`):* the oracle cannot be removed while the mock code is public: whichever way the refusal is worded, a requester who knows the code sees "refused" where an unheld number would link. Making the mock code secret would need a stand-in for the ABHA holder's phone, which this release does not have. The oracle is therefore **bounded, not removed**, and this document and the requirement text say so. (a) An already linked record is refused first, and an out-of-scope duplicate is decided before the code is looked at, so neither answer depends on the code. (b) The server writes at most one `abhaLinkReview` event per requester and holding record in 24 hours (a repeat adds nothing). (c) A requester with `ABHA_REVIEW_LIMIT` (3) such refusals for different holding records in the last 24 hours has every further `abhaLink` refused with the same ordinary refusal, for any number and code, without a new event, so further probing reveals nothing until the day has passed; scope, version and already-linked checks still run first, on a copy. Steward review events show the probing to members who may see the holding records. (d) The access action text now says the event is recorded on the holding record only. A real ABDM gateway sends the code to the ABHA holder's registered phone, which closes the oracle for anyone not with the holder; that gateway is not built.
3. **A correction to a demonstration destination was classified as a create (low, slice 7e).** `misOperation` reads the mapped payload's `operation`; demonstration destinations have no payload, so the correction of an accepted visit counted as `create` and withdrawing `update` did not stop it.
   *Fix (`lib/saha/core.ts`):* `visitOperation` classifies a plan item as `update` when its payload says so or when a visit it corrects (following the correction chain, as `mappedPayload` does) has an accepted submission to the same destination. Preparation and execution both use it.
4. **ABDM consent steps and the EHR patient read were not governed (low, slice 7e).** `abdmConsentRequest` and `abdmConsentRevoke` had no operation; an EHR publication read `Patient/<externalId>` before its create recheck, so a publication whose create had been withdrawn still made that read.
   *Fix (`lib/saha/abdm.ts`, `lib/saha/ehr-execution.ts`, `lib/saha/adapter-operations.ts`):* a consent request is the first step of a fetch and is governed by `lookup`. A revocation is never refused, because withdrawing permission must always work in Saha; the gateway's `delete` operation decides only whether the mock gateway is told (nothing is sent in this release either way), and the audit and the command result (`gatewayNotified`) say which. The publication rechecks `create` on a fresh read before the patient read; the existing recheck after it stays.
5. **The 7d soak oracle was too loose (low, slice 7d).** A resend counted as allowed once the partner had delivered `not_found`, even if Saha never stored that answer; duplicates were checked per idempotency key with pre-seeded submissions only (plan creation, re-preparation, 7e withdrawals and `cancelSubmission` were not exercised); and the callback path was a copy inside the test without the route's 60-event limit and endpoint/binding checks.
   *Fix (`tests/replay-soak-contract.mjs`, test only):* a resend counts as allowed only if the partner delivered `not_found` *and* Saha's stored delivery events at the moment of the resend contain a `not_found` recorded after the previous send. Signed callbacks now run the real route function (`app/api/mis/callback/route.ts`, transpiled with an in-memory stand-in for its two D1 queries and the same compare-and-swap store), with HMAC signatures, so its signature, grant, endpoint/binding checks, stored-receipt replay and event limit are exercised. A bounded set of organisations (`SAHA_SOAK_PLAN_ORGS`, default 4) creates its submissions through the real `preparePlan`/`approvePlan`/`executePlan`, cancels one unsent delivery with `cancelSubmission`, has `create` withdrawn (round 2) and restored (round 4), re-prepares every visit whose deliveries are all closed (a new key), and tries to re-prepare visits whose delivery is open or resolved (refused). A new check asserts that the partner holds at most one accepted record per visit across keys. The bounded CI run takes about 4 seconds.
6. **The assistant summary input carried "[object Object]" (low, slice 2i).** The summary source listed every truthy fact, so the `entered`, `unusual` and `provenance` objects appeared as `entered: [object Object]`.
   *Fix (`lib/saha/agent.ts`):* only text facts are included. The objects are left out rather than formatted: the reasons for unusual values are free text and are not needed for a summary of the recorded values.
7. **Aggregate reports did not use the population check (round-5 integration limit, slice 7g).** `screen` and `recordReleases` in `lib/saha/aggregate-execution.ts` compared releases by key only.
   *Fix (`lib/saha/aggregate-execution.ts`):* both now build the population with `releasePopulation(state, ledgerHash(orgId), date)` (preparation and the pre-send recomputation on the state given, the checkpoint on the state read inside the checkpoint) and pass it to `screenReleases`, as the indicator page does. A report is a release to a destination, so the population is the organisation's assigned people, not a viewer's scope. A ledger write that D1 refuses (for example a value over its size limit) closes the report as not sent with the reason "the differencing ledger could not record this release (storage refused the write)", instead of an unhandled error after the checkpoint.

## Limits

- The ABHA oracle is bounded, not removed (see finding 2): a requester can learn, for up to three numbers a day, that an out-of-scope record holds them, and each such probe is recorded for a steward. The throttle is per requester and organisation; several requesters together get three each.
- The throttle query reads the audit table on every `abhaLink`; a D1 failure there refuses the link with a storage error (fail closed).
- The consent revocation is never blocked by the operation setting; only the (mock) gateway notification is governed.
- The soak's callback route runs with an in-memory stand-in for D1, not D1; the plan path covers four organisations by default, not the 10,000-event full soak.
- The aggregate population check uses today's records, like the indicator page (slice 6aa residual risk applies).
- These fixes have not been independently reviewed. BR-DATA-05, BR-INT-02, BR-INT-09, BR-INT-14, BR-REP-05, BR-AG-01 and NFR-05 keep their status; their current text and evidence are updated.
