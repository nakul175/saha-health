# Development slice 10a — scheduled trigger (Cron) foundation

2 October 2026 (IST). Synthetic data only; formal acceptance unchanged. Not independently reviewed. Built, tested and documented by an agent without human review, like the slices before it.

Until this slice Saha did its time-based work only when someone used it: a due caseload transfer applied on the first read or command at or after its effective time (slice 1f), alerts were recomputed on reads and after commands (slices 6g and 6v), and a request that never got its answer was noticed when a page showing it was opened. The hosted Worker now has a Cloudflare Cron Trigger that calls a scheduled job every five minutes, whether or not anyone is signed in.

## What changed

- **Worker entry.** `worker/index.ts` is the Worker's main module (`vite.config.ts` `main`, which was `vinext/server/fetch-handler`). It passes every HTTP request to that same handler unchanged and adds `scheduled(controller, env, ctx)`, which runs `runScheduled` inside `ctx.waitUntil`. It follows Vinext's documented custom-entry pattern. The built `dist/server/index.js` exports both handlers.
- **Trigger.** `scripts/cloudflare-staging.mjs configure` writes `triggers.crons` into the hosted configuration from `scheduledCron` in `deploy/cloudflare-staging.json` (`*/5 * * * *`; an empty string turns the trigger off; anything that is not a five-field cron expression is refused). The built configuration is not edited by hand and no other host has a trigger: where none is configured the handler is never called and the Worker behaves as before.
- **The job** (`lib/saha/scheduled-job.ts`, version 1.0.0). For each organisation in turn:
  1. **Due caseload transfers** are applied through the existing all-or-nothing path (slice 6ae, `applyDueTransfers`) with the scheduling steward's authority re-checked, at most 10 a run, oldest effective time first. A refused transfer is held whole with its reason and is never retried by the job. The commit names the actor `Saha scheduled transfer` (user `system`), as the on-use path already did.
  2. **Requests past their time limit** are marked as needing review (`lib/saha/scheduled-review.ts`), at most 25 a run, oldest overdue first. An assistant request whose recorded time limit (slice 5e) has passed with no confirmed result keeps its status and gains `timeoutReview` (who, when), so the requester or a clinician can still record the decision (`closeTimedOutAgent`); the assistant panel and the visit trace show "Flagged for review". A programme delivery in `sending`, an EHR publication in `running` or an aggregate report in `sending` for more than ten minutes becomes `uncertain`, the state in which the only step offered is a receipt lookup. One audit event per request names `Saha scheduled job`. Nothing is resent or retried and no provider or destination is called: the outcome of such a request is unknown, and an unknown outcome is resolved by a person (repository rule: uncertainty never authorises a blind external retry).
  3. **Operational alerts** are evaluated and delivered in-app by the slice 6v writer, independent of traffic. Nothing is emailed, texted or sent outside Saha. The evaluation is recorded in the organisation's operations record (`operations.scheduledJob`: time, alert and delivery rule versions, counts opened, closed and escalated, and why it was recorded) through the normal commit with an `scheduledAlertEvaluation` audit event. It is recorded when it is the first, when an alert opened, closed or escalated, and otherwise at most once an hour, so a steady state does not move the organisation revision or lengthen the audit chain every five minutes. Operators see the record in `GET /api/operations` (`operations.scheduledJob`); no screen shows it yet.
- Every change to the organisation record goes through `persist`: the revision guard, a record revision per changed record, the hash-chained audit event and a command receipt. The job's keys are `caseload-auto-…`, `scheduled-review-…` and `scheduled-alerts-…`; a conflict with a concurrent command is reported and left for the next run.
- **Refusals.** The job does nothing in an environment that is not configured correctly (`misconfigured`, slice 6n: any `SAHA_ENVIRONMENT` that is not one of the known names): it reads and writes nothing, and the Worker logs one fixed line. Organisations in maintenance get no transfers, no marks and no recorded evaluation (the same pause as slice 1f); their alerts are still evaluated.
- **Bounded and resumable.** A run visits at most 20 organisations, stops starting new ones after 800 database statements (a batch counts one per statement, as Cloudflare counts them) or 20 seconds, and always completes one organisation if there is one. Organisations with a due transfer are visited first, oldest first; the rest follow in a rotation that moves each run. Nothing is carried between runs: what was not reached is still due and is found again. There is no migration.
- **Logs.** The Worker writes one line per run with fixed counters only (organisations, not reached, why it stopped, transfers, marks, problems, statements, milliseconds) and fixed error lines; no organisation, patient or message text. `tests/safe-logs-contract.mjs` lists them.
- **Trace.** `scheduledTimeoutReview` is a trace execution action; an assistant request's thread shows a "flagged for review" step.

## Configuration and cost

- `deploy/cloudflare-staging.json` holds `"scheduledCron": "*/5 * * * *"`. To stop the job, set it to `""` and merge (or redeploy by hand); to change the interval, change the expression. See [Hosted synthetic staging](HOSTED-STAGING.md).
- Cloudflare's limits page (read 2 October 2026) gives Cron Triggers 10 ms CPU on the Free plan and 30 seconds on the Paid plan for intervals under an hour, a 15-minute wall limit, 5 Cron Triggers per account on Free, and 50 subrequests per invocation on Free. D1 queries count toward the per-invocation limit (50 Free, 1,000 Paid). Loading an organisation's JSON state is more than twenty statements and more than 10 ms of CPU for any non-trivial organisation, so **on the Free plan the job will stop early or be cut off, and the trigger should be considered to need the Workers Paid plan**. That plan has a monthly charge; whether the account is on it was not checked. A cut-off run is harmless: each commit is atomic and the next run finds the same work.
- The deployment's API token must be allowed to set the Worker's schedule. Cloudflare's Workers Scripts edit permission is understood to cover it; this was not confirmed against the token in use, and the first deploy with the trigger will show it.

## Evidence

- `tests/scheduled-job-contract.mjs` (32 checks, in the CI contract loop) runs the real job and review modules over the repository's migrations in an in-memory database, with any outbound `fetch` failing the suite: a due transfer is applied by the scheduler with one audit event, one revision per moved patient and a receipt, and a repeat run changes nothing; a refused transfer is held whole with every patient byte-for-byte unchanged and never retried; late requests of all four kinds are marked once with audit events, receipts and trace links, fresh, closed, accepted and unlimited ones are left alone, nothing is resent and no attempt counter moves; the alert evaluation opens the occurrence and delivers at the evaluation time, is recorded as first, as changed (an escalation due by the clock alone) and as an hourly heartbeat, and a steady state is not recorded again; misconfigured names are refused with the database unchanged; maintenance pauses transfers, marks and the record; transfers, review marks, organisations, statements and elapsed time are bounded and resume on the next run; a failing organisation is reported by step and error class only and does not stop the others; the job and review modules import no execution, provider or transport module.
- `tests/cloudflare-staging-contract.mjs` (extended): the committed configuration carries the default cron, the generated configuration has `triggers.crons`, an override and an empty value work, an invalid expression is refused, a trigger in the built file never survives, and the external-call switches are unchanged.
- `tests/safe-logs-contract.mjs` (extended) scans the Worker entry and fixes the scheduled log line's fields.
- `tests/scheduled-local-check.mjs` (not in the CI loop; run on the built Worker with wrangler's scheduled-test support): 8 checks passed on the built Worker under wrangler 4.92.0 (scheduled endpoint `/cdn-cgi/handler/scheduled`), a fresh local D1 and synthetic accounts: the Worker still serves requests through the custom entry; the handler runs on an empty database and logs fixed counters only; a transfer scheduled 20 seconds ahead is not applied early even when the job runs; once due, the job applies it with nobody using Saha and the audit trail names the scheduled transfer actor; alerts are evaluated and the evaluation is recorded with an audit event naming the scheduled job; a repeat run records nothing again; the Worker output shows no network error; with `SAHA_ENVIRONMENT=prod` the job logs its one fixed refusal line and the database is unchanged. The check drops the static-assets binding from its temporary copy of the Worker configuration: miniflare's assets router has no `scheduled` handler, and the first run, with assets, got an `exception` outcome. The deployed Worker keeps its assets; that a Worker with static assets runs its Cron Trigger on Cloudflare was not verified here.

## Limits

- **Not run on the hosted Worker.** The trigger is in the configuration the next deploy will write; no one has seen it fire on Cloudflare, and no detection time has been measured. "Every five minutes" is the cron setting, not a measured result. Cloudflare may start a run late and does not guarantee it.
- **Plan.** See above: the Free plan's CPU and query limits are likely to defeat it.
- **Detection delay.** A request past its limit is marked by the run that reaches its organisation: with more than 20 organisations the rotation means it can take several runs. Work is not carried over, so a busy organisation with more than 10 due transfers or 25 late requests is finished over several runs.
- **Coarse record.** The recorded evaluation time is at most an hour old in a steady state (the Worker log line has every run). The alert occurrences and notifications carry their own times.
- **Queue.** Organisations in maintenance with a due transfer lead the queue each run and are then skipped for writes (the known slice 1f cost of a due transfer in maintenance, now paid by the job rather than every request); the queue is capped at 1,000 organisations.
- **Full read.** Each visited organisation is loaded whole, as every command does today; the job does not make that cheaper.
- **In-app only.** Delivery outside the app (email, SMS, paging) remains unbuilt and no recipient list or ladder has been approved; escalation is the slice 6v in-app ladder.
- **Marking is not resolution.** A flagged request still needs a person: the decision for an assistant request, a receipt lookup for a destination. The EHR lookup policy of slice 7f and the aggregate lookup are unchanged.
- **Only the hosted configuration has a trigger.** Sites and local runs have none (local runs can call the handler with `wrangler dev --test-scheduled`); there the on-use behaviour of slices 1f and 6v is all there is.
- Requirement rows BR-ID-04, BR-OPS-04 and NFR-18 stay partial; none of the 176 formal acceptances changes.
