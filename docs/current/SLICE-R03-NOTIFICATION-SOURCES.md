# Development slice r03 — routing further alert sources through the notification channel

3 October 2026 (UTC). Slice 10b gave the out-of-app notification channel a demonstration simulator and a tiered planner, but only the fourteen in-app operational alerts (slice 6g/6v) flowed through it. This slice extends the same channel to the alert sources the requirements still ask to be delivered out of app: AI-budget alerts (already carried, now listed beside the others), drift alerts (slice 5i), timed-out assistant requests (slice 5e), individual exception-queue items (slice 6i) and open field referral requests (slice 3i). Nothing new leaves Saha: every message still uses the demonstration simulator, holds no contact detail, carries no patient name or identifier, and is refused outside the synthetic and training environments.

## What changed

- **A wider notifiable catalogue** (`lib/saha/notification-channel.ts`). The in-app `ALERT_IDS` and `ALERT_OWNERS` (14 kinds) are untouched, so slice 6g/6v and their contracts are unchanged. A parallel `SOURCE_KINDS` adds `drift`, `agent-timed-out`, `exception-item` and `referral-request`, each with an owner role in `SOURCE_OWNERS`; `NOTIFIABLE_KINDS` / `NOTIFIABLE_OWNERS` are the union. `mayReceive`, the recipient-schema `kinds`, `canonical` and `ladderFor`/`planNotifications` now work over the union, while the exported `kindsFor` keeps returning the in-app list so the owner screen's in-app set and existing tests stay as they were. A new `notifiableKindsFor` returns the full list per role, and `applyNotificationChannel` validates saved recipients against it, so an owner can list a member for `drift`, an administrator for `agent-timed-out`, and a supervisor for `exception-item` or `referral-request`, with the same "a kind their role does not hold is refused" rule.
- **A pure source planner** (`planSourceNotifications`, in `notification-channel.ts`). It is the `planNotifications`-style pure function for the new kinds: configuration, environment, `SourcePresent` values, keys already sent, members and a time in; messages out. Each `SourcePresent` is one occurrence per (kind, scope) with an `openedAt` (the earliest underlying item time, so tier escalation timing is stable), a fixed title, and the recipient's own count. `sourceKey` gives a stable occurrence id `src:<kind>:<scope>`; the unique index `(org_id, occurrence_id, tier, user_id)` from migration 0015 makes repeats harmless without a new table. `planSourceNotifications` reuses `planNotifications`, so the ladder, the SMS 160-character bound, the fixed `/?view=operations` link, the simulated receipt and the no-patient-data wording are identical to slice 10b.
- **A source builder** (`lib/saha/notification-sources.ts`, new, `SOURCE_RULES_VERSION` 1.0.0). `channelSources(s, now)` derives, on read, the additional occurrences: drift revisions with an agreement drop (`driftReport`), assistant runs past their task time limit (`timedOut`), and — per supervisor's own care scope, one occurrence each — the exception-queue and open-referral-request counts (`exceptionQueue`, `referralRequestQueue`). A count is only ever the recipient's own view (slice 6v/10b); organisation-wide kinds (drift, timed-out) go to their owning role, care-scoped kinds to the supervisor who sees them (owners may hold them but receive the count withheld). `SOURCE_SCOPED` marks the care-scoped kinds so the owner log redacts another person's count, exactly as `CARE_SCOPED` does for in-app alerts.
- **Server wiring** (`notification-channel-server.ts`, `alert-delivery-server.ts`). `evaluateChannelSources` runs at the end of `evaluateDelivery`, beside `evaluateChannel`, so it inherits the same reads, organisation-wide commands and scheduled trigger. It reads the already-sent keys for the source occurrence ids, plans with `planSourceNotifications`, and commits at most `MAX_SENDS_PER_EVALUATION` messages through the existing `commit` — each message row and its `notificationSent` audit event in one access-audit commit under `system:notification-simulator`, never moving a revision. A failure is recorded in the delivery result and never undoes or blocks the in-app delivery. The owner read (`GET /api/notification-channel`) now lists the full catalogue (`NOTIFIABLE_KINDS` with `source: true`) and `notifiableKindsFor` per member, and the message log already shows the new messages.
- **AI-budget alerts** (`ai-budget-reached` 100%, `ai-budget-near` 80%) were already owner-owned kinds in `ALERT_OWNERS` and already flowed through the channel; they remain eligible and are asserted alongside the new kinds.

## Evidence

- `tests/notification-sources-contract.mjs` (19 assertions): the catalogue and owner roles (in-app 14 unchanged, the 4 new kinds, `sourceKey`); `notifiableKindsFor` per role; `kindsFor` unchanged; storing and refusing the new kinds through `applyNotificationChannel`; the pure `planSourceNotifications` tiering, escalation timing, idempotence and a late evaluation; the supervisor-scope rule with the owner's count withheld; the fixed message shape, SMS bound, simulated receipt and no patient data; disabled/refused channel planning nothing; `SOURCE_SCOPED` redaction; purity (same input, same output, derived receipt ids); and source-scan of the builder, the server evaluation and the delivery hook for the simulator reuse and no `fetch`/network/console, plus the migration's unique index and free-text `alert_id`/`occurrence_id`.
- `node tests/notification-channel-contract.mjs` (24), `node tests/alert-delivery-contract.mjs` (23) and `node tests/alerts-contract.mjs` (25) all still pass, confirming the shared planner and the in-app catalogue are unchanged.
- Type check (`tsc --noEmit`) clean. No network code, no real recipients, no new table or migration.
- Requirements BR-AI-12, BR-AI-10, BR-AG-07, BR-REP-01 and BR-CARE-01 stay partial with their "delivered notification" gaps narrowed; no acceptance case is promoted.

## Limits

- Demonstration only, as slice 10b: no contact details, no live provider, simulated receipts; a real channel needs approved recipients, consent and a provider contract.
- The new kinds have no in-app acknowledgement lifecycle, so there is no "cleared" state: a source occurrence is the current open set, and a message once sent is not sent again for that (kind, scope, tier, recipient). If the set empties and later refills, the first tier is already recorded and the next unsent tier continues (documented, not the slice 6v close/reopen cycle).
- Per-scope counts are computed on read by running the existing queue functions per eligible member, so a very large organisation costs more work per evaluation; the message count is capped at `MAX_SENDS_PER_EVALUATION` and the rest follow on the next evaluation.
- Care-scoped kinds are delivered to supervisors (and non-administrator owners) per scope, matching `canAcknowledge`; clinicians who can open the referral queue in Saha are not notified out of app, and destination-delivery exceptions remain operations work (already covered by the in-app `destination-uncertain`/`ehr-uncertain` alerts).
- Detection still depends on traffic or the scheduled trigger; the five-minute NFR-18 target is unchanged.
- Built in a parallel round and not independently reviewed.
