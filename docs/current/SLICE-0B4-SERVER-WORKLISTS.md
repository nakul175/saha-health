# Development slice 0b-4 — server-side work lists for paged workspaces

2 October 2026 IST (1 October UTC). Storage slice of the development-completion plan, built on GitHub `main` (15bb1de). Synthetic data only; formal acceptance unchanged; NFR-24 remains unverified. No migration and no command. One HTTP handler is added (`GET /api/worklists`), so the route count goes from 41 to 42; certified patient commands are unchanged at 48.

## What changed

- **The known limit of slice 0b-3 is closed for three views.** When a non-ASHA viewer with more than 500 people in scope is paged, My work (its four statistics, the visit list and programme follow-ups), the referral tracker on My work and the Submissions page are now built on the server over the viewer's whole permitted scope and returned one page at a time. Before, the browser built them from the records it held, so they covered only the patients opened in that session, and My work said so in a notice. That notice is replaced by a one-line status that the lists are built on the server and load page by page.
- **One definition for both workspaces.** `lib/saha/worklist-views.ts` holds the order and counts of these views as plain functions: the visit list (not yet confirmed first, then due today, then name, then record id), the statistics, follow-ups grouped by person in order of each person's earliest open task, submissions with the attention filter, and referrals (open first, then due date, undated last, then record id). The unpaged workspace (`app/workspace.tsx`, `app/programmes.tsx`, `app/referral-panel.tsx`) now calls these functions on the records it holds, and the server calls the same functions on the whole scope, so the same viewer sees the same counts and order on the same data either way.
- **`GET /api/worklists?view=work|followups|submissions|referrals`** (`lib/saha/worklists.ts`, `lib/saha/worklists-server.ts`). The viewer's permitted patients are selected with the slice 0b-2 SQL predicate, exactly as for `/api/patients`, and each is checked again with `access.ts`: ASHAs see only their assigned patients, clinicians also see patients under a current emergency-access grant, owner authority never widens the scope, and administrators, providers and inactive members see nothing (inactive and non-members get 403). Only the columns a view needs are read (patient summary fields with `json_extract`; visit states; submission states for the statistics; full submissions or referrals only for those views), in one batched round trip. Rows are summaries: no delivery payloads, payload hashes, referral events or sources. `total` counts the whole ordered view on every page; the work view also returns the statistics, the follow-up view the open task count, and the submissions view the all and needs-attention counts.
- **Nothing identifying in the address.** The query carries only `view`, `tab` (`all` or `attention`, Submissions only), `limit` (1–100, default 50) and an opaque offset cursor `n:<position>`. Any other key (`q`, `personId`, a name), a cursor in any other form (including the 0b-3 `after:<id>` and the pre-6q name cursor) and an unknown view are refused with 400. There is no search here; search stays in People (`POST /api/patients`).
- **Workspace.** In a paged workspace, My work shows the server statistics, the visit list with Load more ("Showing 100 of 606"), the follow-ups and the referral list; Submissions shows server tabs with counts and Load more. A row opens its record on demand (the 0b-3 path); a referral or submission row opens the record at that visit, where the full referral card and receipt controls (send, look up, view receipt) work as before. "Open next visit" uses the first unconfirmed row of the server list. The Submissions sidebar count is hidden in a paged workspace, because it would count opened records only. The lists reload after each command answer. ASHAs and unpaged workspaces keep the browser-built views, now through the shared functions.
- **One order changes (decision).** The Submissions list showed the reverse of the snapshot's record-id order. Submission ids are random, so that order was not by time. It is now most recent first by creation time, then record id, in both workspaces. The visit list, follow-ups, referrals and statistics keep their earlier order and values; the record-id tie-breaks only make explicit what the id-ordered snapshot already produced, and name order now uses a fixed `en` collation so the browser and the Worker agree.
- **Probe.** `tests/load-envelope.mjs` with `SAHA_LOAD_WORKLISTS=1` (and `SAHA_LOAD_SUPERVISOR=1`) seeds an open follow-up for every tenth person, a submission for every fourth and a referral for every twentieth, and also measures the four work lists and the last page of the visit list for a whole-team supervisor.

## Limits

- Each page request recomputes the whole view over the viewer's scope (the scope is read, ordered in the Worker and sliced); nothing is cached or indexed for these views. Response size stays at one page, but time grows with the scope (about 0.6 s for the work view at 20,006 people on a shared local machine; 50,006 was not measured). Name order cannot be done in SQL with the same collation, so it is not pushed down.
- The cursor is an offset. If records change between pages, a row can repeat or be skipped; `total` is repeated on every page so a client can notice, and the workspace reloads the first page after each command. A cursor past the end returns an empty page.
- The paged visit list has no search or programme filter (People has both). The Submissions list in a paged workspace shows summaries; sending, looking up and viewing a receipt happen on the opened visit. Referral cards in the paged list are summaries; events, delays and ownership are changed on the opened visit.
- Other browser-built views in a paged workspace (AI tools lists and activity counts by patient) still cover only opened records. Server-computed queues (action plan, exception queue, referral escalations, alerts, worker activity, indicators) were already whole-scope.
- Local probe only: hosted D1 latency, Worker CPU and memory limits, concurrent sessions and reference devices were not tested. NFR-24 stays unverified; BR-CARE-04 stays partial.
- Not independently reviewed.

## Correction — 1 October 2026 (slice 6w)

The offset cursor did not notice a list that changed between pages, and the panel appended pages without checking, so rows could be skipped or repeated. Slice 6w carries the view's total in the cursor (`n:<offset>:<total>`); a changed total restarts at the first page and the panel replaces its rows. A list that re-sorts with the same total is not detected. Found by a fifth independent review (an agent that did not write the code) of round-1 slices 0b-4, 4e, 6s and 6t; the original text above is kept. See [slice 6w](SLICE-6W-FIFTH-REVIEW-FIXES.md).
