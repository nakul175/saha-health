# Development slice 10d — workforce roster import from a CSV file

2 October 2026 (IST), evening build round (lane d). Builds on slice 1d (roster reconciliation), slices 2f and 2h (dry run, plan hash and apply exactly the plan for imports), slice 2h's rejection report and slice 9a (demonstration fixture clinicians). Synthetic data only; formal acceptance unchanged. BR-ID-01 stays partial.

## What changed

- **Who may import.** An active organisation owner, whatever role the owner holds, as with the pasted roster of slice 1d. Supervisors, clinicians, ASHAs, administrators who are not owners and suspended owners are refused with a 403 on the dry run, the rejection report and the apply; the apply is checked again on a replay by key under the current membership.
- **The file.** A CSV whose header names `name, account_code, role, team, status` (any order, each once) and may add `external_staff_id`. RFC 4180 quoting through the slice 2f parser; up to 100 rows and 16,000 UTF-8 bytes (the 20,000-byte command body bound); the file travels only in request bodies. `role` is `asha`, `clinician`, `supervisor` or `admin`; `team` is a team name (or id), several separated by semicolons; `status` is `active` or `left`; the staff id is 1 to 64 letters, digits or `/ . _ -`, starting with a letter or digit, so a spreadsheet formula cannot be stored as one.
- **Dry run.** `POST /api/workforce-import` with `{csv}` classifies every row and stores nothing:
  - **invitation to create** (`invite`): a new account, or one whose earlier membership was removed, becomes an ordinary account-bound invitation (72 hours; only the token hash is stored), the same shape `createInvite` and slice 1d make;
  - **membership to update** (`update`): a different role or team set, or a staff id to record for a member or current invitee whose membership does not otherwise change; `suspend` for a row marked `left`;
  - **no change** (`none`): the member already matches, a current invitation already exists, the person is already suspended or not a member, the row is the importer's own, or the row is a slice 9a fixture clinician;
  - **conflict**, never applied and left for review: an owner listed as left, a locally suspended member listed as active, a provider-sandbox account, a current invitation with a different role or team, a person listed as left who holds a current invitation, and the staff id rules below;
  - **rejected**, with reasons: a wrong field count, a missing or over-long name (or one with control characters), an account code that is not 24 hexadecimal characters, an unknown role or status, a team name that matches no team, a care or supervisor role without a team, a malformed staff id, a repeated account code (every row involved is rejected) and one staff id given for different accounts (every row involved is rejected).
  The response holds row numbers, the action, the role and team names to be set, the reasons, counts and a plan hash, and no names, account codes or staff ids. The workspace reads names and codes from the file the owner already holds.
- **Slice 1d rules are reused, not copied.** Every row that passes the file checks goes through `rosterDiff` of slice 1d, so an import never removes a membership, never reactivates a local suspension (a conflict), never changes an owner flag, never suspends an owner (a conflict), never changes the importer's own membership and leaves fixture clinicians alone. A contract test classifies the same rows with `rosterDiff` and with the import and requires identical results. Unlike the pasted roster there is no "complete roster" mode: a person missing from the file is never suspended, only a row marked `left` suspends. A leaver's role and teams are not checked, because the source system's roles and team names are often out of date and failing to suspend a leaver is the unsafe way to fail.
- **External staff ids.** An id is recorded against the account code (so it reaches the member when an invited account joins) in the organisation's `operations` record (`staffIds`: id, time, importer and batch), not in a new table. Case-insensitive uniqueness within the organisation; an account that already has a different id keeps it (an import never replaces one); the same id for a second account is a conflict; the same id again is no change. Ids are recorded for invite, update, suspend and no-change rows of members or current invitees, never for the importer's own row, fixtures, conflicts or people who are not members.
- **Plan hash.** Bound to every parsed cell of the file, the classification, the environment, the importer, the version and status of every membership, the teams, the pending invitations (a pending invitation that expires between dry run and apply changes the plan) and the recorded staff ids, so a change to any of them forces a new dry run.
- **Apply exactly the plan.** `workforceImportApply` (`csv`, `planHash`, a reason of 10 to 500 characters) recomputes the dry run and refuses with a 409 unless the hash matches, or when nothing would change. Environments that are misconfigured refuse it (as slices 2f and 2h do) and maintenance pauses it like other writes. It creates the invitations, updates and suspends memberships (version plus one) and records staff ids. Rejected rows, conflicts and unchanged rows are never applied. One audit event per applied row (row number, account code or user id, what changed; no name, no staff id) and one summary event with the batch, plan hash and counts. The result holds the batch id, counts, the applied row numbers and each invitation's row, account code, code and expiry; like slice 1d, it is kept in the command receipt so an identical retry returns the same codes.
- **Rejection report.** `POST /api/import-rejections` accepts kind `workforce` (owners only). The slice 2h report lists the rows that are not accepted, as Rejected or Conflict with their reasons, never names, account codes or staff ids; it carries the definition, export identifier, a control total and the slice 6k manifest, and is recorded as an access-audit event that moves no revision.
- **Screen.** Organisation & team gains "Import a workforce roster from a CSV file" for owners (next to Roster sync): choose or paste a file, run the dry run, read the per-row results, download the rejection report, give a reason and apply exactly the plan; the invitation codes are listed once.

## Limits

- Account codes still come from each person's own account. Saha does not create accounts or verify identity with the institution (BR-ID-10 federation is not built).
- A file is one batch of at most 100 rows and 16,000 bytes. Larger rosters are split by the owner into batches, each with its own dry run and plan.
- There is no scheduled or API feed from an HR or identity system, no upstream de-provisioning and no batch reversal. A mistaken invitation is revoked by hand; a wrong role or team is corrected with another import or the member editor.
- Staff ids are recorded, not verified: nothing contacts the institution, they are not shown in the members table or sent to any destination, and there is no command yet to correct or remove one. Operators (owners and administrators) can read them in the operations record.
- Invitation codes still have to be delivered to each person outside Saha, and the apply result holds them in the command receipt.
- The rejection report is generated from a fresh dry run at download time; if memberships or invitations changed since the dry run on screen, its plan hash differs.
- The dry run sees the organisation as it is now; two owners importing at once are separated only by the plan hash (the second apply is refused), not by a lock on the file.
