# Development slice 6aa — fixes from a seventh independent review of slices 6w, 2h and 6y

2 October 2026 (UTC). Builds on `int8-2i-value-overrides` (`8b941d0`: rounds 1–4 of the overnight build). Synthetic data only; formal acceptance unchanged. No command, route or migration is added; the route count stays 48 and the certified patient command count stays 51. `importRejectionsExport` joins the access-audit action list. The trace contract version moves from 1.0.0 to 1.1.0.

These defects were found by a seventh independent review, carried out by an agent that did not write the code, of round-3 slices 6w (fifth-review fixes), 2h (enrolment and identifier import) and 6y (task trace). That code had been built, tested and recorded as passing; the earlier runs did not test these cases. Each defect was reproduced on the base before it was fixed (the reviewer's scripts `diff-bypass.mjs`, `diff-excl.mjs`, `diff-days.mjs` and `ledger-size.mjs`, and the new regression checks), and the new checks fail on the base and pass after the fix. The slice 6s, 6w, 2h and 6y documents carry a dated correction; their original text is kept.

## What the review found, and the fix

1. **Differencing protection was bypassed by a different grouping or an exclusion definition (high, slices 6s and 6w).** The 6w check compared only releases of one *series*, keyed by grouping and exclusions. All villages (6 provisional identities) and village V with the same grouping were compared, but village V grouped by village, team, age band or programme was a different series and was released (5), revealing 1 outside V. In one request, the cohort total (30) minus an owner definition "patients excluding provisional identities" (28) revealed 2 while the provisional count itself would have been withheld. This is the second review in a row that bypassed the check with a rule-specific key.
2. **The query window was not part of a release's identity (high, slice 6w).** A same-filter query over another window replaced the protecting release (all villages over 30 days, then all over 7 days, then village V over 30 days was released, revealing one referral outside V), and two windows were never compared (patients seen over 30 days minus over 9 days revealed one person).

   *Fix for 1 and 2 (`lib/saha/indicator-differencing.ts`, `lib/saha/indicators.ts`, `lib/saha/indicators-server.ts`):* the key-based comparison is kept, but it is no longer what protects small groups. Comparing releases by key cannot be made complete, so a new check does not compare keys at all. Each measure release now records what it disclosed: the measures shown (numerator and, for a proportion, denominator), the query and definition filters, the exclusions, the grouping dimension, the window start and which cells were suppressed (all hashed or from fixed vocabularies; still no names, villages or identifiers). Before a result is returned, every measure release the viewer received in the last seven days is re-evaluated against the people in their scope now, using the same hashed attributes, and the people are split into *atoms*: people who appear in exactly the same set of shown cells. For a windowed measure (visits, people seen, referrals, reuse, repeats, corrections) each person's value is split into window-to-window increments first, so the atom is "these people, between these two window starts". Every released figure is a sum of atoms, so any sum or difference of the viewer's released figures is a sum of atoms. A candidate result is withheld if any atom it creates or splits holds 1 to 4 (people, visits, referrals or other counted events). The same check runs for denominator minus numerator, per window, for the pairs a definition uses and for the fixed containment pairs (people seen within people, provisional identities within people, overdue within open follow-ups, completed within created referrals, served and blocked within reuse opportunities). Because it works from the people, not from keys, a grouped cell is the same as a filter, an exclusion is the same as any other restriction, and the query programme filter and a definition's programme filter are the same condition. A query over a different window is a different release: it never replaces one over another window, and nested windows are compared through the increments.

   The old key-based check (6s, 6w) still runs as well, now with the window in each measure release's identity; it also uses the counts recorded at release time, so it catches some changes between queries that the population check, which uses today's data, does not.

   *Residual risk, stated to owners:* the protection is still not complete, and the owner sees this in the indicator registry (and every result carries it as `differencing.limits`): it does not protect against two people combining what each was shown, against changes in the records between two queries (repeating a query after a new visit reveals that visit), against queries older than seven days, or against differences between unrelated measures outside the listed pairs; and a denominator-minus-numerator difference across two windows is checked per window, not by increments. The check is conservative: it refuses when a small atom exists even if no combination of releases actually determines it. That is the trade-off. In the property run below, 211 of the 314 queries' indicator results were withheld over 26 to 43 synthetic people in three villages (the base withheld 63, and released 86 nested pairs differing by 1 to 4). With realistic team sizes far fewer results are withheld, but small teams and narrow filters will see more "withheld" results than before.

   The fallback the brief suggested (refuse any query that nests with an earlier one unless identical) was not needed: the atom check is the conservative rule, and it still allows drilling down from a total into disjoint groups of 5 or more.

3. **The paged-window audit was opt-in (medium, slice 6w).** A supervisor with more than 500 people in scope who called `GET /api/workspace` without `x-saha-patients: paged` received every in-scope full record and no `viewPatientRecord` event was written.
   *Fix (`lib/saha/server.ts`, `lib/saha/access-audit.ts`):* chosen option — audit the full read. A workspace read (or the snapshot returned after a command) without the paging request, by a non-ASHA viewer whose scope is above the paging threshold, records a `viewPatientRecord` event for every returned record not opened through the detail route or the window in the last 12 hours, before the records are returned; if the event cannot be written, only records already recorded in that period are returned (fail closed). The look-up of already-recorded records is chunked under D1's bound-parameter limit. Paging on the server regardless of the header was not chosen because the unpaged read is the independent oracle of the work-list tests (slice 0b-4) and the load envelope; making it empty would have removed that check. ASHAs and scopes at or below the threshold read as before.
4. **The differencing ledger was bounded by count, not size (medium, slice 6w).** 400 grouped releases per viewer over 60 villages are about 1.2 MB and D1 refuses a value over 2 MB, so two such supervisors failed every query with a raw 500 until releases aged out.
   *Fix (`lib/saha/indicator-differencing.ts`, `lib/saha/indicators-server.ts`):* the ledger is also bounded by serialized bytes: 1,000,000 for the organisation and 250,000 per viewer (the count bounds stay). Reaching either refuses the new query with 429 and the existing "many different queries" message. A ledger write that D1 refuses for any reason is also answered with that 429, not a raw 500. The ledger stays in the operations row; it was not moved to its own table (no migration).
5. **ABHA refusal in record import was a three-name denylist (low-medium, slice 2h).** Issuers `abha_number`, `healthid` or `abhaid` with 14-digit values were accepted, skipping ABHA verification and organisation-wide ABHA uniqueness.
   *Fix (`lib/saha/record-import.ts`):* issuers are an allowlist (`KNOWN_ISSUERS`: `rch`, `nikshay`); any other issuer is refused with a reason naming the listed ones. A value shaped like an ABHA number (14 digits, optionally grouped 2-4-4-4) or an issuer code containing `abha`, `health`, `hid` or `phr` is refused under any issuer with the ABHA reason. Adding an issuer is a code change; an owner-maintained issuer list was not built.
6. **The rejection report's audit moved the organisation revision (low, slice 2h).** It was written through `recordExportAudit` → `persist`, an organisation-wide commit with a command receipt, so a clinician saving at the same time got a 409.
   *Fix (`lib/saha/record-import-server.ts`, `lib/saha/access-audit.ts`):* the event is written with `recordAccess` (slice 6t pattern) before the file is returned: it appends the event only and moves no revision. Its detail text is unchanged.
7. **A redacted trace returned the destination receipt (low, plausible, slice 6y).** For an owner or administrator outside the patient's scope the thread still carried the receipt string.
   *Fix (`lib/saha/trace.ts`, `app/trace-panel.tsx`):* a redacted trace sets `receipt` to null and says only `receiptExists`; a full trace carries both. The panel shows "recorded (not shown outside your care scope)".
8. **Trace look-ups dropped the newest events silently (low, slice 6y).** The execution and access look-ups were `ORDER BY at LIMIT 300/200` ascending, so a long history lost its latest events with no sign.
   *Fix (`lib/saha/trace-server.ts`, `lib/saha/trace.ts`, `app/trace-panel.tsx`):* both look-ups are newest first (`ORDER BY at DESC, seq DESC`), and the trace says `truncated: true` when a look-up reached its limit; the panel then says only the most recent events are listed. The output is still sorted oldest first.

## Limits

- The differencing protection is not complete (see the residual risk above); it is a per-viewer, seven-day, today's-data check.
- The population check re-evaluates every measure release of the viewer's last seven days against everyone in scope on each query. With 400 releases and some thousands of people this is several million membership tests per query; it has not been measured on a Worker at that size.
- Releases recorded before this slice have no disclosure fields and are used only by the key-based check until they leave the seven-day window.
- An unpaged read of a large scope writes one audit event per record not recently recorded, in one commit; for scopes of several thousand records that commit is large. Paging clients are unaffected.
- The issuer allowlist is in code; an owner cannot add an issuer.
- These fixes have not been independently reviewed. BR-REP-04, BR-AG-11, BR-SEC-08, BR-DATA-11 and NFR-18 stay partial; their current text and evidence are updated.
