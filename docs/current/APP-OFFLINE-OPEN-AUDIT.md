# Durable client-reported offline presentations

5 October 2026. Synthetic local software implementation; this document does not close BR-SEC-08 or formal/device acceptance.

The browser must commit a fixed metadata report inside the encrypted notebook transaction before showing a new cached name list, patient record, registration form or match result. A failed transaction denies that new display and leaves the prior ciphertext intact. Repainting, typing, blur and ordinary saves do not create presentations. The report describes a browser claim, not a server-observed clinical read or proof that a human saw the material.

The fixed reference kinds are prepared grant, accepted registration, protected match-copy receipt, and unresolved local registration. Prepared provenance comes from the immutable original-worker grant, including issuance, expiry, original role and baseline versions. Accepted registration and candidate provenance come from their original server registries and exact accepted receipt. Legacy unavailable provenance remains unknown. A wholly unsent form has only an opaque encrypted form ID and content digest; the server checks its worker's stored own-organisation relationship and creates no patient subject or historical clinical permission claim.

When that same opaque form ID later receives a trusted accepted registration receipt, a separate count-zero mapping report can append that exact correlation. It leaves the original unresolved presentation immutable and makes no claim about patient permission at its earlier client time. No time or patient-name join is used.

A server upload validates every reference and prior replay body before any write. It atomically appends report records, trusted derived patient-subject rows where available, and chained audit events. Changed metadata under an existing UUID refuses the entire batch. Exact retries do not duplicate records or audits. The response returns only the original authenticated worker and accepted report IDs. No clinical or organisation revision changes. A revoked, expired or suspended worker can submit their own historical metadata without obtaining clinical content or renewing a grant.

The encrypted queue is bounded to 2,000 outstanding reports and retains exact UUIDs after uncertain network, receipt or acknowledgement-save outcomes. Uploads are bounded to 20 reports and 12,000 bytes. Pending reports survive prepared/registration privacy deletion and retain no names, facts, packet, tokens or client-supplied patient authority. Accepted local-form links remain bounded until exact correlation is available; a full pending-report queue prevents further material opening; a full unresolved local-form link budget prevents opening further local forms until exact correlation or deliberate eligible reset succeeds. Already received local-only history stays on the server after eligible reset, even when no later mapping becomes available. Manual reset must refuse pending reports.

Client-reported occurrence and server receipt time remain separate. Client clock rollback, fabricated client reports, modified browser code, lost/tampered/evicted storage and a device that never reconnects cannot establish complete clinical-access coverage. Successful durable queuing records the application boundary locally; it cannot prove physical erasure or prevent an already unlocked copy from being viewed outside that boundary. Formal field/device and hosted qualification remain separate.

Both original `/field` and app offline surfaces queue before initial cached name-list display, automatic prepared-record entry, deliberate record/form/list re-entry, new prepared or registration copies, and returned match-candidate presentation. Internal scope refreshes, rendering, blur, save and language changes do not increment counts. Clinical additions and the report share one encrypted compare-and-swap transaction; metadata writes reserve the existing persistence chain and reject stale owner/lock epochs. The service-worker namespaces advance and cache only the fixed public module, never an API response.

Historical reports upload before current care validation, so positive ownership withdrawal can purge raw material and still record earlier client claims. If a later strict receipt check refuses after a committed purge, recovery reads the newer ciphertext and uploads only its metadata. An initial purge abort must not trigger this recovery: the original ciphertext remains exact, all plaintext is hidden, and the original privacy latch/refusal remains. No clinical receipt body is resent or changed.

Migration 0023 adds immutable reports and derived subject rows alongside the original registration registries and 0024 wire receipt mappings. Protected export retains only the exporting actor's metadata reports and filters patient subject rows by current patient scope. The existing latest migration marker remains 0024, and populated export/reimport checks preserve all tables and chains.

Evidence is in `tests/evidence/offline-opens/`: real encrypted-storage contracts, actual Worker/D1 HTTP checks, phone-sized Chromium checks, and affected privacy/registration/field/export regressions. Initial fixture/schema failures and the detected purge-abort recovery regression are kept separately from repaired results. These are synthetic local software checks, not installed-device, hosted-load, physical-erasure or complete clinical-access acceptance.
