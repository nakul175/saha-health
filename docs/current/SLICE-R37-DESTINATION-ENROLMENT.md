# Development slice r37 — destination enrolment request/rejection/acceptance lifecycle against a mock programme destination

3 October 2026 (IST). Adds a versioned, audited state machine for a programme episode's *destination enrolment* (`local → requested → accepted | rejected | uncertain | retryable → active`), driven by a demonstration/mock programme destination only. It reuses the checkpoint/idempotency/receipt pattern of `lib/saha/mis-execution.ts` and `lib/saha/mis.ts`. Synthetic data only; formal acceptance unchanged. BR-PROG-06 stays partial. The slice is built on a lane branch and has not been independently reviewed.

## What changed

- **A versioned, audited destination-enrolment state machine.** A local programme episode (an `Enrolment`, slice 2h) starts with `registration: 'not_submitted'` and no `destinationEnrolment`. `lib/saha/destination-enrolment.ts` adds the lifecycle that takes it through `requested` → `accepted`/`rejected`/`uncertain`/`retryable` → `active`. Every transition increments `version`, appends a bounded history entry (20), and is audited through the execution module. Only a verified destination acceptance can reach `active` (official registration `submitted`), and a rejection leaves the episode locally visible with a clear reason and no false enrolled status — exactly what BR-PROG-06 requires.
- **Request → accept/reject → active, with no automatic activation.** `requestDestinationEnrolment` (an ASHA or clinician in care scope) builds a request body bound to the episode (no patient name), records a durable checkpoint, and asks the destination. A destination acceptance records a simulated reference but does *not* mark the episode enrolled; `activateDestinationEnrolment` (a clinician, supervisor or organisation owner, with a reason) is the separate programme-specific authorisation that sets `active` and `registration: 'submitted'`. A rejection records the destination's clear reason and leaves the episode active but not enrolled.
- **The mock destination only — no network, no real partner.** `lib/saha/destination-enrolment-adapter.ts` is a pure, deterministic simulator. The destination must be an active `mis` integration in `demo` mode whose programme list covers the episode; an HTTP, inactive or non-demo connection is refused ("mock adapter only"). The destination's `behavior` decides the outcome: `accept` returns a simulated reference, `reject` returns a clear reason, and `uncertain` loses the first response (a lookup then finds the record, modelling safe reconciliation rather than a blind resend). There is no clock, randomness, fetch or credential. The environment gate mirrors slices 10b/6n: the simulator runs only in the synthetic and training environments and is refused everywhere else.
- **Checkpoint/idempotency/receipt, reused.** `lib/saha/destination-enrolment-execution.ts` mirrors `mis-execution.ts`: a checkpoint is persisted before the mock adapter is called, then the adapter's decision is applied on a fresh read under the organisation's compare-and-swap guard (three retries), so a concurrent change never authorises a blind resend. The receipt is bound to the request's key and payload hash, `not_found` is only accepted on a lookup, and an uncertain outcome stays `uncertain` until a lookup resolves it (`retryable` or terminal). The original requesting worker performs the lookup; a second worker is refused.
- **Wiring (additive).** `destinationEnrolmentSchema` is added to `lib/saha/platform.ts`; `authorizeDestinationEnrolment` and `executeDestinationEnrolment` are dispatched in `lib/saha/server.ts` (replay re-checks authority, as for the other commands). `lib/saha/types.ts` extends `Integration.behavior` with `reject` (the existing `accept`/`uncertain` values are unchanged) and `lib/saha/programmes.ts` extends `Enrolment` with `registration: 'submitted'` and an optional `destinationEnrolment` record. No migration, no new table, no change to any MIS/EHR/ABDM adapter.

## Evidence

- Contract test `tests/destination-enrolment-contract.mjs` (45 checks). Schema and authority (care role to request/look up; clinician/supervisor/owner to activate); the pure mock adapter (accept/reject/lost and the environment gate); `requestTarget` validation; receipt application (accepted, rejected, idempotent repeat, conflicting terminal, `not_found` lookup-only, enrolment-reference and key/payload-hash matching); the execution happy path (accepted, still `not_submitted`), the rejection path (locally visible, not enrolled), the lost-response → uncertain → lookup reconciliation path, `not_found` → retryable, original-worker-only lookup, activation to `active`/`submitted`, the environment refusal, and a compare-and-swap conflict on the final write that is retried, not lost. The harness injects a compare-and-swap `store` and a mock transport; no network I/O and no real partner. Result: `tests/evidence/slice-r37/`.

## Limits

- **Demonstration destinations only.** The request and lookup use the deterministic in-process simulator; no HTTP destination-enrolment contract is implemented. A real partner's enrolment/registration acceptance is a separate piece of work, exactly as the MIS and aggregate-delivery adapters keep their real-partner paths out of scope.
- **Activation is a local authorisation.** `active` means the destination accepted the request *and* a Saha clinician/supervisor/owner recorded the programme-specific authorisation. It is not evidence of a real registry write; the simulated reference (`SIM-ENROL-…`) is a label, not a partner record.
- **No per-patient read screen.** The record is stored on the episode (`enrolment.destinationEnrolment`) and returned through the existing command snapshots; a dedicated scoped read route and surfacing it in the action plan/exception queue are separate, additive work left to the integrator.
- **Authority is role-based and normal-access.** An ASHA or clinician requests and looks up; a clinician, supervisor or owner activates. Owner authority does not widen the patient's team scope.
- Not independently reviewed.
