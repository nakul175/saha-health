# Development slice 6w — fixes from a fifth independent review of slices 0b-4, 4e, 6s and 6t

1 October 2026 (UTC). Builds on `int6-2g-note-answer-signoff` (`d00e438`: round 1 and round 2 of the overnight build). Synthetic data only; formal acceptance unchanged. No command, route or migration is added; the route count stays 45 and the certified patient command count stays 50. `indicatorExport` joins the access-audit action list.

These defects were found by a fifth independent review, carried out by an agent that did not write the code, of round-1 slices 0b-4 (server work lists), 4e (programme pack migration), 6s (indicator registry and differencing) and 6t (access audit), with the 0b-3 paged window they build on. That code had been built, tested and recorded as passing; the earlier runs did not test these cases. Each defect was reproduced on the base before it was fixed, with the new regression checks, which fail on the base and pass after the fix (and, for findings 1–3, with the reviewer's scripts `s6-diff.mjs` and `s6-defs.mjs`). The slice 0b-3, 0b-4, 4e, 6s and 6t documents carry a dated correction; their original text is kept.

## What the review found, and the fix

1. **Differencing compared people counts only, never numerators (high, slice 6s).** A query for provisional identities over all villages (6) and then over village V (5) were both released, so exactly one provisional identity outside V was revealed: the cohorts differed by 10 people, so the people-count test passed.
   *Fix (`lib/saha/indicators.ts`, `lib/saha/indicator-differencing.ts`):* every definition now contributes two series: its people per cell, and a measure series keyed by numerator and denominator measure that records each cell's numerator and denominator. The remainder test (1 to 4 is refused) is applied to people, numerator, denominator and denominator minus numerator. Ledger entries from before this slice (people only) are still read.
2. **Ledger eviction dropped protecting entries inside the window (medium-high, slice 6s).** The ledger was shared by the organisation and cut to its newest 500 releases; a parent query followed by 250 unrelated queries pushed the parent out, and the child that differed from it by 3 people was released.
   *Fix:* pruning is by time only (seven days). A repeat of the same viewer, series and filters replaces its older release, which the check never used (it reads the latest release per filter set). When adding a query would take the viewer past 400 distinct releases in the window, or the organisation past 4,000, the query is refused with 429 and a message to repeat an earlier query or wait; nothing inside the window is dropped.
3. **Definition filters were part of the series key, so complementary definitions were never compared (medium, slice 6s).** Owner-maintained definitions "all people", "female" and "male" (22, 10, 10) were each released, revealing 2 people of another sex.
   *Fix:* a definition's own filters (sex, age band, programme) travel as nesting dimensions of the release (`sex`, `ageBand`, `defProgramme`), beside the query filters, and the series key holds only grouping, exclusions and, for a measure series, the measures. The candidates of one query are screened in order, each against the ledger plus the candidates already accepted from the same query, so all/female/male in one request releases two of them and withholds the third.
4. **Every indicator view committed organisation-wide (medium, slice 6s).** JSON, CSV and GET queries went through `persist`, moving `organisation.revision` and writing a command receipt, so a clinician's save could fail with 409 and every workspace refreshed; a cross-site GET could trigger it.
   *Fix (`lib/saha/indicators-server.ts`, `lib/saha/store.ts`):* the ledger is written by its own compare-and-swap statement on the ledger value inside the operations row (`json_set` guarded by the ledger read before), retried on a fresh read up to three times; it moves neither revision and writes no receipt. Commands that save the operations row now keep the stored ledger (`store.guarded` merges it), so a command built on an older read never drops releases recorded since. The CSV export's audit event is an access-audit commit (`indicatorExport` in `ACCESS_ACTIONS`), written before the file is returned and failing closed; the Activity log groups it with the other access events. `GET /api/indicators` answers the catalogue and question interpretation only; a GET naming indicator ids answers 405.
5. **The migration dry run showed organisation-wide counts and every batch to any clinician (medium, slice 4e).** `outOfScope: 1` revealed one pregnancy episode in another team, and the batch history carried other appliers' examined and out-of-scope counts.
   *Fix (`lib/saha/programme-migration-server.ts`, `lib/saha/programme-migration.ts`, panel):* an owner sees the dry run and history as before. A clinician sees `examined` counted within their care scope, `outOfScope: null`, `scopeOnly: true`, and only the batches they applied, without examined and out-of-scope counts. A clinician's apply result returns `outOfScope: null`. The panel says the counts cover the reader's care scope.
6. **Data exit exported the differencing ledger (medium, slice 6s with 6m).** Hashes of organisation id plus user id or village are reversible by guessing, and cells held unsuppressed counts from other viewers' scopes.
   *Fix (`lib/saha/data-exit.ts`, `scripts/verify-export.mjs`):* the operations row is exported without `indicatorReleases`, and the table note says so. The offline verifier has a new `protection-state` check that fails an archive whose operations document carries the ledger.
7. **The paged workspace window returned full records without an access event (medium-low, slices 0b-3 and 6t).** A paging client could name up to 50 patient ids in `x-saha-patient-window` and receive their full records on every workspace read without the `viewPatientRecord` event that `/api/patients/detail` writes.
   *Fix (`lib/saha/access-audit.ts` `auditWindow`, `lib/saha/server.ts`):* chosen option — audit, not restrict. A window id the viewer has not opened through the detail route, or re-read through the window, in the last 12 hours is recorded as a `viewPatientRecord` access (one access-audit commit for all such ids, naming an emergency grant where one is the route) before the record is returned. If that event cannot be written, those ids are left out of the window and nothing of them is returned. Restricting the window to opened ids was not chosen because the workspace and command responses already rely on the window for patients just created or acted on, and existing HTTP checks exercise that.
8. **No checkpoint past 100,000 chained events (low, plausible; slice 6t).** A checkpoint was issued only when a full verification said `intact`; past 100,000 events it says `incomplete`, so checkpoints would be refused for good.
   *Fix (`lib/saha/audit-chain.ts`, `lib/saha/audit-chain-server.ts`):* `verifyChain` can start from an anchor: the event at the anchor must still hold the anchor's hash and every later event must link from it. When the full verification is incomplete, a checkpoint request is verified from the checkpoint the owner names (`checkpoint=seq:hash`) or else from the last checkpoint recorded in the chain. The response (`verifiedFrom`) and the audit line say which anchor was used.
9. **Work-list pages could skip or repeat rows (low, slice 0b-4).** The offset cursor did not notice a list that re-sorted between pages, and the panel appended pages blindly.
   *Fix (`lib/saha/worklists.ts`, `app/worklist-panel.tsx`):* the cursor carries the view's total as well as the offset (`n:<offset>:<total>`, digits only). If the total has changed, the server serves the first page with `restarted: true`, and the panel replaces its rows and says the list was loaded again. A cursor without a total (`n:<offset>`) is still accepted.

## Limits

- The ledger still lives in the organisation's operations row: its size grows with distinct queries per viewer in seven days, bounded at 4,000 releases. At that bound new indicator queries are refused until releases leave the window. A busy organisation could reach it; the bound was not measured against D1's row size limit.
- Releases recorded before this slice used series keys that included the definition's filters; apart from the cohort series they are not compared with releases recorded after it, and they leave the seven-day window within a week of deployment.
- The differencing check compares one viewer's releases only. Two supervisors can still combine their results outside Saha.
- The measure series compares queries using the same numerator and denominator measures; a definition built from a different measure that counts the same thing is not compared.
- The ledger write is not atomic with computing the result: authority is checked when the result is computed, and the release is recorded afterwards. A query refused for differencing returns nothing.
- Window auditing records an access at most once per patient per viewer in 12 hours; a workspace left open longer re-records it on the next read.
- The migration out-of-scope count is still in the stored batch and in the owner-visible audit line; audit events naming another team's patients are not re-filtered here.
- Anchored verification does not re-read events before the anchor. An anchor taken from a checkpoint recorded inside the chain is only as trustworthy as the chain up to it; a checkpoint the owner kept outside Saha is the stronger anchor. If more than 100,000 events follow the anchor, the checkpoint is still refused.
- The work-list restart catches lists whose total changed; a list that re-sorted with the same total can still skip or repeat a row between pages.
- These fixes have not been independently reviewed. BR-REP-04, BR-AG-11, BR-PROG-07 and BR-SEC-08 stay partial and NFR-24 stays unverified; their current text and evidence are updated.

## Correction — 2 October 2026 (slice 6aa)

A seventh independent review found that fixes 1 to 3 above were incomplete: the series key (grouping and exclusions) let a differently grouped figure or an exclusion definition escape the comparison, the window was not part of a release's identity, the ledger bound counted releases but not bytes (D1 refuses a value over 2 MB), and the paged-window audit applied only when the client sent the paging header. Slice 6aa replaces key comparison as the protection with a population check, keys releases on their window, bounds the ledger by size with a 429, and audits an unpaged read of a large scope. See `SLICE-6AA-SEVENTH-REVIEW-FIXES.md`.
