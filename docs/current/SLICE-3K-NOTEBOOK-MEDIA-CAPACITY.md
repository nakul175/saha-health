# Development slice 3k — field notebook at 200 visits plus 100 photos and voice notes

2 October 2026 (IST). Field slice, stacked on the round-5 integration (`int9-7g-aggregate-delivery`). Synthetic data only; formal acceptance unchanged. No migration, no route and no server change.

## What changed

- **Device media budget: 100 items and 25 MB.** The field notebook (`public/field/app.js`) held at most 1 MB of queued media across the device, which is four reduced photos. It now holds up to 100 photos and voice notes waiting to upload (`MEDIA_DEVICE_ITEMS`) and up to 25 MB of them (`MEDIA_DEVICE_BYTES`, 100 times the 256 KB item limit), so 100 items of any permitted size fit beside 200 visit drafts. Four items per draft, the 256 KB item limit, photo reduction (slice 3e) and per-item encryption (slice 3a) are unchanged. The 101st item is refused before anything is written, with a bilingual message to sync or discard first; the 25 MB check stays as a guard but cannot be reached while the item limit is 256 KB.
- **The storage checks still come first.** The slice 3b low-space pause (under 50 MB free or over 80 percent of the browser's allowance used) is checked before every prepare and every queued item, as before. The new budget (25 MB of media plus about 1 MB of sealed notebook) is smaller than the 50 MB free-space floor, so on a device with under 50 MB free the pause refuses new work before the budget is reached.
- **A long Sync all keeps the notebook open while it progresses.** The notebook locks after two minutes without a tap or key press, and before this slice nothing restarted that timer while Sync all ran (the new client check below shows no re-arm on the old code). Sync all of 200 visits and 100 items took about 110 seconds of wall time on loopback with no emulation (restart run below), so on any slower connection the idle lock would stop the run part-way. Each draft, registration or upload that the server confirms now counts as activity and restarts the two-minute timer. A run that stops making progress (a stalled request) still locks after two minutes, and hiding the page still locks it at once.

## Evidence

- 30 client checks (`tests/field-media-capacity-client.mjs`, in CI; the slice 3j Node harness with real Web Crypto and vault sealing, injected storage and an idempotent fake server): 200 drafts and 100 items (75 reduced photos of 247,500 bytes and 25 voice notes of 240,000 bytes, 24.56 MB in total) queued and sealed one by one, with media bytes kept out of the notebook record; the 101st photo and the 101st voice note refused with the new message, with nothing written, deleted or sent; the 201st draft refused with no network call; discarding one item frees one place; lock and unlock return all 200 drafts and 100 sealed items, and a sealed voice note opens to its recorded hash; a lost response on the 120th visit stops Sync all with that draft's key kept; after a restart (lock and unlock) the next run sends that key first and then the remaining drafts in notebook order; a lost response on the 50th upload stops the run with the item's key and sealed copy kept, the sweep on unlock spares it, and the next run resends it first with the same key; at the end the fake server holds 200 visits and 100 items, each applied once, every device receipt and media id matches the server, and no sealed copy remains. The idle-lock check fails on the code before this slice (no timer was re-armed during the run).
- Browser check, restart (`tests/evidence/slice-3k/3k-restart-none.json`; headless Chromium at 412 × 915 with real IndexedDB and Web Crypto, the built Worker served locally on loopback, no network emulation): 201 synthetic patients created and assigned through the API; 200 visits prepared through the notebook's own Prepare button (server-signed grants) and 100 items queued through its file input — 75 canvas-drawn photos reduced on the device and 25 synthetic WebM voice notes, 8.56 MB in all (59,577 to 178,785 bytes each). The 101st item and the 201st visit were refused with the new messages, and the 201st patient has no visit on the server. IndexedDB held the notebook plus 100 sealed items; the browser reported 8.9 MB used of a 492 MB allowance. Lock and unlock returned all 200 drafts. Sync all was then interrupted by reloading the page after 100 visit commands had been sent, and again after 50 uploads; after each reload the notebook was unlocked and Sync all run again. The second run sent 101 commands (the interrupted one again, with its key, then 100) and the third 50 uploads. At the end the device showed 200 synced visits with receipts naming their own visits, 100 uploaded items and no sealed copies; the server held 200 visits for the 200 patients and 100 media items, each once, matching the device's media ids. No console errors.
- Browser check, timing (`tests/evidence/slice-3k/3k-timing-3g-like.json`; the same setup on a fresh local server, built with this slice's idle-lock change): with Chromium network emulation of 300 ms latency, 1.6 Mbit/s down and 750 kbit/s up applied to the page, one uninterrupted Sync all of the 200 drafts and 100 items (8.56 MB) took 300.5 seconds and finished with all 200 visits and 100 items synced, each once on the server, and no console errors. It ran past the two-minute idle lock without locking. The run sent 400 command requests (200 prepares before the run, 200 syncs in it), 100 uploads and 27 workspace reads; the time to finish the drafts alone was not recorded. Filling the notebook (200 prepares and 100 queued items, no emulation) took 108 seconds and unlocking 0.7 seconds. These are local emulation figures on a shared two-core build machine, not the reference network or a phone.
- The restart run above used the build before the idle-lock change (each of its three Sync all segments was under two minutes). The first three throttled attempts gave no result: the memory-limit killer ended the local `workerd` process (1.3 GB resident) during the first, the second could not connect to the stopped server, and in the third the page's renderer crashed after 100 prepares; the sandbox's memory is shared with other builders. Each was restarted on a fresh local server.
- All suites: see `VALIDATION.md`.

## Limits

- Local emulation only. Chromium's network throttling on the build machine is not the reference network or device in NFR-12, which stays unverified. No physical phone, real quota pressure, eviction, background sync or battery use was tested.
- The browser run's photos are synthetic drawings that reduce to 58–175 KB; the near-limit case (100 items at about 247 KB, 24.6 MB) was tested only in the Node harness.
- The Sync all summary counts uploads per completed draft: when a run stops part-way through a draft's items, items already uploaded on that draft are not in the summary (they are marked uploaded on the device and are not sent again).
- Each upload is preceded by a fresh workspace read for its draft (slice 3a), so Sync all reads the workspace once per draft with media, and the notebook is still one encrypted record rewritten on every save (slice 3j). Batch preparation, per-record notebook storage and device-measured thresholds are not built.
- The Hindi strings added here have not been reviewed by a native speaker.
