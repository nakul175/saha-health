# Development slice 6y — trace from a user task to provider calls and destination receipts

1 October 2026 (UTC). Builds on slices 6i (exception queue), 6t (material-read audit), 5e (task limits), 6u (EHR publications closed as not sent) and the MIS, EHR and assistant execution checkpoints. Synthetic data only; formal acceptance unchanged. One read route is added (`GET /api/trace`); no command and no migration.

## What changed

- **Correlation from now on.** Every step an external execution adds now carries a correlation reference (`TraceRef`): the command type that caused it, that command's receipt key, the actor, and the id of the audit event written in the same commit. `linkTrace` (`lib/saha/trace.ts`) stamps it on the steps a commit adds, immediately before the commit is persisted, in every path that adds such a step: the generic command path in `lib/saha/server.ts` (plan execution, EHR publication preparation, assistant preparation, cancellation, apply and timed-out decisions, consent withdrawal), the programme delivery checkpoint and receipt (`mis-execution.ts`), the EHR publication checkpoint and receipt (`ehr-execution.ts`), the assistant checkpoint and result (`agent-execution.ts`) and the signed programme callback (`app/api/mis/callback/route.ts`). The reference lives in the record's existing JSON: programme delivery events gain `ref` and `attempt`, EHR publications gain an `events` list (before this slice a publication kept only its latest state), assistant requests gain a `trace` list, and demo submissions gain a one-step `trace`. Nothing written earlier is rewritten; older steps have no reference and are shown as **not linked**.
- **Which audit event.** The reference names the audit event of the same commit about the record itself, else about its visit, else about its patient, else the commit's first event. One commit can link several steps (a plan execution that creates two submissions links both to its `executePlan` event).
- **The trace.** `GET /api/trace?visit=<id>` (or `?submission=<id>`, or `?publication=<id>`) returns, for each programme submission, EHR publication and assistant request of the visit, an ordered list of steps: time, state, attempt number, whether the step came from a user command, a destination or provider response (`misReceipt`, `ehrReceipt`, `agentResult`) or a destination callback (`misCallback`), the command type, who did it, the receipt id (the command's receipt key, and whether its `command_receipts` row was found and when it was written) and the linked audit event's id and chain sequence. Each item also gives its destination or provider, current state, the destination receipt id, attempts used against the limit (three sends for a programme delivery, one publication, one provider call per approved assistant request), and for assistant requests the 5e task limits, the task attempt number on the visit and whether the request has timed out with an uncertain outcome. A separate list gives the audit events of the visit's external work (execution actions about the visit or its items, events linked from steps) and, for viewers with care scope, the slice 6t record-access and external-request events about the visit, each with time, sequence, action, actor and role and the steps it is linked to.
- **No clinical content.** Ids, states, times, attempts, limits, command types and actor names only. The trace never returns facts, notes, assistant input or output, payloads, document bundles, audit detail text (the route does not select the `detail` column) or credentials. The query takes exactly one record identifier (letters, digits, `-` and `_`, at most 200 characters) and nothing else; any other parameter is refused with 422.
- **Who may see it.** *Decision:* the people who may open the visit see all of it: the assigned ASHA, clinicians, supervisors and owners in the patient's team, and a clinician with a current emergency-access grant. Owners and administrators may open the trace of a programme submission or EHR publication of a patient outside their care scope, as the exception queue already shows them those rows: that one item only, without the patient or visit identifier, assistant requests, record-access events or audit subjects (the response says so). Owners are not widened beyond patient scope: a visit outside their teams is refused. Everyone else gets 404, the same answer as for a record that does not exist. Checks are on the server.
- **Not a material read.** *Decision:* reading a trace is not audited under slice 6t because it reveals no patient data beyond what the viewer's own scope already shows (no name, facts, notes or documents); it is like the exception queue, which 6t also leaves unaudited. A trace read writes nothing: no audit event, no receipt, no revision change (asserted over HTTP).
- **Screens.** The visit's Receipts tab has a "Trace: commands, checkpoints, receipts and audit events" disclosure that loads the visit's trace when opened. Each programme submission and EHR publication row of the exception queue has "Show trace", which opens that item's trace inline (redacted for owners and administrators outside the patient's scope). Each exception row now names its trace (`trace: {query, id}`) for these two kinds.

## Evidence

- 27 contract checks (`tests/trace-contract.mjs`): stamping of new programme delivery events with command, key, actor, attempt and the submission's own audit event, earlier events untouched, a commit that adds no step stamps nothing; EHR publication state changes, demo submissions and assistant requests stamped, with prepare, send, result and apply times; one-identifier query validation (none, two, repeated, free text, extra parameter, too long, unknown kind); scope for ASHAs, clinicians, supervisors, owners and administrators in and out of the team, a suspended member and an emergency-access grant; full and redacted assembly with linked and not-linked steps, receipt rows found and missing, audit sequences, assistant limits, task attempts and the timed-out flag; no names, notes, input, payload, document text or audit detail in either form; exception rows naming the trace; and source-order checks that each of the five paths stamps steps before the persist that records them, that the route selects no audit detail and does not write an access event.
- HTTP/D1 assertions (`tests/trace-smoke.mjs`): a local assistant request (prepared, sent, result) and a demo programme submission whose response is lost, each step linked to its command, receipt key (found in `command_receipts`) and chained audit event; the visit's FHIR download listed as a record-access event; no patient name, visit note, assistant input or measurement in the response; a trace read leaves the audit count and revisions unchanged; the ASHA, clinician and supervisor answered according to whether the patient is in their workspace; the administrator refused the visit and shown only the redacted submission; a non-member refused; query validation; the exception rows for the submission naming its trace for the owner and the administrator.
- Harness changes: `tests/mis-delivery.mjs`, `tests/note-answer-signoff-contract.mjs` and `tests/ehr-execution.mjs` now also transpile `trace` (and `operations`, `referral-rules`, `task-limits` where missing), because the execution modules import `linkTrace`. Their checks are unchanged.
- All suites: see [VALIDATION.md](../../VALIDATION.md). Reports in `tests/evidence/slice-6y/`.

## Limits

- Steps recorded before this slice are not linked, and EHR publications made before it show only their latest state. Correlation is not back-filled.
- Linking is to the audit event and receipt of the same commit; there is no separate trace or span id carried to the destination, so a destination's own logs are matched by the delivery key or document identifier, not by a Saha trace id. Saha's request ids (slice 6l) are not stored with steps.
- EHR execution events written before this slice name the patient, not the publication, so they are not listed for a visit. Programme callbacks that fail authentication leave no step.
- The trace covers programme submissions, EHR publications and assistant requests of one visit. EHR document retrieval, ABDM exchanges, evaluation runs and connection tests are not traced here.
- The trace is read on demand; nothing is pushed. NFR-18 and BR-REP-01 stay partial.

## Correction — 2 October 2026 (slice 6aa)

A seventh independent review found that a redacted trace carried the destination receipt string and that the look-ups kept the oldest 300 and 200 events, silently dropping the newest. Slice 6aa returns only whether a receipt exists in a redacted trace, looks events up newest first and reports `truncated`; the trace version is 1.1.0. See `SLICE-6AA-SEVENTH-REVIEW-FIXES.md`.
