# Protected work attribution and internal support

This B26 software batch adds current, receipt-linked active-work stages and a durable internal assistance workflow. It supplements independent fixed-band counters; those counters never enter completed-visit totals. Measurement stays disabled by default. External pilot measurements, observed savings, baseline comparability, costing and external help-desk integration remain acceptance work. Shared encrypted field timing hooks are a separate active software follow-up; the existing outbox infrastructure is not an integrated field capture claim.

## Saved command provenance

Migration `0021_work_burden.sql` enriches existing command receipts with nullable command type, initiating mutation subject/event and fixed task context. Common persistence derives these from exactly one newly appended matching command event by the actual initiating actor and their pre-mutation membership role. Provider/system events, ambiguous events and earlier/imported history are not guessed. Assignment/acknowledgement/closure context contains only server-validated task ID, parent ID and kind, with no detail-text parsing. Programme-answer commands whose initiating audit subject is the patient carry an exact server-validated visit ID only when that current visit belongs to the initiating event's patient; the receipt remains unavailable for another visit of the same patient. Legacy/direct helper receipts remain untracked. Existing receipt key, hash, result, replay behaviour and transaction remain unchanged. This operational metadata accompanies existing receipt rows even when measurement is disabled; disabled measurement adds no measurement rows or separate measurement writes.

## Protected stages

`POST /api/work-burden/attribution` accepts bounded fixed metadata: immutable UUID, expected original actor, visit and saved command receipt reference, session UUID, capture/correction/reconciliation stage, origin/segment/completion phase, integer foreground seconds, source and optional task ID. The expected actor is compared with trusted identity; it never grants authority. Current membership, normal patient scope, actual visit lineage, exact own receipt/event subject and specific task binding are required. A segment requires a saved origin for the same actor/session/stage/task. Origins precede confirmation; missing history is unknown. Capture and correction completion require the current confirmed visit's receipt. Reconciliation requires a matching current task command and closure; downstream evidence remains separate and is never fabricated by telemetry. Automatic recomputed obligations require no human timing stage.

Entries and their chained audit evidence append atomically under current organisation/patient revisions, membership versions, exact enabled configuration and a bounded per-visit entry count. Audit failure records neither entry nor success. Stable same-key retries read the immutable entry only after fresh scope checks and do not replay clinical mutations. No clinical revision moves. Digests cover client-reported metadata and server context; audit detail contains no facts, raw timing, free text, URLs or clinical request body. Exact IDs live only in the protected operational ledger and are omitted from aggregate reports.

The reachable online app observes foreground, focused input intervals with a 30-second idle bound. Successful clinical receipt callbacks originate and complete sessions; metadata delivery uses separate stable UUIDs and an explicit metadata-only retry. Online samples are in memory, so reload/account/organisation change or a denied metadata request can leave incomplete coverage. Amendment preparation contributes correction time; ordinary edited-fact capture contributes capture time once; manual assignment/acknowledgement/closure contributes reconciliation time. Independent correction/identity/void/backfill bands stay separate when no exact visit/task origin exists. These are client-reported active seconds, not independently observed staff time.

## Internal support workflow

`POST /api/work-burden/support` accepts only fixed category and protected visit/workflow references with an expected originating actor. A current care worker requests support; a current scoped operator assigns a distinct current helper; that helper attests; the original requester acknowledges. Assignment can change before attestation only. Every append carries immutable sequence, stable request/action key, current requester/helper/member and patient checks, and atomic chained audit. A sequence conflict calls for refreshed metadata, never clinical retry. No ticket text, patient content, reasons, URLs or external messages are collected. This is durable internal intervention linkage, not a claim that a real external help desk was used. The visit workspace includes request/assignment/attestation/acknowledgement controls with current helpers.

## Governed reports and limits

Operations reads are durably audited before disclosure and recheck current role/owner. A UTC-week report uses bounded grouped queries for at most 1,000 current confirmed local visits, explicit overflow, correction depth 32 and at most 500 stage entries per visit. A current corrected visit's total covers its own capture and correction work plus manual downstream reconciliation along its ancestor chain; earlier ancestor capture sessions are distinct visits and excluded. Every required observed session needs origin and completion; imported, partial, missing ancestry and open/undocumented downstream work remain unknown. Automatic recomputation is excluded. Mean and median use covered totals only; absence is not zero. Programme mix comes from the visit's pinned server capture, never a client-supplied programme list. Internal request/helper/requester-acknowledgement counts use the distinct recorded human care-active UTC denominator, separate from request latency metrics. No patient or actor IDs are returned in aggregates.

Both protected ledgers and receipt provenance are registered for scoped export/restore with matching applied SQL and `db/schema.ts`. History is append-only; imported history is not rewritten. Independent clinician/operational acceptance and a comparable observed pilot remain pending.
