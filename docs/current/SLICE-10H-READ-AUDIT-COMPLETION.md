# Development slice 10h — audit of the remaining read paths

2 October 2026 (UTC). Builds on slice 6t (material-read audit and fail-closed audit writes), slice 6w (paged-window audit) and slice 6aa (unpaged-read audit), and on the hosted-staging `main` at `150b9fc`. Synthetic data only; formal acceptance unchanged. One route is added (`POST /api/record-opened`: fifty method/route handlers); no command and no migration is added, so the certified patient command count stays 52. Requirement counts stay 14 implemented-local, 151 partial, 2 not-built and 9 unverified; BR-SEC-08 stays partial.

Slice 6t listed what it did not audit: the workspace snapshot, opening a record in the browser, searches and lists, and aggregate views. This slice audits those, with the same single-event, chained, fail-closed access commit, and adds the acting membership's version and delegated authority to access events.

## What changed

- **Workspace snapshot loads: one summarised event per load.** `viewWorkspace` is written when a whole-caseload snapshot is returned: `GET /api/workspace`, the snapshot returned with a command (when the client does not ask for a partition delta), and the snapshot returned when a saved command is replayed. The event names the viewer (as every event does), the scope size, how many records were returned in full, the paging window (opened records, scope total and threshold) for a paged workspace, the numbers of visits, referrals and submissions returned, and how many records were reached through emergency-access grants; and how the snapshot was asked for ("workspace load", "response to a command", "replay of a saved command"). It is one row however many patients are in scope, holds no name, id, fact or note, and is written after the window audit of slices 6w and 6aa and before the snapshot is returned.
- **Record opened.** A non-paged workspace carries the whole permitted caseload to the browser, so opening a record is a screen change the server never sees. `POST /api/record-opened` (`{personId, source}`, source one of work list, patient list, search, link, other) checks that the patient is in the caller's care scope (404 otherwise), writes one `openRecord` event naming the patient, and answers. The workspace now waits for that answer before it shows the record, and does not show it if Saha refuses (it could not write the audit entry, or the patient is out of scope). A repeat for the same viewer and patient within 60 seconds is acknowledged and not recorded again (a double click or a re-render is one open). The event is reported by the browser: it says the browser claimed an open, not that the server saw one. Opens that load the record through `GET /api/patients/detail` are recorded there (`viewPatientRecord`, slice 6t) and send no second event. Offline, when the report cannot be sent, the record is opened from the device and the person is told that the open is not in the organisation audit log.
- **Searches and lists: kind and result count, never the text.** `searchPatients` records a patient search (`POST /api/patients` with search text: "text search (name, village or id)", with or without a programme filter) and the duplicate check on registration (`POST /api/patient-matches`); `listPatients` records an unsearched patient page (browse or programme filter) and a work-list page (`GET /api/worklists`, view and attention tab). Each records the kind, first or later page, the rows returned and, where known, the total matching. The recorder is never given the search text or the entered name, age or village, so there is nothing to redact; the tests check that a distinctive search string and the entered name appear nowhere in the event.
- **Aggregate views.** `viewAggregate` records an on-screen indicator view (`POST /api/indicators` with ids: the figures and versions, how many were released and how many withheld, grouping, window, and which filters were set, not their values), the scoped care report (`GET /api/operations` in its JSON form, which is the preview of the CSV and support exports that were already audited as `opsExport`), and the aggregate report history (`GET /api/aggregate-reports`: counts only). No cell value is recorded. The indicator CSV export keeps its own `indicatorExport` event and writes no second event; the catalogue and question interpretation hold no results and write nothing.
- **Authority on access events.** Every access event, old and new, now ends with an authority clause: the acting membership's role, whether it is an organisation owner, its membership version, and the delegated authority in force at that moment (delegation kind, id, grantor and end, from slice 1e's own check). For a read answered from SQL alone (patient pages, work-list pages) delegations are not consulted and the clause says so: those views are scoped by the viewer's own membership and teams, and a delegation never widens patient access. The clause is part of the event's `detail`, so the audit-chain hash covers it; no schema change, no migration.
- **Fail closed, as in 6t.** All of these are written before anything is returned. If the event cannot be written the read is refused (503, "Saha could not record this access in the audit log, so it was stopped: nothing was shown or sent"). The exceptions (partition-delta command responses, searches over the already-loaded caseload, offline opens, and the report of a record open, which comes from the browser) are stated under Limits.
- **Activity log.** `viewWorkspace`, `searchPatients`, `listPatients` and `viewAggregate` carry no patient id, so only owners and administrators see them, and the log leaves them out of its default page so routine loads do not bury other events (`GET /api/audit?summaries=1`, and an "Include workspace loads, searches and aggregate views" checkbox for owners and administrators). They stay in the audit chain and in every export of it. `openRecord` names a patient and appears with the other "Record access" events for members in scope.

### Cost

One workspace load adds one audit row and, in D1 terms, one chain-head read plus one batch of two statements (the batch token update and the insert): three statements in two round trips, independent of the number of patients (500 stub records in scope cost the same three statements). For comparison, a viewer-scoped read of the contract's small organisation takes 26 statements. The extra write moves neither the organisation revision nor a patient revision and writes no receipt, so it cannot make a teammate's command conflict. The same one-row cost applies to a list page, a search, a record open and an aggregate view. A snapshot returned with a command costs one more commit on top of the command's own; a client that asks for partition deltas (the workspace does) pays nothing extra on commands. At one load per active user per hour, 100 users add about 2,400 rows a day; the audit chain's full verification stops at 100,000 chained events (slice 6w verifies from an anchor past that), so a busy organisation reaches that limit sooner than before. Those figures are arithmetic from the one-row rule, not a measured load.

## Limits

- **Reads that stay outside the server-enforced audit.** (1) A partition (delta) response to a command carries the full record of the patient just acted on; the command's own audit event is its record and no `viewWorkspace` event is written. (2) The browser's search over the loaded caseload, and filtering and sorting there, are not server reads; the load that brought the caseload is the audited event. (3) Offline opens from the device (the workspace opened offline, and the field notebook, which holds its own encrypted copy) cannot be reported; the workspace says so, and the notebook is unchanged.
- **Record opens are client-reported.** A changed or blocked client can skip the report; the server-enforced events are the loads (`viewWorkspace`, `viewPatientRecord` through the detail route and the window audit). The explicit open event shows what an honest client did, not that a person never saw a record.
- **A snapshot returned with a command is audited after the command committed.** If its audit event cannot be written the response is 503 although the command is saved; a retry with the same key replays it (and tries the audit again). The audit-store outage that causes this also refuses the next command at its own audit row, as before.
- **A failed indicator audit leaves the release in the differencing ledger.** The ledger entry is written before the view's audit event; if the event cannot be written the viewer is shown nothing but the ledger still holds the release, which errs toward withholding later queries.
- **Not yet audited:** other patient-level lists and queues (exception queue, referral requests and escalations, continuity, household, caseload preview, action plan, identity cases), pilot and expansion views, worker activity and the operations alert inbox. Only the reads named in this slice are covered.
- **Role, version and delegated authority are on access events only.** Command events keep the role column and their existing text; adding the clause there would change every command's audit text and was not done. Authority is the state at the time of the read (delegations in force for the member), not proof that a delegation was relied on.
- **Volume.** One row per load, search, list page and aggregate view makes the audit chain grow with reading. The default Activity log hides the summary events; the chain, its export and its checkpoints include them. There is no sampling and no aggregation window; a viewer who reloads often writes often.
- **Opens are coalesced at 60 seconds per viewer and patient**; two opens inside that minute are one event. Searches and list pages are not coalesced.
- BR-SEC-08 stays partial; NFR-10 is unchanged. These changes have not been independently reviewed.
