# Development slice 2j — correction propagation tasks

1–2 October 2026 (UTC). Builds on slices 1c, 4b, 6i, 7e and the existing visit amendment and wrong-patient void. Synthetic data only; formal acceptance unchanged.

## What changed

- **Every downstream output becomes a task.** When a clinician or ASHA amends a confirmed visit (`amendVisit`, which creates a correction draft) or marks a confirmed visit as recorded against the wrong patient (`voidVisit`), `lib/saha/correction-tasks.ts` lists every output that used that version before anything changes, and stores one task per output on the earlier visit (`correctionTasks`, JSON in the existing visit record; no migration). The outputs are: programme submissions (accepted, uncertain or sending, queued or retryable; rejected and cancelled ones reached no destination and are skipped), EHR publications (accepted, uncertain or running, prepared), the visit's unfinished sharing plan, open referrals made from the visit or naming it as a source, open follow-ups created between the visit's confirmation and the correction, protocol evaluations, assistant results (applied, open, and reviewed legacy AI results), shadow comparisons that scored the visit, worker-activity evidence and indicator releases recorded since confirmation (a count only). A visit with more than 60 such outputs is refused before anything changes.
- **External outputs are never corrected automatically.** For an accepted programme submission on an amended visit, when the destination has correction support enabled and its operation setting (slice 7e) permits `update`, the task is to send the destination's correction through the normal path: confirm the correction visit, then prepare, approve and execute its plan, which sends a correction replacing the earlier receipt (the existing `saha-mis-v1` `correct` operation). Otherwise, and for every void (Saha has no programme void operation) and every accepted EHR publication (Saha has no EHR amendment path), the task is a manual correction with the destination. An unknown outcome is a "look up first" task (never resend). An unsent delivery is a "cancel" task: the server already refuses to send a delivery whose visit is no longer current.
- **Internal outputs.** Work the server already refuses once the visit is not current is recorded as invalidated and done: the blocked plan, a prepared EHR publication, open assistant requests, and an evaluation with no findings or decision. Worker activity (slice 4c) and indicators (slice 6d) are computed on every read and recorded as recomputed. Outputs a person must judge become review tasks: referrals and follow-ups, decided or undecided protocol findings (re-run the check on the correction visit), applied assistant values (copied into the correction draft; check them before confirming), reviewed AI results, shadow comparisons (to note in Clinical governance) and, when releases were recorded since confirmation, whether a reissued indicator figure is needed. Indicator releases are reported as a count; no release content is copied.
- **Owner, age and link.** Each task names its owner (the worker who made the correction), its creation time and the earlier visit. Open tasks appear in the patient's action plan (slice 4b) as "Correction task" items with owner, age, the output's state at correction, destination and receipt, and a link to the earlier visit; external tasks are urgent. When the owner loses care access the item shows the ownership gap and the supervisors' queue. The exception queue (slice 6i, rules 1.3.0) lists each open task as a `correction-task` row with owner, age, recovery action and link; external ones are high severity. Administrators do not see these rows.
- **Closing needs evidence and is audited.** `closeCorrectionTask` (patient, visit, task, and a Saha receipt id or a reason of 10–500 characters, with an optional destination reference) closes one open task. A receipt id is accepted only for a "send correction" task and only when it is the receipt of an accepted submission to the same destination from a visit that corrects this one (the amendment chain); it is then recorded as verified. A cancel task cannot be closed while the delivery is still waiting. The close is appended to the task (who, when, receipt or reason, reference) with an audit line, and never changes the submission, publication, referral or any other output. Closed tasks are kept; nothing is deleted.
- **Scope.** A care worker with normal access to the patient (an ASHA only for an assigned patient), or a supervisor of the patient's team (or a slice 1e supervision delegate), may close a task. Administrators, members outside the team, an owner outside the team (owner authority does not override patient scope) and emergency-only access are refused. The same check runs when an idempotent request is replayed. `closeCorrectionTask` is a certified patient command (52), so it loads and commits only the named patient.
- **Workspace.** Correction items in the action plan carry a "Close with evidence" form (correction receipt where it applies, destination reference for external outputs, reason). The plan reloads after an amendment or void. The exception queue's kind filter includes "Correction task".

## Limits

- No programme destination in this release declares correction support for a void, and Saha has no EHR amendment or withdrawal path: those are always manual corrections with the destination, closed on a reason. The only partner correction path is the existing `saha-mis-v1` correction of an accepted submission, sent from the correction visit's plan; the demonstration simulators have no correction support.
- Follow-ups do not record the visit that created them; open follow-ups created between confirmation and correction are listed as possible dependants for review.
- Shadow comparisons, released indicator figures and the governance record are not changed; the tasks tell a person what to review. A patient-scoped commit cannot write organisation-level documents.
- Tasks cannot be reassigned yet; a lost owner shows as a gap with the supervisors' queue. Nobody is notified; the tasks are seen in the action plan and the exception queue.
- Corrections made before this slice have no tasks; nothing is backfilled.

## Correction — 2 October 2026 (slice 6ad)

A ninth independent review found that a visit with more than 60 downstream outputs could not be amended or voided: the refusal said to ask an administrator, but no administrator path exists. Slice 6ad corrects such a visit, keeps a task for every external output and folds internal outputs past the cap into one review task per kind with the count. The organisation-wide indicator-release count on the correction task is not changed. See [SLICE-6AD-NINTH-REVIEW-FIXES.md](SLICE-6AD-NINTH-REVIEW-FIXES.md).
