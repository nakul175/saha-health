# Development slice r17 — correction of imported identifiers and destination-specific identifier correction through the approval path

3 October 2026 (IST). Builds on slices 2h (record import and external identifiers), 10e (append-only identifier crosswalk ledger), 7g (aggregate-report prepare → approve → send → lookup pattern), 7e (adapter operation permissions) and 6t/6y (access audit and trace). Synthetic data only; formal acceptance unchanged. BR-ID-08 and BR-DATA-11 stay partial. The slice is built on a lane branch and has not been independently reviewed.

## What changed

- **Correction of imported identifiers with provenance.** The append-only crosswalk ledger is extended so an imported identifier (source `import`, slice 2h) can be corrected or withdrawn with full provenance. `prepareIdentifierCorrection` appends a `correct` or `withdraw` entry that names the entry it replaces (its id, or `import:<batch>:<row>` for an imported entry) and records who (`recordedBy`), when (`recordedAt`), where it came from (`origin`), its verification state (`unverified`, `document-seen`, `issuer-checked`) and the evidence described, plus the reason. The imported entry is never edited or removed: it stays in the record, its revision history and the history list. `currentIdentifiers` then holds only the new value, so the slice 2h record-import matching and the slice 10e identifier search follow the corrected value exactly as they do after an `identifierLink`.
- **`identifierLink` / `identifierWithdraw` are unchanged.** This slice adds a separate command; it does not alter the slice 10e commands. A local-only correction remains `identifierLink` with `corrects` (or `identifierWithdraw`); the new command is for a correction that must also reach a destination.
- **Destination-specific correction through the approval path.** A correction prepared for a destination is never sent automatically. `prepareIdentifierCorrection` records the local ledger entry and a `prepared` correction bound to one destination; `approveIdentifierCorrection` (a different authorised person, matching payload SHA-256, inside the 24-hour window) approves it; `sendIdentifierCorrection` (the preparer or the approver, inside the approval window) sends it; `lookupIdentifierCorrection` looks up an unresolved outcome and never resends. This is the same prepare → approve → send → lookup pattern as aggregate report delivery (slice 7g).
- **A destination must be prepared to receive a correction.** The destination is an active demonstration programme connection with correction support (`mis.corrections`) and the `update` operation permitted (slice 7e). A non-programme, HTTP, inactive, non-correcting or non-updating destination is refused before anything is prepared or sent. HTTP crosswalk correction needs a partner contract and stays refused, as aggregate delivery does.
- **Downstream repair list.** `identifierRepairs(person)` returns the open corrections for a person (destination, issuer, state; never the identifier value). It is the repair list a corrected link generates (FR-ID-08) and is intended to feed the action plan and exception queue.
- **Masking.** The prepare result and the client-facing view (`correctionView`) mask the identifier value (all but the last four characters); the entry reference stays visible so the earlier entry can be opened and audited. Audit lines mask the value too. The payload carrying the real value exists only while the correction is open and is dropped once it is closed (as slice 6ad does for reports).
- **Wiring (additive).** `crosswalkCorrectionSchema` is added to `lib/saha/platform.ts` and `applyCrosswalkCorrection`/`authorizeCrosswalkCorrection` are dispatched in `lib/saha/server.ts` (replay re-checks authority, as for the other commands). Corrections are stored in the operations document (`operations.crosswalkCorrections`) beside the aggregate reports, so no migration is added.

## Limits

- **Demonstration destinations only.** The send and lookup use a deterministic in-process simulator (a destination with behaviour `uncertain` loses its first response; a lookup then finds the receipt). No HTTP crosswalk-correction contract is implemented; a real partner contract is a separate piece of work, as for aggregate delivery.
- **The ledger correction and the destination correction are one step here.** A user who wants to correct locally without a destination still uses `identifierLink`/`identifierWithdraw`; the new command always names a destination and always prepares a `prepared` correction.
- **Per-organisation, stored in the operations document.** Corrections are organisation-wide records, not patient-partitioned (the command compares against a destination's integration and is not listed in `PATIENT_COMMANDS`). The operations document is the same one that holds aggregate reports and the indicator ledger, so its size is bounded by the existing organisation-document limits; the payload (with the raw value) is kept only while open.
- **No migration, no new table.** `operations.crosswalkCorrections` is added on the fly, exactly as `aggregateReports` and `indicatorReleases` are.
- **The repair list is not yet wired into the action plan or exception queue.** `identifierRepairs` is a pure read; surfacing it in those screens is a separate, additive change left to the integrator.
- **Authority is role-based and normal-access.** A care role with normal access (not emergency-only) prepares; a clinician or supervisor withdraws or records `issuer-checked`. Owner authority does not widen the patient's team scope.
