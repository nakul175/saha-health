# Development slice 2h — controlled import of programme enrolments and external identifiers

2 October 2026 (IST). Builds on slices 2f (patient import with a dry run), 4e and 4f (pack versions and adopted version), 6k (reconciled export with a manifest) and 6u (neutral wording for an ABHA number held by a record outside scope). Synthetic data only; formal acceptance unchanged. BR-DATA-11 stays partial.

## What changed

- **Who may import.** The slice 2f importers, through the same `importsInto` and `mayImport` helpers: an active owner or supervisor with a clinician or supervisor role in the team, or a clinician holding a supervision delegation for it. ASHAs (including an ASHA owner), clinicians without supervision, administrators and suspended members are refused. Every check runs on the server; a replayed apply checks the importer's authority again under the current membership.
- **Two kinds of file.** `enrolments` with the header `person, pack, version, episode_label, start_date` and `identifiers` with `person, issuer, identifier` (any order, each once; RFC 4180 quoting by the slice 2f parser; up to 100 rows and 16,000 UTF-8 bytes). The file travels only in request bodies.
- **Matching the person.** The `person` cell is a Saha record id, or an external identifier already recorded on one record, written `issuer:value` (the issuer is matched without regard to case). The record must be in a team the importer belongs to and may import into, and visible to them. An unknown id, an identifier no live record carries, and a record outside those teams all get the same reason ("No record in the teams you may import into matches this person.") and no record id, so the dry run cannot be used to learn whether a record exists elsewhere. A merged record in scope is refused with a pointer to the surviving record.
- **Enrolment rows.** The pack must be in the organisation's catalogue (compiled packs plus activated or retired installed versions). An empty version opens the episode on the organisation's adopted version (slice 4e/4f `adoptedVersion`); a named version must be a compiled or an activated version (`enrollableAt`), so a version that is staged, approved but not activated, retired or unknown is refused. The episode label is 3–200 characters; the start date is empty or a valid `YYYY-MM-DD` not in the future. A record that already has an open episode of the pack is refused, and so is a second row in the same file opening the same pack for the same record.
- **Identifier rows.** The issuer is a short lower-case code; the value is 1–64 letters, digits or `/ . _ -`, starting with a letter or digit (so a spreadsheet formula cannot be stored as an identifier). Known issuers have a format check: `rch` (12 digits) and `nikshay` (6–10 digits); these formats are illustrative and have not been checked against the issuing registries. `abha` and `abha_address` are refused: an ABHA is linked through the ABHA verification flow (slice 7a), never imported. A record that already carries the same identifier, or a different value from the same issuer, is refused (an import never replaces an identifier). The same issuer and value already on another live record anywhere in the organisation is refused: when the importer can see that record the reason says so and the row names its id and version; otherwise the reason is neutral ("This identifier cannot be recorded here. Ask an identity steward to review before importing it.") and names nothing, as slice 6u does for ABHA. Repeats inside the file are refused.
- **Dry run.** `POST /api/record-import` with `{kind, csv}` returns, per row, the row number, accepted or rejected, the reasons and, when the record is in scope, its id and version (and the id and version of a visible conflicting record); counts; and a plan hash. It never returns names, episode labels or identifier values, and stores nothing. The plan hash is bound to the kind, the environment, the importer, every row's classification, the parsed accepted rows and the id and version of every permitted record in the teams of the matched records, so a change to any of them forces a new dry run. A misconfigured environment refuses the dry run and apply.
- **Apply exactly the plan.** `recordImportApply` (`kind`, the same file, the plan hash, a reason of at least 10 characters) recomputes the dry run and refuses with a 409 unless the hash matches, or when nothing would be applied. Enrolment rows open an episode exactly as `enrolProgramme` does (pack version pinned, official registration not submitted, the pack's programme added to the person's programmes, open plans blocked because the record changed) and add `imported` lineage (batch, row, time, importer, plan hash) to the episode. Identifier rows append `{issuer, value, verified: false, source: 'import', recordedAt, recordedBy, imported}` to the person's new `identifiers` list. Like ABHA numbers, identifier values are masked (all but the last four characters) in workspace snapshots, patient detail and revision history; the stored record and its revisions keep the full value. The store writes one revision per changed record with the reason; one audit event records the kind, batch, plan hash and counts (rows, applied, records, rejected) and no names, labels or values. The command result carries the batch id, counts and the applied row numbers only, so a replay by key returns no record ids.
- **Rejection report.** `POST /api/import-rejections` with `{kind, csv}` (kind `people`, `enrolments` or `identifiers`, so it also covers the slice 2f people import) reruns the dry run for the requester and returns a CSV download of the rows that were not accepted: row number, result (Rejected or Possible duplicate) and each reason, never names, localities, labels, identifier values or record ids. It names its definition (`saha-import-rejections` 1.0.0), a new export identifier, the status "Dry-run rejection report; nothing was imported by this download", the requester's role, the time, the import and plan hash, and the rows in the file and accepted; carries a control total (rows not accepted against distinct rows listed); and ends with the slice 6k manifest (row count and SHA-256 of the lines above), so `verifyExportCsv` and `head -n -2 file.csv | sha256sum` check it. Cells are written by the shared CSV writer, which escapes formula-like text and flattens line breaks. The export identifier and checksum are returned in `X-Saha-Export-Id` and `X-Saha-Content-SHA256` and recorded in an `importRejectionsExport` audit event through `recordExportAudit` (slice 6p): on a retry after a concurrent commit, the requester's import authority, role and care scope are checked again, and if the event cannot be written nothing is delivered.
- **Screen.** Organisation & team gains "Import enrolments or identifiers for existing people" for eligible members: choose the kind, choose or paste a file, run the dry run, read the per-row results (names resolved in the browser from the people the member already holds), download the rejection report, give a reason and apply. The slice 2f people import panel gains the same "Download rejection report" button.

## Why visits are not imported

A visit is clinical content: measurements with their source and observation time (2c) and author (2e), notes and programme answers with their authors (2g), pinned pack-version captures, sign-off state, AI results and submission receipts. Importing one would need, at least: a mapping of each external field to a shared fact key with units and plausibility checks; a statement of who performed and who recorded each external observation (the server-identity author rules would otherwise attribute imported observations to the importer); a source marker that keeps imported visits out of reuse metering, indicators and programme submissions until reviewed; clinical review or sign-off of imported visits before they count as confirmed; and a rule for visits that conflict with visits already recorded for the same day. None of those are designed, so this slice does not import visits.

## Limits

- Enrolments and identifiers for people already in Saha only. Visits are not imported (see above); nor are contacts, household links, assignments or follow-ups. A person must be created first (slice 2f or registration).
- Identifiers are recorded, not verified: nothing contacts an issuer, the known-issuer formats are illustrative, and there is no command yet to correct or remove an imported identifier (a wrong one stays in the record's history and needs a later correction slice). Identifiers are not shown on the patient screen and are not sent to programme destinations or FHIR documents; matching by identifier covers identifiers recorded by this import only, not linked ABHA numbers.
- The neutral refusal for an identifier held outside the importer's scope still tells the importer that the value is in use in the organisation (as the slice 6u ABHA refusal does); it does not say on which record or team.
- Uniqueness is per organisation and per issuer and value; there is no cross-organisation or national check, and no duplicate review across external sources.
- An open episode of the same pack is refused rather than merged or updated; closing or migrating episodes stays with the existing commands. Imported episodes do not schedule follow-ups.
- No batch reversal and no data-quality report beyond counts, reasons and the rejection report. The rejection report is generated from a fresh dry run at download time; if the records changed since the reviewed dry run, its plan hash differs from the one on screen.
- Files are bounded at 100 rows and 16,000 UTF-8 bytes as in slice 2f.
