# Prepared device copy privacy and redacted failures

5 October 2026. Synthetic software evidence; clinical, hosted privacy and physical Android acceptance remain pending.

The shared browser-owned encrypted notebook now checks prepared copies against current server consent and access before connected unlock/load/sync and on reconnect. A withdrawn copy is removed with its sealed media in one revision-checked IndexedDB transaction. Only after that transaction completes does the client send a stable deletion acknowledgement. Confirmed server facts, receipts, revisions and audit evidence remain intact. Both `/app/offline/` and the original `/field/index.html` retain schema-1 encrypted storage.

## Server authority and durable evidence

`POST /api/device-work` uses the existing trusted identity provider and organisation boundary. Strict bodies permit fixed failure codes and bounded counts, or original lease/package references and operation key/body digests. They reject arbitrary patient text, raw errors, stacks, URLs, headers and device fingerprints. The streamed body cap is 16,000 bytes, a reconciliation batch contains at most 20 unique leases, and an individual lease has at most four pending media references. Reports require an active care membership, use stable operation IDs, and are capped at 200 daily per actor/organisation.

Migration `0020_device_work` adds append-only grant metadata and event ledgers. New preparation registers original worker, exact package hash, patient/visit pointers, membership/consent versions, identity digest, actual issuance role, signed visit version and issue/expiry times in the existing atomic command commit, together with the lease, command receipt and audit. The registry survives bounded legacy lease trimming. Legacy bootstrap accepts only an exact original server lease and trusted owner; its original role is explicitly unavailable (`null`) rather than inferred from today's membership. No packet or clinical facts are stored in this registry.

The original trusted worker can obtain only redacted deletion instructions, own receipt status and acknowledgement after care membership is removed. That proof does not grant patient reads, diagnostics or care commands. Other actors, organisations, hashes and receipt bindings share a uniform refusal. A receipt lookup binds original actor, key, body digest, patient and original lease (or media visit) and returns `accepted` or `unknown`; absence never means failure and never triggers a resend. Instructions and acknowledgements append with the chained audit under organisation revision guards. Current patient data/version guards prevent a stale permission read from publishing an instruction. Duplicate operation content returns its immutable prior result; changed content is refused. Server evidence has no automatic expiry pruning.

## Client behavior

The purge transaction replaces the encrypted notebook and deletes linked sealed media together. A failed transaction changes neither copy and sends no acknowledgement. A minimal encrypted tombstone retains the original lease/package, instruction, sync/media operation keys and body digests, outcome status and stable acknowledgement key; it retains no patient pointer, packet, facts or original command body. Lost acknowledgements retry only that metadata action. The reachable “Check deletion acknowledgements” control also refreshes unknown receipt status without resending a care command; an unknown status can become accepted, while accepted evidence is never downgraded.

Uncertain media references remain when a later upload is refused or its visit/copy is no longer usable. Manual notebook reset requires an unlocked notebook and refuses unresolved sync or deletion references. A safe completed reset clears both storage and unlocked memory. Unknown absent receipts remain unresolved; the app does not invent a failed outcome merely to permit deletion. Fixed-code online reports cover storage quota/write, known purge write failures and sync transport/refusal; reporting failure never erases drafts or changes care authorization. The route supports the fixed crypto-unavailable code, but initial inability to decrypt has no trusted notebook organisation and is not automatically attributed.

Unlock submission is disabled throughout async verification, including the locked early-render path. Wrong-account checks fail closed and preserve ciphertext. During reconnect, the notebook is hidden until privacy reconciliation finishes; the app additionally retains its existing current patient/identity gate. Account mismatch does not authorize purging another account's notebook. Offline clients cannot observe a withdrawal until a connected check succeeds.

Root/field service-worker cache namespaces are updated for the new public module. Only fixed public resources remain cacheable; patient HTML/API and device metadata API responses remain uncached. IndexedDB version, encryption associated data, passphrase derivation and prior confirmed outputs are unchanged. This is browser custody, with no native Keystore or verified flash erasure claim.
