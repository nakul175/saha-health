# Verification review holds and sending

This bounded B05 implementation connects clinician-disputed measurement, note and programme-answer reviews to the existing append-only Dispute / DisputeResolution workflow. The before witness is frozen in `7a162912` and `tests/evidence/verification-send-before/manifest.json`: three real synthetic confirmed visits were disputed through supported review commands, then prepared, approved and executed to a carrying demonstration destination. Existing explicit disputes already stopped that delivery.

A new disputed review now creates a Dispute in the same guarded command transaction, linking the review ID and SHA-256 of the exact target value and provenance. Facts, programme capture, confirmation, earlier reviews and approved stored bodies are not rewritten. Review, linked hold, audit and receipt must persist together. The server awaits the successful fact-review result before persistence. Rejected validation still throws synchronously; a successful disputed fact review may return a Promise. The sole production caller awaits it.

The send gate reads both stored disputes and retained latest-disputed legacy reviews. New holds apply at prepare, approve and execution checkpoints. Measurement and note holds remain destination-specific according to the existing mapping; the EHR carries facts and notes, not programme answers. The existing conservative HTTP MIS answer hold remains because answer-aware destination mapping is not implemented. That is an open B05 software clause, not a claim that every HTTP destination actually carries every answer. Other connection kinds remain unaffected. Saved uncertain delivery lookup/reconciliation stays available; resolving a hold does not authorize a duplicate accepted delivery.

A later verification click appends a review but does not resolve an existing hold. Review-origin resolutions require an independent current clinician, excluding the disputer, the trusted recorders retained when the hold was created and the current target recorders. Existing explicit-dispute semantics are preserved, including their previous corrected-outcome rules; this additional independence applies only to verification-origin holds. Commands retain current record revision, membership, patient scope and purpose governance. A saved receipt remains an authorized historical outcome read, not a new current decision. Role or patient-team withdrawal refuses that read without recreating mutation evidence.

## Retained legacy reviews

Earlier FactReview/EntryReview rows have no content hash. Their latest disputed state is treated as a conservative `legacy-unbound` hold with a deterministic review reference and an empty hash; no historical content fingerprint is invented. Before a newer review or explicit resolution, the hold is materialized without changing the old review. The independent clinician may explicitly attest current content as standing; the new resolution records a new current-content hash and evidence. It does not prove what was reviewed historically.

A supported amendment carries unresolved review-origin holds even when their target was removed. A legacy amendment records the exact target content at carry time, explicitly distinct from the missing original review binding. A corrected resolution requires a real difference from that new comparison basis. Unchanged content cannot be resolved as corrected. Original confirmed facts/reviews remain on the superseded source. Voiding retains history and makes the visit ineligible for sending; it does not silently append a resolution or transfer a hold to unrelated new visits. The existing per-visit dispute/resolution bounds remain; over-limit legacy states fail closed and are not automatically purged.

The three review/dispute panels show held sending, exact versus legacy-unbound provenance and explicit independent resolution. No new command, endpoint or migration is introduced. The only server dispatch change is awaiting `applyFactReview`; no B12 confirmation/scheduling hook is changed.

## Verification and integration

Final focused author checks are recorded with source/driver/artifact hashes in `tests/evidence/verification-send/manifest.json`. They include actual Worker/D1 modern review holds and lookup/replay, retained synthetic pre-upgrade state, supported correction, role and cohort withdrawal, rejected public hash injection, atomic audit rollback and same-key recovery; a normal 390 × 844 Chromium resolution journey; the original sign-off HTTP assertions with a genuinely invited additional clinician; and injected MIS/EHR checkpoint transports observing zero requests after a new review hold.

The original pinned drivers are unchanged. Separately named `verification-current-*` adapters add the new leaf to explicit copied-module inventories and redirect their result JSON to owned evidence. `fixture-map.json` pins 113 original driver hashes and maps their current adapters; only the stated focused adapters are qualified here. Directory-copy fixtures already copy the new leaf. Root must map stable catalogue IDs to the adapters and independently run the combined gates. The current sign-off smoke adapter adds supported independent resolution before the original later prepare/send assertions; all original assertions remain.

Initial fixture expectation/inventory errors and direct-Miniflare browser static-request failures are retained. The phone qualification uses the established Wrangler browser harness, not a product workaround. No whole-unit or hosted qualification is claimed.

Full B05 remains open: answer-aware mappings, the remaining blocked-send notice/exception clauses and other residual verification/sign-off workflow requirements need their own buildable work. Clinical, partner, physical-device, hosted and formal acceptance are unchanged. All tests use synthetic records; no real provider is enabled and no external message is sent.
