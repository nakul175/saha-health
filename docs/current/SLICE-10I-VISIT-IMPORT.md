# Development slice 10i — controlled import of historical visits with clinical content

2 October 2026 (IST). Builds on slices 2f and 2h (dry run, plan hash, apply exactly the plan, rejection report), 2i (stated units and unusual-value rules), 2c (fact provenance), 2e and 2g (authors, sign-off) and 6k (reconciled export). Synthetic data only; formal acceptance unchanged. BR-DATA-11 stays partial. The slice is built on a lane branch and has not been independently reviewed.

## What changed

- **A third import kind, `visits`.** `POST /api/record-import` with `{kind: 'visits', csv}`, `recordImportApply` with `kind: 'visits'` and `POST /api/import-rejections` with `kind: 'visits'` take a CSV with one row per historical visit. No new route, no new command and no new table: the file travels in request bodies (100 rows, 16,000 UTF-8 bytes, RFC 4180 quoting) and an imported visit is an ordinary stored visit with an `imported` marker.
- **Who may import.** An active clinician, or an organisation owner whose role is supervisor, who belongs to at least one team. ASHAs, administrators, providers and supervisors who are not owners are refused (403) on the dry run, the rejection report, the apply and a replay. This is narrower than the enrolment and identifier importers, because the file carries clinical content. Each row is resolved inside the importer's normal care scope only: the importer's own teams, with no emergency access and no widening by owner authority.
- **File format.** The header must name each of these 21 columns once, in any order: `person`, `visit_date`, `source_system`, `systolic`, `diastolic`, `bp_unit`, `bp_source`, `weight`, `weight_unit`, `weight_source`, `temperature`, `temperature_unit`, `temperature_source`, `gestation`, `gestation_unit`, `gestation_source`, `cough_duration`, `cough_unit`, `cough_source`, `override_reason`, `notes`. A visit date is `YYYY-MM-DD` or `YYYY-MM-DDTHH:MM`, not before 2000-01-01 and not in the future (a date alone is stored as 00:00). The source system is 2–60 characters. Notes are at most 3,000 characters without control characters.
- **Person.** A Saha record id or an exact `issuer:value` identifier already recorded on one record (as slice 2h). An unknown record and a record outside the importer's teams get the same neutral reason, so the dry run is not an existence oracle. A merged record, a record under a processing restriction and a record whose identity review is provisional are refused with their own reasons.
- **Measurements, units and sources.** Every recorded value states its unit and its source (`measured` or `reported`); a unit is never assumed. Supported: blood pressure in mmHg (both readings or neither); weight in kg or lb; temperature in degC or degF (also `C`, `F`); gestational age in weeks; cough duration in days or weeks. A unit other than the stored one is an alternative unit of slice 2i: the server converts it and keeps the value as entered. Without a value, the source column may only say why it is missing. A row needs at least one measurement or notes.
- **Unusual values.** The slice 2i rules apply to the converted values, using the placeholder ranges `saha-value-ranges-0.1.0` (an engineering placeholder, not clinically approved). A value outside the expected range needs an `override_reason` of at least 10 characters (kept with the value as a reason-tier override, authored by the importer); a value beyond the confirmation range is refused, because an imported visit has no draft stage in which a clinician could confirm it; a reason on a row with nothing unusual is refused. The shared `checkFacts` is the final authority on every row.
- **Duplicates.** A row is refused as a duplicate of an imported visit that is still current (not marked wrong-patient) for the same record, source system (compared without regard to case and spacing) and visit date, or of an earlier row of the same file. A repeated file, or a second file from the same system, therefore imports nothing twice. The dry run names the existing visit's id for the first kind. Visits recorded in Saha are not compared (see Limits).
- **Dry run.** The response lists, per row, the row number, accepted or rejected, the reasons and, when the record is in scope, its id and version, with counts, the SHA-256 of the file as sent, and a plan hash. It never returns a name, a note, a source system or a clinical value, and no reason repeats a cell. It stores nothing. The plan hash is bound to the file digest, every row's classification with the matched record's id and version, the parsed accepted rows (which stay on the server), the importer, the environment and the imported visits already held for the matched records, so a changed file, a changed record or a second import for the same people forces a new dry run.
- **Apply exactly the plan.** `recordImportApply` recomputes the dry run and refuses with 409 unless the hash matches or when nothing would be applied. Each accepted row becomes a confirmed visit (`state: confirmed`, version 1, created and confirmed at the import time) with `imported: {batchId, row, at, by, byName, role, planHash, fileDigest, sourceSystem}`: file digest, row, importer and time are the source lineage. No clinician review, patient check, verification or sign-off is recorded, so none is implied; the server credits each value to the importer as the person who recorded it in Saha, and the observation's own source is the stated measured or reported source and the source system. The store writes one revision per visit with the reason and one audit event with the batch, plan hash, file digest and counts, naming no cell. The command result is counts and row numbers only, so a replay by key returns no ids; replay authority is rechecked under the current membership.
- **What an import never does.** It creates no programme enrolment, submission, referral, plan or follow-up and changes no person (no version, programme, enrolment, assignment or status). Visits are not counted as visits recorded in Saha.
- **Imported visits are read-only history** (`lib/saha/imported-visits.ts`, one check in the command dispatch chain). Every command that names an imported visit and would use it as something current is refused with 409: plans and their approval and execution, assistant runs and reviews, referrals and referral requests, amendment, protocol check and review, clinical concern, programme answers, fact and entry verification, sign-off, unusual-value confirmation, agent tasks, outreach, EHR publication, ABDM care-context linking and linking a referral source. Marking the visit wrong-patient, a safety report and the commands that cannot apply to a confirmed visit stay possible. A contract test reads every command schema and fails if a command naming a visit is neither blocked nor explicitly allowed, so a new visit command must be classified before it ships. The FHIR download refuses an imported visit, and the organisation data export (slice 6m) lists imported visits with their lineage in the visits table but writes no FHIR document for them. Imported visits are left out of indicators, care reports, pilot measures, shadow comparisons, the freshness statement for visit-based indicators (the import is described under imports instead) and the My work statistics. Imported facts are therefore not reused as current observations without a fresh measurement in a new visit.
- **Rejection report.** `POST /api/import-rejections` with `kind: 'visits'` returns the slice 2h CSV (row numbers and reasons only, formula-escaped, control total, SHA-256 manifest) with an `importRejectionsExport` access-audit event, for the same importers only.
- **Screens.** Organisation & team: the import panel offers the third kind, shows the file's SHA-256 beside the plan, and says that clinical values stay on the server. Patient page: an imported visit opens in a read-only panel (IMPORTED tag; "Imported from <system>. Not recorded or signed off in Saha"; lineage; measurements with unit, entered unit, source and time; reasons for unusual values; notes) and never as an editable visit; the patient's current visit is their latest visit recorded in Saha, so an import does not become the visit that is edited, sent or summarised; the previous-visits list tags imported visits and shows the visit date; the correction control is hidden for them; the ABDM and referral panels list only visits recorded in Saha; the record history labels the lineage fields.

## How the slice 2h list of missing design was answered

Slice 2h listed what importing visits would need. The slice answers it as follows. A mapping of external fields to shared fact keys with units and plausibility checks: the 21 columns, stated units and the slice 2i rules. Who performed and who recorded an observation: the source system and the stated source (measured or reported) are on every value, the importer is the recorder, and no performer is claimed. A source marker that keeps imported visits out of reuse, indicators and submissions: `imported`, with the exclusions above. Review or sign-off before counting as confirmed: not built; instead an imported visit is never counted as a Saha visit and no sign-off is implied. A rule for conflicts with visits already recorded for the same day: not built; only repeats of imports are detected.

## Decisions

- Owner or clinician only, in normal care scope, not the slice 2f importers: supervisors who are not owners and delegates do not import clinical content. This follows the slice brief and keeps the audience small.
- Visits beyond the confirmation range are refused rather than imported with a flag: there is no step in which a clinician confirms them. The importer corrects the file or records the visit directly.
- Imported visits are confirmed from the day they are created, so they cannot be edited; a wrong import is marked wrong-patient (a correction that appends evidence) and a corrected row can then be imported again.
- The visit date is the observation time of every measurement in the visit; the file has no per-measurement time.
- The 2h plan hash for enrolments and identifiers is unchanged; visits have their own hash input because an import does not change the person, so staleness is detected through the file digest, the matched records' versions and the imported visits already held.

## Limits

- No batch reversal. A wrong import is corrected one visit at a time by marking the visit wrong-patient and importing a corrected row; there is no command that voids a whole batch. Slice 2d's fixture-marking reversal does not cover imports.
- Imported visits carry measurements and notes only: no programme answers, attachments or media, structured notes, assistant output, plans or follow-ups, and no per-measurement time or performer. Contacts are not imported.
- No clinician review or sign-off step exists for imported visits, and they are not counted as Saha visits. A review workflow that could let a clinician adopt an imported fact would be a separate slice with its own design.
- Duplicates are detected between imports only. A visit already recorded in Saha for the same day is not compared and no conflict is shown; the same clinical event can appear as an imported visit and a Saha visit.
- The value ranges are the slice 2i placeholder, not clinically approved. Units cover the measurements the visit form holds; other analytes and units are refused.
- The importer's attestation that the file is what the source system held is not checked: the file digest identifies the file as received, nothing verifies it against the source system. The source system is free text.
- A person whose care scope the importer cannot reach cannot be imported for, even by an owner. Emergency-access or cross-team imports are not designed.
- Files are bounded at 100 rows and 16,000 UTF-8 bytes as in slice 2f, so a large history needs many batches. Imported visits appear in the patient's record and history but not in the care report, the indicator tables or the pilot measures.
- Records with an imported visit have their retention clock and "latest data" time computed from the import time (the visit's created and confirmed times are the import time), not from the visit date; the slice does not change retention.
- The previous-visits list and the record history are the only places an imported visit appears beside Saha visits; there is no merged timeline.
