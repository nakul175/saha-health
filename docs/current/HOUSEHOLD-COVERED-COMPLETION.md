# Household covered completion and declared programme work

This B13 implementation addresses the software gaps grounded in [the residual audit](HOUSEHOLD-COMPLETION-RESIDUAL-AUDIT.md). It adds explicit per-item visit lineage, governed installed pack completion and referral declarations, and individual neutral outreach linked to an original household slot. It retains the delivered atomic rescheduling contract. BR-PROG-05 and BR-CARE-03–07 clinical, official programme, provider and operating acceptance remain pending; this is synthetic software evidence.

## Installed contracts and compatible work

Optional `completionRules` in the strict versioned installed manifest declare an id, label, required question ids and an optional validated question condition. Optional `referralNeeds` declare a known need, a compatibility key (or null to require separate work), urgency and an optional condition. Independent pack review and original owner activation remain required. Existing compiled packs and older installed snapshots retain their legacy worker-reviewed behavior; this change invents no clinical rules for them.

The normal programme follow-up form exposes the selected episode's pinned installed rule labels. `scheduleFollowUp.completionRuleId` pins the full rule, installation id, manifest hash and pack version to that task. Completion requires the exact captured episode/version/hash/rule, currently active required questions, nonempty answers or facts, no explicit absence, and satisfied conditions. Shared question values keep the existing programme capture contract. Unsupported declarations and conditions refuse. The server rechecks the pinned rule at scheduling and the captured contract at completion. No automatic task or referral completion occurs merely because a slot was planned or a reminder was delivered.

The programme referral form requires a declared need for packs with explicit declarations. Matching declared compatibility keys and needs can create one referral with every programme request and immutable source hash; null or different compatibility keys create separate referrals. Highest declared urgency is retained. Legacy grouping remains unchanged for packs without declarations. Existing completed referrals keep their own care outcome evidence; a household visit cannot close an open referral.

## Household commands, authority and history

`householdVisitRecord` supplies the current household and person versions, original slot id, own confirmed visit id/version/record revision, explicitly selected original covered items and an evidence reason. It requires a current ASHA or clinician with normal access to that original current member, both household-sharing and care-coordination purpose, resolved identity and an original confirmed, unvoided, unsuperseded visit on the slot date, created after the slot. Imported visits cannot authorize completion. There is no owner bypass.

Each selected task is checked before any edit. Eligible declared follow-ups close together; unmet requirements, unresolved dependencies, another member's work and open referrals remain unchanged. Each selected item receives its own append-only source record. Independently resolved follow-ups must have resolution after the confirmed own slot visit, and declared contracts must still match its evidence. Existing terminal fields are preserved. Every mutation uses the existing organisation CAS, durable receipt and chained audit transaction; the actual audit-failure probe rolls back task changes, slot lineage and receipt together.

A void or amendment does not rewrite original task closure. Its visit-backed completion becomes derived unresolved in household/action-plan/continuity views, with dependency blockers visible again. Closed-history assignment is not offered. Linking a new original confirmed visit appends replacement evidence; it does not re-close or rewrite original `closedAt`, resolution or evidence. Saved receipt replay rechecks current member, role, purpose and evidence access, and does not append another completion.

`householdVisitOutreach` requires the original slot and all current original covered person versions, current normal care scope and both purposes. It creates one individually scoped item per covered member, copies only that member's covered source refs, and links the original slot date/window. Scheduling, message approval and simulation refuse changed/cancelled slots or covered work that is no longer open. Shared/private contact constraints, neutral approved templates, independent message review, bounded delivery attempts and failed-delivery owned recovery remain in force. This action prepares a draft; it sends no message and acknowledges no care. Existing uncertainty behavior remains receipt lookup only.

Both new commands are explicitly parsed and purpose classified, remain on the organisation atomic path, and are not certified patient-partition commands. No migration, provider enablement, official clinical compatibility, push or canonical integration is included.
