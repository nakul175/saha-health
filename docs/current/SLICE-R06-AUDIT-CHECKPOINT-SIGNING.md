# Development slice r06 — audit checkpoint signing + scheduled chain verification

3 October 2026 (IST). Builds on the parallel base (R11 and slices 0a–3f, 6h, 6j, 6t, 6w, 10a). Synthetic data only; formal acceptance unchanged. Not independently reviewed.

Slice 6j built the per-organisation SHA-256 audit chain and slice 6t added the unsigned chain-head checkpoint; its limits noted "no external anchoring, no signing key and no scheduled verification". This slice closes two of those gaps.

## What changed

- **Signed checkpoint** (`lib/saha/audit-chain.ts`, `lib/saha/audit-chain-server.ts`). `GET /api/audit/chain?format=signed-checkpoint` (owners and administrators only, as before) issues the same chain-head checkpoint as slice 6t but additionally signs the compact head summary — `organisationId`, `seq`, `hash`, `at`, `issuedAt` — with HMAC-SHA256 under the server secret `SAHA_AUDIT_SIGNING_KEY`. The signature is over `JSON.stringify(['saha-audit-checkpoint-signed-v1', organisationId, seq, hash, at, issuedAt])` and never over itself or the key id (`saha-audit-signing-key-v1`), so a copy kept outside Saha (a ticket, a signed email, a public log) can be checked against the deployment key without trusting the transport. Issuing it is recorded in the chain under a distinct `auditChainSignedCheckpoint` event whose detail carries the key id and the signature. Without a key the request fails closed (503) with a clear message; the unsigned `?format=checkpoint` still works. Existing verification, export and unsigned-checkpoint behaviour is unchanged.
- **Scheduled verification** (`lib/saha/audit-chain.ts`, `lib/saha/scheduled-job.ts`). The Cron job (slice 10a) gains a fourth step: for each organisation it recomputes the chain from a stored anchor — the head of the last recorded verification, kept in the organisation's operations record (`operations.auditChain`) — rather than from the genesis every time. A tampered suffix is therefore found even when nobody uses Saha. The result (status, events checked, head, first break, and the anchor for the next run) is recorded through the normal commit as an `auditChainScheduledVerification` audit event, with no event content. Recording follows the slice 10a heartbeat discipline: on the first run, when a break first appears, when the status changes, and otherwise at most once an hour, so a steady intact state does not move the organisation revision or lengthen the chain every five minutes. Verification itself is a read and is skipped for recording only while an organisation is in maintenance (alerts keep being evaluated, as before).
- **No migration, no command.** The anchor and the record live in the existing operations document (like `operations.scheduledJob`); nothing new is added to the command schema or the database.

## Evidence

- 15 contract assertions (`tests/audit-checkpoint-contract.mjs`, the real modules over the real migrations in an in-memory SQLite database, no network): the signature is a 64-hex HMAC over the compact summary and verifies with the correct key, fails with a wrong key and for any tampered field, and the signed content is deterministic and never covers the signature or key id; the planner records on first / break / status-change / heartbeat and not for a steady state within the heartbeat; and the scheduled job verifies an intact chain and records the anchor, does not record again within the hour, detects a tampered suffix and records it as broken with the first break named, carries no event content, and calls no external service.
- The existing `tests/audit-chain-contract.mjs` (48) and `tests/scheduled-job-contract.mjs` (32) still pass unchanged on this source; `node_modules/typescript/bin/tsc --noEmit` reports no errors.

## Limits

- **Shared-secret signing.** The signature is HMAC-SHA256, so whoever holds the deployment secret can also forge a checkpoint. It proves the checkpoint came from someone with the key, not (like an asymmetric signature) from a specific holder; there is no key rotation or revocation and the key id is fixed until one exists.
- **The key is not provisioned by default.** The signed-checkpoint format is refused until `SAHA_AUDIT_SIGNING_KEY` is set for a deployment; the unsigned checkpoint and the scheduled verification do not need it.
- **Scheduled verification is not run on the hosted Worker.** As with slice 10a, the trigger has not been confirmed firing on Cloudflare, and the Free plan's CPU/query limits may cut a run short; a cut-off run is harmless because each commit is atomic and the next run finds the same work.
- **Anchor lags the chain head by one event.** The anchor is the head seen before the verification record is written, so the next run re-reads the verification record itself; a whole-chain rewrite from the anchor is still detected because the anchor event must keep its hash.
- **The record is not surfaced.** The verification result is stored in `operations.auditChain` and the audit chain, but no screen shows it yet (as with `operations.scheduledJob`).
- BR-SEC-08 stays partial: the audit chain is now externally anchorable and signed at the head, but material reads are still not audited and the audit fields do not yet record authority or object version consistently.
