# SAHA — Documentation standards for every hierarchy level

Version 1 · 10 October 2026 · requested by the sponsor.
This is the authoring format for the existing SAHA hierarchy. It adds templates and links; it does not approve product decisions, change source requirements, revise frozen specifications or release the current coding hold.

## The eight elements and where they live

| Element | Question it answers | Linear representation |
| -- | -- | -- |
| Product vision | Who are we helping, with what long-term outcome? | Vision section in the product vision and strategy document |
| Product strategy | What choices will achieve that outcome, and why? | Strategy sections in the same document |
| Roadmap | In what order will we pursue outcomes? | Roadmap document, linked releases, epics and product views |
| Release goal | What usable outcome must a particular release deliver? | Release-goal section and its corresponding project milestone |
| Epic | What coherent capability or work package groups the scope? | Existing epic issue with canonical child product items |
| User story | What can a particular user achieve, and why does it matter? | Canonical functional story issue; supporting work uses the variant below |
| Acceptance criteria | What observable conditions prove that item meets its requirements? | Identified criteria and scenario sections inside the owning product item |
| Technical task | What bounded implementation or verification work produces that result? | Child task or existing nested subtask, linked to the canonical owning item and criterion IDs |

Logical chain: **Vision → Strategy → Roadmap → Release goal → Epic → User story → Acceptance criteria → Technical task.**
In Linear, acceptance criteria are sections within a story, and tasks link to that story, directly or through an existing parent task. Acceptance criteria do not require another parent-issue layer. Shared epics can span releases; allocate the actual stories to releases without duplicating the epic.

## Rules shared by every template

Use these fields where they apply, keeping the document proportionate to the decision:

* **Identity:** stable ID or document link, title, element type and version.
* **Purpose:** intended outcome and the people or operators it serves.
* **Traceability:** parent, authoritative source IDs, relevant children and decisions. Link the canonical record rather than copying a second backlog item.
* **Boundary:** included scope, excluded scope and constraints.
* **Responsibility:** actual accountable owner or assignee, and applicable approval authority. If unknown, write “Pending: owner/authority to be agreed”; do not invent a person or an approval.
* **State:** planning/readiness/delivery state with its reason. Record dates and targets only when agreed; otherwise state what is pending.
* **Evidence:** claims supported by links, observations or test outputs; assumptions marked explicitly.
* **Change history:** what changed, why, when, and any decision/source/frozen-version impact.

Keep three separate fields whenever criteria or delivery claims are involved:
**source provenance** (original source or proposed supplement), **approval/specification state** (draft, approved or frozen revision), and **execution result** (not run, passed, failed, blocked or skipped with reason).
Passing a test does not approve a proposed requirement. An original requirement is not automatically satisfied by being documented.

**Supporting-item variant:** for reliability, security, performance, integration enablers or investigations, state the operator/consumer, bounded outcome and value without forcing an ASHA actor. **Quality check:** one bounded, testable user outcome, rooted in the real system. Draft planning text does not authorize new databases, clinical policies, services or provider activation.

## 7. Acceptance-criterion template

Keep each criterion inside its owning story/supporting item. Use stable IDs so tasks and tests can reference it.

* **Criterion ID and owning item:**
* **Source reference/provenance:** original source clause or proposed supplementary criterion:
* **Approval/specification state:** draft/approved/frozen revision, and authority/decision evidence:
* **Scenario kind:** positive, refusal, error, authorization, recovery or applicable NFR:
* **Given:** actor, identity/assignment, data state and preconditions:
* **When:** concrete action or event:
* **Then:** observable result, including the record/state the user sees:
* **Prohibited effects:** writes, disclosures or other effects that must not happen:
* **Measurement conditions:** source threshold, timing/profile/device/environment where applicable:
* **Synthetic fixture and verification method/test ID:**
* **Expected evidence:**
* **Actual execution:** not run/passed/failed/blocked/skipped with reason:
* **Observed evidence:** output link, final commit, environment and time:
* **Unresolved gap or blocker and resume condition:**

An equivalent observable format is acceptable if it is clearer than Given/When/Then. Retain original source clauses/test cases unchanged; add a linked supplementary scenario instead of silently rewriting an original clause or frozen specification. Readability refinements must preserve meaning.

**Quality check:** a reviewer can reproduce the scenario and distinguish its expected result from actual evidence. Include adverse paths relevant to the boundary; do not mark an unexecuted criterion passed.

## Applying this standard to SAHA

* Existing counts stay **11 epics, 140 planned functional stories, 20 supporting product items and 200 tasks**. D01–D08 are included in the 200 tasks.
* There are eight documentation elements, not eight new issue categories or another backlog.
* Original requirements/cases and frozen D02/D03 specifications retain their authority and version history.
* The eight future CWO items SAHA-153–160 still need approved missing source narrative/criteria. Their proposed scenarios remain draft; this template does not resolve that gap.
* D03 remains held for the existing baseline/readiness decision. Templates do not advance a delivery state.
* Use this standard for future refinement and qualification. Record actual approvals and execution evidence in the canonical item; no bulk rewrite or duplicated story set is required.
