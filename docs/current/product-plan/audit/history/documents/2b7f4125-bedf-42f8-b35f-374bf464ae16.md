# SAHA — Product quality checker and improvement loop

Version 1 · 10 October 2026 · reusable quality contract requested by the sponsor.

**Implementation verified:** catalogue, executable workflow and independent review are complete. Package tests: 29/29; independent adversarial cases: 19/19; complete-catalogue synthetic mechanics fixture: 1,797/1,797 instantiated checks. No actual SAHA backlog item is certified by these fixture results.

This checker applies to all eight documentation elements and their individual fields/details. It evaluates documentation quality against explicit, versioned criteria. Planning readiness, requirement approval and delivered product behaviour remain separately evidenced.

## What the checker contains

1. A field catalogue: every field in the [eight-level documentation standard](<https://linear.app/aplyd-sandbox/document/saha-documentation-standards-and-templates-for-every-hierarchy-level-c5336c6c1dbc>), plus its explicit embedded details.
2. Field checks: concrete pass criteria, evidence requirements, failure examples, repair instructions and targeted questions.
3. Element checks: whether each vision, strategy, roadmap, release goal, epic, story, criterion or task performs its intended job.
4. Hierarchy checks: alignment, requirement ownership, actual prerequisites, coverage and consistent terminology across records.
5. A repeatable check → repair → question → recheck loop with persistent findings, answers and revision history.
6. A runnable local checker, reports and synthetic test examples. Semantic quality requires an evidence-backed review; a nonempty field or a local reviewer name is not authenticated external approval.

## Quality factors and clear pass conditions

Apply relevant factors to each field; required applicability is declared and reviewed. An irrelevant dimension may be marked not applicable only with a specific scope reason and supporting review. Missing information is not evidence of non-applicability.

| Factor | Pass condition | Example that fails |
| -- | -- | -- |
| Completeness | Every required component is present; unknown decisions and evidence are visible and owned. | A metric has a target but no population, baseline or measurement source. |
| Clarity | The intended reader can identify the action, subject and result without resolving undefined terms or ambiguous alternatives. | “Handle it appropriately” without defining “it” or the required handling. |
| Specificity | Actors, objects, boundaries, relevant states and referents identify the intended behaviour or decision. | “Users can see records” without role or assignment scope. |
| Traceability | Statements link to their authoritative requirement, decision or research evidence, and to the canonical owning record. | A task adds a feature that no story or approved requirement owns. |
| Consistency | Values, terms, scope and states agree within the item and with applicable sources and parent/child records. | A story promises read-only access while a task creates a visit. |
| Scope and atomicity | The field/item has a coherent purpose and bounded completion; separate unrelated outcomes and retain required hand-offs. | One story combines unrelated registration, clinical decision and notification outcomes. |
| Nonredundancy | Each scope item has a canonical owner; repeated text is referenced or has an explained purpose; counts do not double-count shared work. | The same requirement appears as two independent accepted stories. |
| Testability | A reviewer can state what observation would prove or disprove the claim at the relevant level. | A criterion says “works well” without an observable result. |
| User value | The work contributes to an identified user/operator outcome and the causal link is explained. | A feature list with no user problem or benefit. |
| Feasibility | The proposal respects existing constraints; dependencies, access, resources and uncertainty have supporting evidence. | A release assumes an unapproved provider or unavailable integration. |
| Measurability | Quantitative claims define unit, population, baseline/method, period and any authorized threshold. Qualitative outcomes have an appropriate observation method. | “Improve by 20%” without a baseline or denominator. |
| Security | Identity, permissions, assignment/scope and adverse paths are explicit where affected; prohibited harmful effects can be checked. | An authorization error hides a record in the UI but the API discloses it. |
| Privacy | Collection, disclosure and retention are bounded to the existing approved purpose and access policy; fixtures and evidence avoid real patient data. | Test evidence contains an unnecessary real patient record. |
| Operability | Ownership, relevant failures, recovery and operational conditions are understood and observable. | A save failure has no retry or recovery behaviour. |
| Versioning | IDs and revisions are stable; changes, dependencies and evidence identify the assessed version. | A review of an old specification is presented as approval of a new revision. |
| Authorization | Claimed decisions or permissions identify their actual authority and evidence; drafts remain drafts. | The checker labels a proposed clinical rule approved. |
| Evidence integrity | Evidence is inspectable, scoped to the claim and revision, and its observed result is separated from the expectation. | A URL or self-written “passed” statement is treated as proof of a live test. |
| Prioritization | Order and trade-offs follow declared outcomes, dependencies and constraints. | An optional capability blocks a prerequisite routine journey without a reason. |
| Learning | Assumptions have a question, an evidence-gathering method and a decision/review trigger. | An unsupported belief is written as an established user need. |
| Accessibility | Applicable interaction, language, assistive-technology and device conditions have observable requirements and evidence. | “Mobile friendly” without the applicable journey or evaluation conditions. |

These are our operational pass rules. Their design uses the requirements-quality principles in [NASA’s requirements checklist](<https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/>) and the evidence-backed user-needs approach in [GOV.UK’s Service Manual](<https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs>). We apply them at the appropriate product level; this document is not a certification against either framework.

## Levels of review

* **Field:** all listed details are present, interpretable, source-linked and appropriate for that field.
* **Element:** the fields form a coherent outcome, scope and decision rather than a collection of individually polished fragments.
* **Hierarchy:** parents and children align; original scope remains covered; real dependencies, acceptance ownership and release allocation remain consistent.
* **Evidence:** supplied findings and reviews refer to the current content, sources, scope and evidence. Semantic interpretation and factual authority require independent review.
* **Change:** a content, source, criterion, dependency or evidence change invalidates affected prior reviews. Recheck downstream and upstream relationships as appropriate.

## Findings and result states

Every finding records: item/version, field/detail, check ID, factor, severity, failed expectation, actual observation, source/evidence, proposed repair or question, owner and resume condition.

A check is **passed**, **failed**, **unverified/not reviewed**, **stale**, **needs input**, **blocked**, or **not applicable with reviewed reason**. Unknowns, missing reviews and skipped checks are never counted as passes. Deliberately unagreed optional dates/targets are not fabricated or demanded when they do not block the declared assessment stage; their applicability and planning treatment are reviewed. A research plan may document a known uncertainty without pretending that the uncertainty has been resolved.

Priority guides the order of repair:

* Critical: integrity, source/authority, privacy/security, protected-baseline or false delivery claims.
* Major: missing required information, contradictions, traceability, untestable outcomes or infeasible scope.
* Improvement: remaining clarity, repetition or editorial defects.

Priority does not weaken the exit gate. Even an editorial failure remains unresolved until repaired or correctly found inapplicable.

## What “top-notch” means

For the explicitly assessed item/hierarchy scope and catalogue version:

* Every required field and embedded detail is covered.
* Every applicable field, element and hierarchy check passes.
* Every non-applicable decision has a defensible, reviewed scope reason.
* There are no unresolved failures, unknown applicable conditions, stale reviews or unanswered questions needed for a pass.
* Evidence and independent semantic review match the current assessed revision and scope.
* Original/frozen source boundaries and change authority remain intact.

An aggregate completion percentage is a progress display, never an override for a failed check. Report the check IDs and denominator; keep field coverage, source-case acceptance, task completion and execution results separate.

“Top-notch documentation” is relative to this declared catalogue and evidence. It does not establish full truth from prose alone, approve an external authority’s decision, authorize coding or prove deployment.

## The improvement and question loop

 1. **Load and scope.** Identify the item(s), hierarchy relationships, current source/specification revision, evidence and applicable checks.
 2. **Check coverage and structure.** Reject missing/duplicate IDs, orphan links, cycles, unmapped fields and unresolved applicability.
 3. **Review meaning and evidence.** Evaluate each declared criterion, overall coherence and parent/child alignment. Record concrete findings.
 4. **Repair what the evidence supports.** Improve wording, organisation, references or duplicated presentation without inventing facts or changing protected requirements. Keep a reviewable revision and history.
 5. **Ask when facts or decisions are missing.** Turn each unresolved decision into a targeted question linked to the item, field and check. Combine questions that share one underlying decision.
 6. **Pause for needed answers.** Show the outstanding questions and save state. Do not infer an answer from elapsed time or declare a quality exit. Independent repairs may continue.
 7. **Interpret and verify answers.** Distinguish preference, factual evidence and formal authority. Ask follow-ups if the answer is ambiguous, conflicting or insufficient.
 8. **Apply a justified revision.** Record the answer/source, what changed and why; protected/frozen changes use their existing change process.
 9. **Invalidate affected reviews and recheck.** Re-run the changed field, its element and impacted parents/children; unchanged local text does not preserve a hierarchy review after a parent/source change.
10. **Repeat until the exit conditions pass.** There is no fixed number of permitted clarification rounds. If new information is needed, suspend and resume the same loop rather than marking completion.
11. **Independent final review.** Check the final content and evidence, including retained boundaries and applicability.
12. **Record the quality exit.** Save version, catalogue/check coverage, actual results, reviewer evidence, remaining non-quality delivery gates and the conditions that would reopen review.

If a round changes nothing and the same finding remains, do not keep rewriting or asking the identical question. Keep the finding open, identify its authority/research need and resume when relevant information changes. A pause or a blocker is not a successful quality exit.

## Question packet

Each question contains:

* The exact item/version, field/detail and failing check.
* What is unknown or contradictory, with source references.
* Why the answer changes the document or quality result.
* One clear question; choices only when they are real alternatives.
* Who can answer or authorize it, if known.
* What evidence is required and what will be updated.
* The prior answer, if any, and why further clarification is needed.

The runner produces persistent question packets; an assistant can surface them to the user in small batches and resume after the replies. The runner does not silently contact stakeholders or use credentials/providers. Repeated runs do not repeatedly ask an unchanged unanswered question. Deduplicate by the underlying decision and material context, not a cosmetic wording or timestamp change. An insufficient answer creates a linked clarification with a specific reason; it never clears the check by itself.

## Preservation and SAHA operating boundaries

Existing original requirements, test cases, frozen D02/D03 revisions, legacy archives and approval gates retain their authority. Candidate improvements remain reviewable revisions; source text is not bulk replaced.

The eight future CWO items still need their missing approved source narrative/criteria. D03 remains held for its existing readiness decision. Creating or passing this checker does not remove either condition. No original coding automation is restarted.

## Checker records and reporting

The reusable package includes:

* Catalogue and coverage proof.
* A blank structured assessment for each level.
* Per-field/check findings and question queue.
* Current content/source/evidence fingerprints.
* Review records and persistent revision/answer history.
* Synthetic passing, failing and clarification-loop examples.
* Meaningful tests for stale evidence, false passes and protected changes.

Use separate report fields for documentation quality, unresolved questions, execution readiness and delivery evidence. The current project’s actual accepted/delivered counts remain in its canonical records; sample fixtures do not contribute to them.

## Using the reusable package

The downloadable product-quality-checker package is supplied in the chat. Start with README.md and ASSISTANT-WORKFLOW.txt; the latter describes how an assistant uses existing authorized tools to collect real records, independently review meaning, surface questions, repair drafts and recheck without adding a provider or background automation.

The local runner produces a blank assessment, full check report and persistent question queue. Commands support scaffold, check, fingerprint, loop, record-answer and apply-revision. A real assessment needs current source snapshots and actual independent review evidence; it never receives manufactured green attestations.

Qualification evidence is retained in tests/verification-receipt.json and redteam-review.json, with source/code hashes. Synthetic pass, pending and stale examples are included. The pending example remains needs_input; a repeated run creates zero duplicate questions. A changed-content example invalidates 1,534 prior review results. These are mechanical tests, not live Saha acceptance.

A future change to the catalogue or assessed material reopens the relevant review. The process is reusable and resumable; it is not continuously running against every Linear item until explicitly invoked with that scope.
