# SAHA documentation standards — all hierarchy levels

Planning documentation edition 4.2 · 10 October 2026. Criterion standard `3.0-generic`; canonical SHA-256 `a72502ce4dcfe5ec1e8537cd377f93e77ad32b9d998fdad62c252605089759fe`.

**Do not weaken criteria to obtain a pass.** This edition supersedes earlier checker instructions on this record; historical 166-field/449-detail/1,238-check qualification is not current Saha product evidence. Source snapshots are retained in the documentation revision archive.

## How to fill the documentation

State the source-backed fact, explicitly proposed recommendation, actual measurement or unresolved decision for each applicable component. Use stable IDs, versions and locators. Do not fill unknown evidence with optimistic prose or silently declare it N/A. A plan can retain a later-stage result as unmeasured; a dependent readiness/approval decision remains open. Shared components appear once in the team/source records and are linked.

The following current field/component inventory is a documentation reference, not a demand for one review verdict per component. The selected stage uses seven consolidated must-pass reviews per element. AI/personal-data fields are mandatory when applicable, and protected requirements never become optional through sampling.

## Writing and use rules

An epic includes its falsifiable riskiest assumption and decision consequence. Epics/stories include comparative priority reasoning and attributable forecast range/unit/method/confidence. A story records actor/trigger/action/value, scope, observable positive/refusal/error/authorization outcomes, current design/reuse, NFRs, dependencies and task links. A technical task names a bounded input/output and completion evidence. An acceptance criterion names preconditions, action, expected observable result and prohibited side effects without substituting implementation detail for user outcome.

Original source criteria, proposed refinements and frozen implementation criteria remain distinct. SAHA-153–160 drafts need a source/adoption decision before affected execution. R1/R2 targets are preserved; D02’s10/10 synthetic gate does not accept its wider parent.

Use the shared Ready/Done document and current stage rulebook. Post-release learning records target/baseline/actual, denominators, uncertainty, incidents and the real continue/improve/narrow/rollback/retire decision; it cannot be invented before release.
