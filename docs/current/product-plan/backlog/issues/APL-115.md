## User / outcome

As a frontline worker capturing an encounter, I need to receive a saved indicator only after the encrypted local mutation is durably committed, so that I can trust acknowledged work across crash, routine restart and temporary power loss.

Bounded scope: Show storage, database or encryption failure before acknowledging a save; recover all acknowledged records and identify unsaved inputs, with unsynchronised device destruction outside the source guarantee.

## Original requirement and acceptance text

### BR-OFF-02 — Durable local capture

Priority: Must; original release: R1.

The application shall acknowledge a save only after local persistence succeeds. Insufficient storage, database failure or encryption failure shall be shown before the worker believes a record has been saved.

Acceptance: Forced restart and low-storage tests preserve acknowledged data or clearly report that saving did not complete.

### NFR-04 — No loss of acknowledged local work

Priority: Must; original release: R1.

Acknowledged local saves shall survive application crash, routine restart and temporary power loss on supported devices. No record may be marked saved before durable persistence. Device destruction remains outside this guarantee until synchronisation.

Verification: Fault injection recovers all acknowledged records and identifies any unacknowledged inputs as unsaved.

## Additional CWO acceptance / refusal criteria

* **CWO-005-AC02 (New acceptance)**: After a confirmed durable save, force-closing and reopening the supported app/browser restores the same record and reviewed values after authorised unlock.
* **CWO-005-AC03 (New acceptance)**: An interrupted write leaves either the previous committed version or the next committed version, not a partially mixed record.
* **CWO-005-NEG02 (Expected refusal / recovery)**: Quota exhaustion or a failed encryption/write must not return a success receipt.
* **CWO-005-RJ02 (Delivery rejection)**: Reject a restart test that uses only mocked storage but is reported as handset durability.
* **CWO-009-AC05 (New acceptance)**: The declared process-kill/offline/reconnect sample loses no acknowledged save; any failure is reported and prevents qualification of that durability claim.
* **CWO-009-NEG01 (Expected refusal / recovery)**: A browser-simulated storage run cannot be labelled physical-device persistence evidence.
