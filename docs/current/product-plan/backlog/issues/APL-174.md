## User / outcome

As a story implementer or qualification reviewer, I want a reproducible isolated baseline with exact code, dependencies, migrations and actual check outcomes, so each reused component has evidence of preserved behaviour and an explicit unverified boundary.

**Scope boundary:** Compare inherited failures with candidate results. Mixed checkouts, missing access and similarly named legacy tests cannot produce a clean or full-production qualification claim.

## Additional CWO acceptance / refusal criteria

* **CWO-001-AC01 (New acceptance)**: Given an isolated checkout, when qualification begins, the report identifies the exact commit, dependency lock and migration set used.
* **CWO-001-AC02 (New acceptance)**: Given each selected check, when it finishes or is blocked, its actual command, outcome and limitation are recorded; an old pass is not substituted.
* **CWO-001-AC03 (New acceptance)**: Given existing failed checks, when a proposed feature branch is assessed, before/after results distinguish inherited failure from a regression.
* **CWO-001-AC04 (New acceptance)**: Given a proposed reusable component, its decision links a current source path, a behaviour to preserve and an explicit unverified boundary.
* **CWO-001-NEG01 (Expected refusal / recovery)**: A mixed main/candidate checkout is refused as a baseline; it must not produce a clean-baseline label.
* **CWO-001-NEG02 (Expected refusal / recovery)**: Missing runtime access or credentials yields a blocked evidence row, not an inferred pass.
* **CWO-001-NEG03 (Expected refusal / recovery)**: A legacy test catalogue or requirement status change cannot be justified solely by a new similarly named test.
* **CWO-001-RJ01 (Delivery rejection)**: Reject the enabler when it claims full-repository or production qualification from the bounded selections.
* **CWO-001-RJ02 (Delivery rejection)**: Reject when original failing evidence or minimum assertions are silently removed.
