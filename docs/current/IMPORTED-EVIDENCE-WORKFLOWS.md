# Historical source evidence, review and overlap workflows

5 October 2026. B08 software continuation from independently reviewed contact import `7f33f0bf`. Local synthetic evidence only; external source/issuer verification, clinical acceptance, operational migration rehearsal and independent review remain pending. This does not mark BR-DATA-11 or the entire B08 accepted.

## Product behavior

Organisation & team now has a source evidence form for an existing historical imported visit. Choose its source/document reference, an optional pinned documentary programme answer, structured historical note, and original photo/audio files. A dry run precedes application. Advanced JSON manifests support bounded batches; the ordinary form does not require writing JSON. Applying accepted rows stores separate retained patient source evidence and actual attachment bytes. It never changes the original imported visit, programme enrolments, current answers, current measurements or a clinician's recorded decision.

A scoped clinician opens an audited source review showing original visit facts, pinned answers, structured notes, attachment links, source lineage and same-date Saha/cross-source overlaps. They explicitly accept historical reference use, reject it, or reference an existing overlapping visit without creating care. Review is bound to exact source content, original visit, current patient context and current overlapping visit bodies. A later change requires another explicit clinical review even when the client has refreshed its read fingerprint.

An accepted source can explicitly open one linked current care draft, only when no current draft exists. The draft uses the normal current patient/range/active-episode rules, with empty observations and empty programme answers; no historical observations are promoted. The care screen shows the reviewed historical source alongside the ordinary capture form. Clinicians make current decisions and save/confirm/verify/sign off through the existing server commands. Source review never signs off an imported visit or authorises clinical sending. Imported original visits remain excluded from every existing current-use, provider/AI, sending, referral, indicator and sign-off path.

## Initial CSV overlap and reversal

Historical visit CSV dry runs now identify same-date existing Saha/cross-source visits and earlier source rows in the same file. Unreviewed overlaps reject that row until a current scoped clinician explicitly chooses keep-separate, reject-source or reference-existing. The decision fingerprint includes exact source file SHA, row, normalised facts, pinned range/context and full current conflicting records. A new or changed overlap invalidates it. A reference-existing decision retains exact existing visit lineage and creates no new clinical record; a same-file row can be kept separate or rejected but cannot masquerade as an existing visit. Existing same-source/date duplicate refusal remains.

Counts reconcile `rows = accepted + rejected`. `referenced` and `overlapPending`, when present, are subsets of rejected rows, not additional source rows. Neither choice merges or rewrites patient identity or clinical bodies. Identity merge remains its distinct governed workflow. The usual row/reason rejection report and CSV import receipt semantics are preserved.

Both new source evidence batches and original historical visit CSV batches have review/hash/withdrawal workflows. Withdrawals retain source notes, answers, original bytes, original confirmed visits, audit and receipts. A failed original batch adds per-patient retained withdrawal evidence rather than rewriting confirmed clinical JSON. A source withdrawal blocks new linked care; already captured independent care remains intact and displays the historical withdrawal. A clinically corrected original batch requires individual review and refuses blind whole-batch withdrawal.

## Authority, atomicity and retained provenance

`GET/POST /api/imported-evidence` obtains trusted identity before parsing/body validation. Current active clinician or owner-supervisor import scope is required; explicit clinical decisions and linked care require a clinician. Owner authority never widens normal patient/team/facility/programme scope or emergency access. Care-coordination purpose is checked. Provisional identity and processing restrictions reject new evidence imports. Misconfigured environments refuse writes. Maintenance stops new mutations; currently scoped saved receipt lookup and historical reads remain available.

Source apply, attachment media rows, patient retained evidence, audit chain and command receipt share existing `persist` atomicity. No migration or new persisted table. Same-key/hash retry never repeats a mutation; a different body or organisation refuses. Saved receipt reads reauthorise every retained target, including all patients of an applied/withdrawn batch; they do not recreate decisions. Metadata types are type-only dependencies. These whole-organisation persistence commands are **not partition certified**.

Material source content is returned only after durable `viewRecordHistory` audit, followed by a fresh read in the pinned resolved organisation. Current membership, purpose and patient scope are rechecked; any source/visit/version drift refuses the response. Read detail contains only identifiers/counts and a fixed operation label, no notes, facts, names or attachment bytes. Actual media reads use the existing audited media route. Mutation reasons follow existing human-audit semantics.

Answer rows pin a known compiled/retained installed pack version, question label and manifest SHA. Only documentary questions are accepted; measurement questions belong in historical visit import. Options are validated, prototype keys cannot select an implicit question, and no source answer enters current programme capture. Source row SHA is over the validated normalised manifest row; it is not a claim of an external signed original document. Attachment SHA is over the exact original bytes; signature/type/size validation uses the existing photo/audio media policy, not malware scanning or full document validation. No URL fetching, source credentials or live provider activation.

## Bounds and retry limits

At most 20 evidence rows per manifest, JSON under 1 MiB, 30 documentary answers, five structured notes, three attachments per source row; each attachment is 512 bytes–256 KiB in the existing JPEG/PNG/WebP/WebM/Ogg/MP3/MP4 set. PDF and other arbitrary files are refused. Retained per-patient source limit 100, source review/use limits 50 each, overlap decisions 200 and original source-batch withdrawals 100. Caps reject additional work; they never truncate or erase history. Original CSV retains its 16 KiB/100-row limit; unsupported larger withdrawal batches refuse atomically.

Browser retry keys are stable for the same operation body during the mounted session, and the server enforces durable idempotency. Unsaved source import input is not copied into plaintext persistent browser storage. Reload loses an unconfirmed UI key; the operator must inspect retained source lineage/receipt evidence rather than infer a failed import or blindly replay changed input. This is an online workflow, not an offline import queue.
