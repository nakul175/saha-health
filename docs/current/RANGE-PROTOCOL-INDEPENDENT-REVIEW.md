## Reproduced phone save defect and fix

The author's preliminary `Save draft.focus()` hid a real first-touch failure. At 390×844 with Chromium mobile/touch emulation, editing the unusual-weight reason and tapping Save produced pointer/touch events on the button, then textarea focusout, then a click on the containing DIV. No save command or saved toast followed; a second tap succeeded. The button was the same connected DOM node throughout and scroll offset remained unchanged. Its top moved from 400.30 to 377.25 pixels between touchend and click, placing the original finger position just outside its new bottom edge. Original aggregate event evidence is `tests/evidence/range-independent-review/first-tap-before.json`.

Cause: VoiceInput adds 44 pixels of right padding to the focused field and removes it as focus moves away. The textarea uses `field-sizing: content`; changing its available text width reduces its wrapped height on blur and moves the following Save button. The fix reserves that microphone gutter consistently for editable, voice-enabled textareas outside speech-control UI. It preserves content sizing, labels, typing, native keyboard focus and ordinary button click handling. No pointer interception, forced focus or second save path was introduced. Read-only/disabled and `data-voice="off"` controls retain their previous sizing.

New `tests/range-first-tap-browser.mjs` passed 18 checks against actual local Worker/D1: first touch, first mouse click and Tab/Enter keyboard activation immediately after reason editing, exactly one save request and saved toast, actual persisted quantity and reason, and stable button geometry before the click. No preparatory button focus is used. Fixed contextual first-touch events and the full-range rerun result are also preserved separately. Physical Android, its software keyboard and TWA remain outside this emulated-browser evidence.
