# Development slice 6j — tamper-evident audit chain

30 September 2026 (IST). Builds on the parallel base (R11 and slices 0a–3f, 6h). Synthetic data only; formal acceptance unchanged.

## What changed

- **Chain.** Every audit event written through `persist` or `createState` now carries a per-organisation sequence number, the previous event's hash and its own hash (`lib/saha/audit-chain.ts`). The content digest is SHA-256 of `JSON.stringify([org_id, id, person_id, actor_id, actor_name, role, action, subject, detail, at])`; the event hash is SHA-256 of `JSON.stringify(['saha-audit-chain-v1', seq, prev_hash, content])`. An auditor can recompute both without Saha code.
- **Migration 0013** (`0013_audit_chain.sql`) adds `seq`, `prev_hash` and `hash` to `audit_events` and a unique index on `(org_id, seq)`. Existing rows are not changed; the append-only triggers still refuse updates and deletes.
- **Concurrency rule.** One linear chain per organisation, not per patient partition. The head is read immediately before the commit batch and the events are linked to it. Two commits that read the same head (for example, two slice 0a patient-scoped commits on different patients) cannot both insert the next sequence number: the unique index fails the second batch, D1 rolls all of it back, and `persist` rebuilds it on the new head. After six lost attempts it returns a 409 asking the person to retry; nothing from that command is saved. The patient and organisation guards are unchanged, so a real patient conflict is still a 409 and an organisation-wide conflict is not retried. A batch that fails for any other reason is not retried.
- **Genesis marker.** The first chained event of every organisation is sequence 0, `auditChainGenesis`, actor "Saha audit chain" (shown as System in the activity log). For an organisation with events from before the migration, the marker records how many there are, the last one (time and id) and a digest over them in `(at, id)` order, 500 per step. Those events keep empty chain columns; nothing is rewritten. New organisations start the chain at creation with a count of 0; migrated legacy workspaces chain their copied events after the marker.
- **Verification.** `GET /api/audit/chain` (owners and administrators) walks the chain in sequence order, recomputes every hash, checks each link and the genesis seal, and reports `intact`, `broken` (with the first break: sequence, event id, reason), `not-started` or `incomplete` (over 100,000 events). It returns counts, hashes and reasons, never event content. Events whose time is more than five minutes earlier than the event before them are counted as clock regressions; this is reported, not a break.
- **Export.** `GET /api/audit/chain?format=jsonl[&from=N]` returns up to 5,000 chained events as JSON lines: a header with the hashing rule, one line per event with its digests, and a sign-off (who, when, range, head, verification result, SHA-256 of the lines above it). Events linked to patients outside the exporter's care-team scope (the activity-log rule; an administrator never has patient scope) are listed with their digests only, so the chain still verifies. Each export is recorded in the chain as `auditChainExport`, whose detail carries the file digest.
- **Screen.** The activity log gains an "Audit chain" panel for owners and administrators: Verify chain and Download export (JSONL).

## Evidence

- 48 contract assertions (`tests/audit-chain-contract.mjs`, real migrations in SQLite through the D1 shim): offline recomputation of both hashes; genesis at creation; commits extend the chain; an interleaved patient-scoped commit forces a rebuild on the new head with no fork and both writes kept; a real patient conflict still refused with nothing chained; a commit that loses six races in a row is refused with a 409 and writes nothing; a failed batch for another reason not retried; export lines recompute offline, administrators receive digests only for patient-linked events, a changed export line is detected; altered content, content plus its own rewritten hash, a deleted event and a forged appended event are each reported at the right sequence; restoring the original values restores the chain; genesis over 1,203 earlier events reproduces offline and detects a changed or added earlier event; a genesis race leaves one genesis; clock regression reported without a break; the verification limit reports incomplete; the triggers and the unique index hold.
- 40 HTTP/D1 assertions (`tests/audit-chain-smoke.mjs`): worker, supervisor and a non-member refused; an administrator invited to a new organisation verifies it intact without content and exports patient-linked events as digests; bad format and range refused; the owner's export has a header, every line recomputes offline, the sign-off digest matches the body and the export event is chained after it; a forged event inserted directly into the database is reported as the first break, and later commands still chain.
- `tests/storage-contract.mjs` and `tests/scoped-read-contract.mjs` transpile `store.ts`, so `audit-chain` was added to their file lists; both pass unchanged. `tests/database-fixtures.mjs` now expects three audit events after a legacy migration (the genesis marker is the third).
- Browser check (headless Chromium, built Worker, synthetic owner): the activity log showed the panel, Verify chain reported Intact, the downloaded JSONL's sign-off digest matched its body, and the genesis and export events appeared in the log; no console errors. The accessibility audit now covers the activity log (25 screens) with no violations. `tests/evidence/slice-6j/`.

## Limits

- Tamper-evident, not tamper-proof. Someone who can write the database can rewrite a suffix of the chain and all its hashes; that is detected only against a head recorded elsewhere (an earlier export's sign-off). There is no external anchoring, no signing key and no scheduled verification.
- The sign-off is recorded in the chain, not signed with a private key.
- Events written before the chain are sealed by digest but not listed in the export, so an auditor cannot recompute that digest from the export alone.
- Verification and exports read the whole range in one request; very large organisations need paging or background checks. Verification itself is not audited.
- BR-SEC-08 stays partial: material reads are still not audited, and the audit fields do not yet record authority or object version consistently. NFR-10 stays partial: there is no audit-store fault injection and no rule that halts external writes when audit durability fails.

## Correction, 30 September 2026 (slice 6p)

An independent review after this slice was built found two defects in the auditor export. The export's own `auditChainExport` event was committed against the state read at the start, so any command saved while the export was prepared made the whole export fail with 409. The visibility rule excluded administrators from patient-linked event content but not the sandbox `provider` role. Slice 6p records the event through `persist` with a bounded retry on a fresh read that repeats the owner-or-administrator check (and refuses if the role changed), and excludes the provider role in the export query. See [slice 6p](SLICE-6P-REVIEW-FIXES.md). The text above is kept as written.
