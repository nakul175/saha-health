# Development slice 5b — provider self-service in a provider sandbox

30 September 2026 (IST). Stacked on the integrated round-1 branch (slices 3g–6l). Synthetic data only; formal acceptance unchanged.

## What changed

- **Provider sandbox.** An owner can declare an organisation a provider sandbox for exactly one registered AI provider (`declareProviderSandbox`: provider id and a reason). Only an organisation with no patient records, no visits, no reviewed or active packages and no members other than owners can be declared, and the declaration cannot be undone. It is kept in the organisation's governance document (`governance.sandbox`), so no migration was needed.
- **What a sandbox refuses.** A sandbox accepts only capability proposals for its provider, synthetic evaluations, provider documentation, invitations, member and team administration, renaming, switching, and withdrawing (retiring) a proposal. Every other command is refused with 409 for everyone, including the owner: creating patients, visits, agent requests, deliveries, operations settings, review and activation. Independent review and activation happen only in a production organisation.
- **Provider role.** A new membership role, `provider`, can be created only by `inviteProvider` in a sandbox (the ordinary invitation refuses it). A provider account may only save provider documentation, create capability proposals for the sandbox's provider, prepare, run and cancel its own synthetic evaluations, and switch organisation. Everything else is refused with 403 before any handler runs, and again when a command is replayed. A provider never has patient scope: `normallyAllowed` and the viewer-scoped SQL read exclude it, and the activity query gives it no organisation-level or patient events. An owner cannot turn a provider membership into another role or another membership into a provider; a provider can be suspended.
- **Documentation and test credentials.** `saveProviderDocs` stores a versioned summary, intended use, limitations, known failure modes, support contact, an optional https test endpoint without credentials, query or fragment, and an optional credential *reference*: the name of a server-side binding (upper-case letters, digits and underscores). Values that look like keys are refused. No credential value is accepted or stored, and nothing in this slice reads the referenced binding.
- **Import into production.** An owner of a production organisation who is also an owner of the sandbox imports a draft proposal (`importCapabilityProposal`: sandbox, entry and version, clinical owner, teams and change summary). The import requires provider documentation and a completed, passing synthetic evaluation of that exact proposal in the sandbox, and refuses a superseded or already-imported proposal. It creates an ordinary draft capability package through the existing `createGovernance` path, with this organisation's owner and teams, so its manifest hash differs from the sandbox one. The entry records its origin (sandbox, entry, revision, manifest hash, sandbox evaluation summary and the non-secret documentation fields). The sandbox evaluation does not count: the production draft still needs its own passing evaluation, review by a different clinician and owner activation.
- **Reads and screen.** `GET /api/provider-sandbox` returns the sandbox, its documentation and proposals with evaluation status to sandbox owners and providers; for a production owner it lists owned sandboxes with importable proposals (no credential reference or endpoint) and the proposals already imported. The Clinical governance page shows a "Provider sandbox" panel: providers edit documentation, owners invite provider accounts, declare an empty organisation a sandbox, and import proposals. Provider accounts see only the Clinical governance, Activity and Organisation views; proposals and evaluations use the existing governance forms.

## Limits

- Isolation is logical, within the same database and Worker: a sandbox is an ordinary organisation with command and read gates, not a separate deployment, database or network environment.
- The synthetic data is the fixed evaluation corpus; a sandbox has no synthetic patient fixtures and no agent requests on synthetic visits.
- A provider cannot register an HTTP endpoint or credential binding itself; the sandbox owner registers integrations, and live providers remain disabled in the HTTP sandbox, so HTTP evaluations use the local rules provider. The credential reference is recorded, never resolved.
- One provider per sandbox, and only capability packages. There is no provider-side view of production outcomes, no notification to the provider when a proposal is imported or reviewed, and no expiry of provider memberships beyond the usual suspension.
- Other read routes return the sandbox organisation's (empty) data to a provider rather than refusing outright; they hold no patient records because patient work is refused in a sandbox.
- BR-AI-11 is partial: acceptance by an independent tester, a provider-facing contract and a physically isolated environment remain.

## Correction, 30 September 2026 (slice 6p)

An independent review after this slice was built found that importing a capability proposal read the whole named organisation before checking that the importer owned it, and answered differently for an organisation that did not exist (404), was not a sandbox (409) or was not the importer's (403), which told a caller whether an organisation existed and whether it was a sandbox. Slice 6p checks the importer's active owner membership and the sandbox declaration before reading the source, and answers one 404 with one message for all three. See [slice 6p](SLICE-6P-REVIEW-FIXES.md). The text above is kept as written.
