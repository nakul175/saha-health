# Development slice 7e — separate operation permissions for every adapter

1 October 2026 (UTC). Builds on the programme delivery (MIS), EHR exchange, mock ABDM (7a, 7b), exception queue (6i), EHR publications closed as not sent (6u) and task trace (6y) slices. Synthetic data only; formal acceptance unchanged. One owner command is added (`setAdapterOperations`); no route, no patient command and no migration.

## What changed

- **Operations per adapter.** Every record adapter (programme destinations, HTTP and demonstration; EHR connections; the mock ABDM gateway) now declares which operations it may perform: create, update, delete or void, lookup, and aggregate reports. The setting lives in the integration's existing JSON (`operations`: version, permitted operations, aggregate-only flag, who set it, when, the reason, and up to 20 earlier settings). Code: `lib/saha/adapter-operations.ts`.
- **Default is the earlier behaviour, made explicit.** An integration with no stored setting uses the release default, shown as setting version 0: programme destinations create, update (send corrections) and look up receipts; EHR connections create (publish) and look up publication receipts; the mock ABDM gateway creates (ABHA and care-context links), deletes (ABHA unlink) and looks up (consented fetch). Nothing changes for existing data until an owner narrows a setting.
- **Where each operation is used.** Create: queuing or simulating a programme submission, an EHR publication, ABHA and care-context linking. Update: a programme correction of an accepted submission. Delete or void: ABHA unlinking on the mock gateway only. Lookup: programme receipt lookup (HTTP and the demonstration reconcile), EHR publication receipt lookup, the mock HIU fetch. Aggregate: no path in this release. EHR document retrieval stays governed by the EHR read direction and patient-scoped read permission, as before; it is not a lookup in this sense.
- **Owners only, versioned, audited.** `setAdapterOperations` names the integration, the setting version the owner reviewed (0 for the default), the permitted operations, the aggregate-only flag and a reason. Only an organisation owner may send it (checked on the server, and again on replay through the owner-only list in the replay block). A stale version is refused (409), as is a change that changes nothing; AI providers are not record adapters and are refused (422). Each change writes a `setAdapterOperations` audit event with the new list, the version and the reason. *Decision:* changing operations does not bump the integration's approval version, so existing approvals are not silently invalidated as "connection changed"; instead every send and lookup rechecks the specific operation and a withdrawal is recorded as a refusal on the item.
- **Aggregate-only destinations.** A programme destination can be marked aggregate-only. It may then permit only aggregate reports and lookups (never create, update or delete; the schema refuses the combination), and every path that would send it a patient-level record refuses with "aggregate-only destination: it may receive aggregate reports only, never a patient-level record", whatever other operations say. Receipt lookups for deliveries made earlier carry no record and remain possible if lookup is permitted. EHR and ABDM exchange is patient-level and cannot be aggregate-only (422).
- **Checked before preparing and inside the checkpoint.** Programme plan preparation refuses a destination that may not create (or update, for a correction) or is aggregate-only, before any payload is prepared. Plan execution checks again per destination: a destination whose operation was withdrawn after approval gets a submission recorded as `cancelled`, attempts 0, with a `refusal` (operation, setting version, aggregate-only flag, stage `before-send`, time) and the message "Not sent: … Nothing was sent to this destination"; other destinations proceed. Sending a queued HTTP delivery checks the operation before the checkpoint (a withdrawal closes it as not sent the same way) and again after the checkpoint is stored, on a fresh read, immediately before the request: a withdrawal there stops the request, closes the delivery as not sent with stage `checkpoint` and releases the reserved attempt. EHR publication preparation refuses without create; execution closes a prepared publication as `blocked` (not sent) with a refusal before the checkpoint, and rechecks create inside the checkpoint after the remote patient check and before the write (`blocked`, stage `checkpoint`). Receipt lookups (programme, demonstration reconcile, EHR) are refused before the checkpoint and rechecked inside it; a lookup withdrawn inside the checkpoint makes no request and leaves the outcome unknown ("Receipt lookup not made …; do not resend"). Mock ABDM steps are single local commits; a refused step changes nothing. No refused item is ever retried automatically: a closed item stays closed and a new plan or publication must be prepared.
- **Visible on the trace and the exception queue.** Refusal steps are stamped by `linkTrace` with the command (`executePlan`, `sendSubmission`, `executeEhrPublish`, or `adapterOperationRefused` for a refusal inside a checkpoint) and the `adapterOperationRefused` audit event; each trace item now carries `refusal` (operation, setting version, aggregate-only flag, stage, time) or null. The exception queue (rules 1.2.0) adds kind `operation-refused` for programme deliveries and EHR publications closed by a refusal, until a later submission or publication for the same visit and destination exists; it is an operations kind, so owners and administrators see it redacted for patients outside their scope, with the trace link.
- **Screens.** Each programme, EHR and ABDM connection card has a "Permitted operations" disclosure listing the five operations, where Saha uses each (or that no path exists and changes need a separate process with the partner), the setting version and the last few earlier settings. Owners can tick operations, mark a programme destination aggregate-only (which clears create, update and delete), give a reason and save; other members see the setting read-only. Programme destinations state that Saha has no aggregate report delivery yet, so an aggregate-only destination currently receives nothing from Saha. The exception queue labels the new kind "Operation not permitted".

## Limits

- No aggregate report delivery exists yet. The aggregate operation and aggregate-only policy are enforced as refusals of patient-level records; an aggregate-only destination receives nothing from Saha until an aggregate report path is built, and the live payload minimisation audit (BR-INT-09) is not built.
- Delete or void is used only by the mock ABDM unlink; Saha has no programme or EHR void path, and permitting delete there creates none. Update is used only by programme corrections; EHR amendment publication still requires a partner-specific workflow.
- EHR document retrieval is governed by the EHR read direction and patient read permission, not by the lookup operation. AI providers are not covered (their use is governed by capability lifecycle, slice 5d).
- Mock ABDM refusals are plain refusals with nothing changed; they are not raised in the exception queue or traced (ABDM exchanges are not part of the 6y trace).
- A refusal inside the programme checkpoint uses one extra state read before the request. The operation setting is per integration, not per programme, team or patient.
- BR-INT-02 and BR-INT-09 stay partial: no live partner has been configured or tested with narrowed operations, and none of this is accepted for production.

## Correction — 2 October 2026 (slice 6ab)

An eighth independent review found three gaps: a correction to a demonstration destination (which has no payload) was classified as a create, so withdrawing `update` did not stop it; `abdmConsentRequest` and `abdmConsentRevoke` had no operation; and an EHR publication read `Patient/<externalId>` before its create recheck. Slice 6ab classifies a correction by an accepted submission of a visit it corrects to the same destination, governs consent requests by `lookup` (a revocation always applies; `delete` decides only whether the mock gateway is told), and rechecks `create` before the patient read. See [SLICE-6AB-EIGHTH-REVIEW-FIXES.md](SLICE-6AB-EIGHTH-REVIEW-FIXES.md).
