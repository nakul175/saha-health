# Development slice 10e — issuer-identifier search, ABHA number format checks and programme identity crosswalks

2 October 2026 (IST). Lane E of the ten-lane build. Builds on slices 1c (identity cases and two-steward merges), 2h (record import and external identifiers), 6r (emergency access cannot open merge cases), 6t (material-read audit), 6u, 6z and 6ab (neutral and bounded ABHA refusals) and 7a (ABHA mock workflows). Synthetic data only; formal acceptance unchanged. BR-ID-05, BR-ID-08 and BR-INT-14 stay partial.

## What changed

- **ABHA number format, and no checksum.** An ABHA number is accepted as 14 digits, or as 14 digits grouped 2-4-4-4 with hyphens (`91-1234-5678-9012`); anything else, including mixed or partial grouping, spaces, letters and 13 or 15 digits, is refused with a message that shows the accepted shapes. It is stored and shown in the grouped form, as before. The rule is one regular expression (`ABHA_FORMAT`, `lib/saha/identifier-search.ts`) shared by the search and by the slice 7a `abhaLink` schema (`lib/saha/abdm.ts`), and a contract check compares the two. **No checksum is applied, because no official specification of one was found.** See "Why no checksum" below. A number that passes the format check is not thereby known to exist in ABDM.
- **Search by issuer identifier.** `POST /api/identifier-search` with `{issuer, identifier}` returns the people in the searcher's own care scope that hold exactly that identifier now. Searchable issuers are `abha` (a linked ABHA number, slice 7a) and the programme issuers `rch` and `nikshay` (identifiers from slice 2h imports or from the crosswalk below). It is a POST so the identifier travels in the body, never in a URL or a log line; the body is limited to 2,000 bytes, the origin must match and the content type must be JSON. The scope is the same viewer predicate as every other patient read: an ASHA's assigned people, a clinician's or supervisor's teams, never an administrator or provider, never a suspended member. The candidate query applies that predicate inside SQL, so a record outside the scope is never loaded for the searcher; a record reachable only through an emergency grant (slice 6a) is returned only while the grant is live. A merged record is returned flagged as merged, with an "open the surviving record" action only when the survivor is also in scope.
- **No enumeration.** Only exact, complete identifiers are searched: the value must pass the whole-value format of its issuer (an ABHA number as above, an RCH ID of 12 digits, a Ni-kshay ID of 6 to 10 digits), so a fragment, prefix, wildcard or range is refused with a format message and never searched (a "partial" search is refused, not widened). A record outside the searcher's scope gives the same answer as no record at all ("No record in your care scope carries this identifier."), with the same status, text and fields, so the search cannot be used to learn that a person exists elsewhere. Results are masked (all but the last four characters; an ABHA number as `91-XXXX-XXXX-9012`). Searches are limited per searcher from the audit chain: 30 searches an hour, of which at most 8 may find nothing, and 24 finding nothing a day; over the limit the answer is 429 before any record is read.
- **Every search is a material read, audited first.** The server writes an `identifierSearch` access event on each matched record (one event per record, sharing one search id), through `lib/saha/access-audit.ts` (slice 6t), before anything is returned. A search that finds nothing writes an `identifierSearchMiss` event with no record (it is the fishing signal and feeds the miss limits; only owners and administrators see person-less audit events). The events name the issuer label and the number of records, never the identifier value. They add no revision, receipt or organisation-revision movement. If the event cannot be written, nothing is returned (503).
- **Programme identity crosswalk.** A person's `identifiers` list becomes an append-only ledger. Each entry records who recorded it (`recordedBy`), when (`recordedAt`), its source (`import` from slice 2h, or `crosswalk`), where it came from (`origin`: programme card or booklet shown, looked up in the programme's own system, told by the person, or a referral or discharge document), its verification state (`unverified`, `document-seen`, or `issuer-checked`), the evidence described, and the reason. Verification is attested by a person: Saha never contacts an issuer, and every entry is shown as not verified by Saha. Two new commands, organisation-wide rather than patient-partitioned (`PATIENT_COMMANDS` is unchanged) because a link compares one record with every other:
  - `identifierLink` (person, version, issuer, identifier, origin, verification, evidence, optionally `corrects` naming an entry, reason of at least 10 characters). An ASHA with access, a clinician or a supervisor may link; only a clinician or supervisor may record `issuer-checked`. `document-seen` and `issuer-checked` need a described piece of evidence. One current identifier per issuer on a record: a second one is refused unless the command names the entry it corrects.
  - `identifierWithdraw` (person, version, entry reference, reason): clinician or supervisor only.
  - **Corrections append.** A correction or a withdrawal adds a new entry naming the one it replaces (`corrects`, by entry id, or `import:<batch>:<row>` for a slice 2h imported entry); the earlier entry stays in the record, in its revision history and in the history list on the screen. The current identifiers are those no later entry replaces. Slice 2h had no command to correct or remove an imported identifier; this adds one.
  - Matching by identifier in the slice 2h record import and its uniqueness checks follow the current entries, so a corrected or withdrawn value neither resolves a record nor blocks the same value elsewhere.
- **Conflicts go to the identity case path and are never merged.** An identifier is held by at most one live record in the organisation. When a link would put a value on a second record, nothing is recorded on either record. If the requester may see the holding record in the ordinary way and is a clinician or supervisor, the command opens the slice 1c merge proposal (the holder as survivor, evidence "Same identifier", a reason that carries the masked value) and returns `{linked:false, conflict:{personId, caseId}}`; two different stewards must still decide it, and nothing merges until they do. A requester who is not a steward gets a 409 that points to a steward. A record reachable only through an emergency grant counts as outside the requester's scope for this purpose, as in slice 6r.
- **A holder outside the requester's scope is not revealed.** The link is refused with a neutral text ("This identifier could not be recorded. Check the number; if it is correct, ask an identity steward to review this record.") that is also used for the daily limit below; the server records an `identifierConflictReview` access event on the holding record for an identity steward (visible only to members who may see that record), once per requester and holding record a day. After three such records by one requester in a day, every further link by that requester is refused with the same text whether it conflicts or not. As for ABHA numbers in slice 6ab, the oracle is bounded, not removed (see Limits).
- **Merged records.** A link, including a correction, is refused on a merged record (the survivor takes it); a steward can still withdraw an identifier from a merged record.
- **Masking.** The snapshot and patient history mask every ledger value like imported ones (all but the last four characters); the entry id stays visible so an entry can be corrected. Audit lines mask the value too.
- **Screens.** People gains "Find by identifier" (identifier type, complete identifier, results with an Open record action and the verification text, and the limits in plain words). The record tools row gains "Programme identifiers": the identifiers held now with source, origin, verification, evidence and who recorded each; correct and withdraw; a link form; the full history; and the conflict outcome in words. Care roles see the forms; others see the list.

## Why no checksum

The slice allowed a checksum only if an official ABDM or National Health Authority source specifies one. None was found, so none is applied and none is invented. Sources consulted on 2 October 2026:

- Press Information Bureau, Ministry of Health and Family Welfare, ABHA explainer of 4 April 2024 (PRID 2017129): describes the ABHA number as a randomly generated 14-digit number. No check digit is described.
- CoronaSafe ABDM implementers' guide (community-published, not an ABDM document): describes it as a randomly generated 14-digit number, written 2-4-4-4 with hyphens in examples. It is not an official source and is cited only for the grouping used here.
- An OpenMed note on ABHA structure (community-published): says nothing about a check digit.
- `abdm.gov.in` pages and the ABDM sandbox and API documentation could not be fetched from this environment (the FAQ returned 403; the sandbox documentation was not retrievable), so they were not read. The official specifications, which may say more, remain to be checked by a person with access.

The 2-4-4-4 grouping is itself backed by community material and by the examples already used in this repository, not by an official specification. If ABDM publishes a check digit, adding it is a change to `ABHA_FORMAT`'s sibling `parseAbha` and a contract fixture list; until then a mistyped but well-formed number is caught only by the one-time-code verification of slice 7a (which is a local mock).

## Limits

- **Format only, no checksum.** See above. Saha does not know whether an ABHA number, RCH ID or Ni-kshay ID exists, or belongs to the person: the verification state is the word of whoever recorded it, and the ABHA link of slice 7a uses a public mock one-time code against a local mock gateway. Nothing is sent to any issuer or destination; as in slice 2h, identifiers are not sent to programme destinations or FHIR documents.
- **Issuer formats are illustrative.** `rch` (12 digits) and `nikshay` (6 to 10 digits) are those of slice 2h and have not been checked against the issuing registries. Only these two programme issuers exist; adding one is a code change.
- **The conflict oracle is bounded, not removed.** A requester who types an identifier held by a record outside their scope is refused with the ordinary text and cannot tell it from a mistyped value in one attempt. Repeated attempts still leak a little: an attempt that opens a review event or one that does not differ only in the audit trail the requester cannot see, but a requester who is allowed three conflicting probes a day learns that three of the values they typed are in use somewhere. After that every link by them is refused the same way until the day passes.
- **The search leaks nothing about records outside scope by response, but timing was not tested.** The response for a hit and for a miss differ in work done (a hit loads and audits records). No timing measurement was made, and none is claimed.
- **Counting cost and races.** The rate limits are read from `audit_events` for the searcher over the last day: no new table and no migration. The only audit indexes are on organisation and person and time (`audit_org_person_time`) and organisation and sequence (`audit_org_seq`), so each search or link counts by scanning the organisation's audit rows for the actor; the cost grows with the organisation's audit history, and an index on organisation, actor, action and time would remove it. Two parallel searches by one searcher can each read the count before either writes, so the limits can be exceeded by a few under concurrency (as with the slice 6ab throttle). A refused 429 is not itself written to the audit chain.
- **Per-record, not national.** One live holder per issuer and value per organisation; no cross-organisation check, and no duplicate review beyond the slice 1c case a steward opens.
- **Visits and other kinds are not covered.** Search finds people, not visits or other record types. Programme identifiers are not shown elsewhere on the patient screen than the Programme identifiers dialog.
- **Merged records.** A search can return a merged record flagged as merged; the surviving record is offered only when in scope.
- **Cap.** A record holds at most 50 identifier entries (links, corrections and withdrawals count), after which an owner must review the record.
- **Withdrawing is not deleting.** A withdrawn identifier stays in the revision history and the history list, masked.
- **Accessibility.** The screens use the existing dialog, form and list components; the browser check includes an automated axe scan. No assistive-technology testing was done.
