# Development slice 6s — owner-maintained indicator registry and differencing protection

1 October 2026 (UTC). Builds on slices 6d (indicators), 6k (reconciled export) and 6l (safe logs). Synthetic data only; formal acceptance unchanged. No AI model is involved.

## What changed

- **Vocabulary.** `lib/saha/indicators.ts` now separates what can be counted from how an indicator is defined. Sixteen per-patient measures (for example patients, patients with a confirmed visit in the window, open and overdue follow-ups, referrals created and completed in the window, reuse opportunities and reuse served), three cohort filters (programme, age band, sex), two structured exclusions (provisional identities, patients with no programme) and four cadences. There is no expression language, no free field name and no query text.
- **Registry.** A definition is a title, unit (count or proportion), numerator measure, denominator measure for proportions, filters, exclusions with a note, owner, cadence and a minimum cohort of at least 5. The twelve slice 6d/2a catalogue indicators are the registry's version 1 entries ("Saha release"). An active owner adds (`addIndicatorDefinition`), revises (`reviseIndicatorDefinition`, naming the version being replaced) and retires (`retireIndicatorDefinition`) definitions through `/api/commands`, each with a reason of at least 10 characters. Every change appends a new version to `operations.indicatorDefinitions`; earlier versions are never changed. A stale version is refused (409), as is an identifier already in use, a proportion without a denominator, a count with one, an unknown measure or filter, or any extra field. Each change writes an `indicatorDefinition` audit event. The owner check runs again when a saved command is replayed.
- **Results name their definition.** Every indicator result carries the definition identifier, version, recording time and canonical form (measures, filters, exclusions, minimum cohort). A query may name `id@version` to run a recorded version, including a version later revised or retired, so an earlier result can be recomputed from the version it names. Naming a retired indicator without a version is refused with that explanation. A definition's own filters and exclusions narrow the cohort; when the result is below that definition's minimum cohort it is withheld (`refused: "cohort"`) without its rows.
- **Differencing protection.** After a query is computed, the server records a release for the viewer: hashed query filters (team, village, programme), a hashed series key (grouping plus the definition's own filters and exclusions) and the number of people in each released cell under hashed group labels, with a hashed viewer key. No patient identifier, name, village name or value is stored. Before anything is returned, the new release is compared with the same viewer's releases of the same series in the last seven days: if a cohort and its one-filter refinements (for example all villages and one village, or a parent and the sum of several one-village children) leave a remainder of 1 to 4 people in any cell, the result is withheld (`refused: "differencing"`). When the query's overall cohort size would itself reveal such a remainder, the whole query is refused (422). The ledger is kept to seven days and at most 500 releases, written through `persist` on a fresh full read with the viewer's role and care scope checked again (a concurrent commit is retried up to three times), and removed from the operations data returned to operators.
- **CSV.** `POST /api/indicators` with `format: "csv"` returns the suppressed result as CSV: computation time, window, cohort, grouping, minimum cell and draft status, then for each indicator its identifier and version, with suppressed cells written as "suppressed" and withheld results as "Withheld" with the reason. Cells are formula-escaped with the existing CSV helper. The same differencing check applies.
- **Workspace.** The Operations page's Indicators section shows each result's definition and version, explains withheld results, and offers "Download CSV". A new registry panel lists current definitions (measures, filters, exclusions, owner, cadence, minimum cohort) and, on request, every organisation-recorded version with its reason and a "Run vN" button. Owners get a form to add a definition, save a revision as a new version or retire one, built only from the vocabulary lists. All requests post JSON bodies (slice 6l); no filter, title or reason goes into a URL.

- 12 contract checks (`tests/indicator-registry-contract.mjs`): built-ins as version 1; owner-only authority including the replay check; vocabulary validation (no denominator, wrong unit, unknown measure, extra field, unknown filter, minimum below 5, short reason, existing identifier); a result naming its definition and version; revision appending version 2 with version 1 unchanged, and `@1` reproducing the earlier result exactly; definition minimum cohort and exclusion; retirement refusing current use while `@1` still runs; revising a built-in and following the registry in the interpreter; series holding per-cell people counts only; differencing (one-filter refinement, sum of children, order independence, disjoint cohorts, zero remainder, another viewer, another series, outside the window, nested inside another filter, per grouped cell, two filters apart) and ledger pruning.
- HTTP/D1 checks (`tests/indicator-registry-smoke.mjs`, run last in `tests/api-smoke.mjs`): catalogue and vocabulary; supervisor and ASHA additions refused; invalid specifications refused; add, stale revision refused, revision and retirement; results named by version and `@1` reproducing the first result after revision; retired current use refused and `@1` still served; three audit events; the stored ledger free of village names and of the viewer's identifier and absent from the operations read; the CSV carrying versions and no shown count from 1 to 4; in a fresh synthetic organisation with 7 and 2 people in two villages, the whole-cohort query answered, the 7-person village refused for differencing and the 2-person village refused as a small cohort, the same whole-cohort filters still answered, and another viewer unaffected.

## Limits

- Differencing protection covers one viewer's own queries over seven days for nested filter sets (a cohort and its one-filter refinements, singly or summed). It does not track several viewers colluding, overlapping filters that are not nested, differences across grouping dimensions or across definitions with different filters, or changes in the underlying records between queries. Cohort membership changes can cause conservative refusals.
- Each indicator query now also reads the whole organisation state and commits its release through `persist`, so it costs a second read and a write, and a query can fail with 409 after three concurrent commits. This was not measured at scale.
- The ledger stores per-cell people counts (hashed labels) in the organisation's operations record. It is not returned by any read, but it is included in the owner's organisation data export.
- Built-in measures are still code; an owner chooses and combines them but cannot define a new measure. There is no approval workflow, second reviewer or effective date for a definition change, and no validation of a definition against an approved programme specification (BR-AG-11's "validated definitions").
- Reproduction recomputes a recorded version over current records and the current window ending now; it does not snapshot past data, so a figure changes if the records behind it changed.
- The CSV is a draft download without the slice 6k manifest or control totals. Once saved it is outside the application.
- BR-REP-02, BR-REP-04 and BR-AG-11 stay partial.

## Follow-up 6s-2, 1 October 2026 (UTC) — indicator export manifest and audit

- **What changed.** The indicator CSV now names its export identifier and the exporting member and role after its title, and ends with the slice 6k manifest: the number of data rows and the SHA-256 of every line above, so a receiver checks it with `head -n -2 saha-indicators.csv | sha256sum`. The identifier and checksum are returned in `X-Saha-Export-Id` and `X-Saha-Content-SHA256`, and the file is built inside the same commit as the differencing release, which also records an `indicatorExport` audit event naming the export identifier, each definition and version (marked when withheld), the data row count and the checksum. No filter value or village name is written to the audit line. The page confirms a download with the identifier and the start of the checksum.
- **Evidence.** The HTTP smoke recomputes the manifest row count and SHA-256 with Node's own hash, matches them to the response headers, finds the identifier and exporter rows, and reads the audit event (actor, checksum, definition version, row count, no village names). See [VALIDATION.md](../../VALIDATION.md); reports in `tests/evidence/slice-6s-2/`.
- **Limits.** As in slice 6k, the checksum shows the file is unchanged since export; it is not a signature. There are no control totals for indicator results, and every export remains a draft.

## Correction — 1 October 2026 (slice 6w)

Differencing compared people counts only, so a query whose numerator differed from an earlier one by 1 to 4 was released; the definition's own filters were part of the series key, so complementary definitions (all, female, male) were never compared; the ledger was cut to its newest 500 releases across the organisation, so protecting releases could be evicted inside the seven-day window; every view committed organisation-wide through `persist` (moving the organisation revision and writing a command receipt, including on GET); and the owner's data export included the ledger. Slice 6w compares numerators, denominators and their difference, treats definition filters as nesting dimensions and screens one query's definitions against each other, prunes by time only and refuses new queries at a bound, writes the ledger without moving revisions or writing receipts, makes queries POST only, records the CSV export as an access-audit event, and leaves the ledger out of data exit. Found by a fifth independent review (an agent that did not write the code) of round-1 slices 0b-4, 4e, 6s and 6t; the original text above is kept. See [slice 6w](SLICE-6W-FIFTH-REVIEW-FIXES.md).
