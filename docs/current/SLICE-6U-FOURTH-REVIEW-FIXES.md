# Development slice 6u — fixes from a fourth independent review of main

1 October 2026 (UTC). Builds on `int5-6t-read-audit` (`153e741`: main plus round-1 slices 0b-4, 4e, 6s and 6t). Synthetic data only; formal acceptance unchanged. No command, route or migration is added; the route count stays 43 and the certified patient command count stays 48.

These defects were found by a fourth independent review, carried out by an agent that did not write the code, of code already on GitHub `main` (`15bb1de`), which had been merged without independent human review. The code had been built, tested and recorded as passing; the earlier passing runs did not test these cases. Each defect was reproduced on the base before it was fixed, with the new regression checks, which fail on the base and pass after the fix (and, for findings 1–3, with the reviewer's scripts `exc-outreach.mjs`, `retention-leak.mjs` and `exit-household.mjs`). The slice 1c, 6a, 6b, 6c, 6m, 6p, 6r and 7a documents carry a dated correction; their original text is kept.

## What the review found, and the fix

1. **Emergency-access restriction bypassed through outreach plan references (high, slice 6a with 6r).** `targets()` in `lib/saha/exceptional.ts` resolved patients named by person, visit, submission, referral, message, case and hold references, but not outreach `planId`/`itemId` (the processing-restriction and identity guards already did). An owner-clinician whose only access to patient x was an emergency grant could reassign x's outreach item (`outreachAssign`), cancel it (`outreachRecord`) or cancel the whole plan (`outreachTransition`); any grant-only clinician passed the guard for `messageCreate`.
   *Reproduction:* `exc-outreach.mjs` on main: `setContactPreferences` naming x was refused (403) but the three outreach commands applied and the message creation passed the guard.
   *Fix:* an item command (`planId` and `itemId`, including `messageCreate`) names that item's patient; a plan-level command (`planId` alone) names every item's patient. The guard still fails closed across every named patient.
2. **Retention review returned hold reasons and references for patients outside the viewer's scope (medium, slice 6c).** `retentionReview` masked only the patient name and returned every hold's `reason`, `reference`, `personId` and placer, so an owner outside the patient's team, or an owner holding the administrator role, saw the reason and court reference of another team's patient.
   *Reproduction:* `retention-leak.mjs` on main: owner B (team t1) received `SECRET-HOLD-REASON … COURT-REF-42` for a patient in team t2.
   *Fix (`lib/saha/retention.ts`, `app/retention-panel.tsx`):* a hold on a patient the viewer may not see is returned as `id`, `scope`, `placedAt`, release time and `outsideScope: true` only; `holdsOutsideScope` counts them. The panel says the reason and reference are withheld; the owner can still release the hold by its id. Organisation holds and holds on visible patients are unchanged. Eligibility counts still include every hold.
3. **Data exit exported team-scoped households and caseload transfers whole (medium, slice 6m with 6p).** `scopeEntries` was applied to organisation documents only. A household or caseload transfer in the exporter's team was exported with every member, including a patient moved to another team: the member id, relationship and free-text end reason, or the transferred patient id, mapping and assignment.
   *Reproduction:* `exit-household.mjs` on main: `p_kamla` was withheld from `patients.jsonl` but `SECRET-END-REASON` and `p_kamla` were in `tables/households.jsonl`.
   *Fix (`lib/saha/data-exit.ts`):* team-scoped rows go through `scopeEntries` too, which now also filters arrays of bare patient ids (`personIds`, `moved`) and objects keyed by patient id (`assignments`). Each removed entry is counted in the file's `withheldEntries` and the manifest's `entriesWithheld`, and makes the export incomplete. *Verifier (`scripts/verify-export.mjs`):* the relationships check now resolves every household member and every caseload transfer patient against the exported patients, so an archive with the pre-6u shape fails it.
4. **An EHR publication refused before sending stayed `uncertain` forever (medium/low, EHR publication execution).** `executeEhr` saves a `running` checkpoint, then checks the remote patient and rechecks authority before the write. Any refusal there was swallowed and stored as `uncertain`; no command resolves that state and a new publication for the same visit and destination was refused.
   *Fix (`lib/saha/ehr-execution.ts`):* `sent` is set immediately before the write request. A refusal or failure before it is definitive — nothing was sent — so the publication is closed as `blocked` with the message `Not sent: <reason> … Prepare a new publication if it is still needed.`, and a new publication can be prepared. A failure after the write may have started still records `uncertain` and needs a receipt lookup; nothing that may have been sent is marked as not sent, and nothing is retried.
5. **Pilot dossier and expansion pack exports committed their audit event without the slice 6p retry (low).** `pilot-server.ts` and `outreach-server.ts` (`expansionRead`) committed the export audit with a single `persist`, so a command saved meanwhile failed the export with 409 (the defect 6p fixed for the other exports).
   *Fix:* both use `recordExportAudit`. On the retry the exporter's access is checked again on the fresh state: dossier access (operator, named reviewer or supervisor of every pilot team) with unchanged role and clinical reach, or operations access with unchanged role; a change refuses the export and nothing is delivered. `pilotAccess` is factored out of `pilotRead` so the first check and the recheck are the same rule.
6. **The programme callback read the whole organisation before checking its signature (low, programme receipt callback).** `/api/mis/callback` is the only route without `identity()`. It loaded the organisation's full state, then looked up the connection and grant, then verified the HMAC; 404 and 422/409 answers revealed whether an organisation or connection existed.
   *Fix (`lib/saha/mis-callback.ts` `authenticateCallback`, `app/api/mis/callback/route.ts`):* the server grant (configuration, not the database) names the callback secret; the signature is verified with it; only then is the single integration row read and checked against the grant. External services disabled, no grant, missing secret, bad or expired signature, unknown organisation or connection and a changed route all give the same `401 Callback not accepted.` The organisation state is read only after this.
7. **FHIR downloads ignored a processing restriction (low, plausible; slice 6b).** `GET /api/fhir/[id]` checked emergency-access scope but not `ensureNotRestricted`, so a restricted patient's visit could still be downloaded as a FHIR document for sharing.
   *Fix:* `exportFhir` is in `PAUSED_WHEN_RESTRICTED`, and the route calls `ensureNotRestricted` for the visit's patient (both the document and the example format); it answers 409 while a restriction is in force.
8. **The merge view returned the case reason and evidence when the counterpart record was outside the viewer's scope (low, slice 1c).** The counterpart was named "A record outside your scope", but the proposal's reason and evidence (and the decision and reversal reasons) describing both patients were returned.
   *Fix (`lib/saha/merge.ts`, `app/merge-panel.tsx`):* these texts are returned only when the viewer may see both records; otherwise `reason` and `evidence` are null, decision and reversal keep who, when and the decision without the reason, and `detailWithheld` is set. The panel says so.
9. **The ABHA duplicate check revealed an out-of-scope record's ABHA number (low, slice 7a).** `abhaLink` checks the number organisation-wide and answered "This ABHA number is linked to another record", even when that record is outside the worker's scope.
   *Fix (`lib/saha/abdm.ts`):* when the other record is outside the worker's scope the refusal is neutral: "This ABHA number cannot be linked here. Ask an identity steward to review this record before linking." A worker who may see the other record still gets the specific message. One current record per ABHA number is still enforced.

## Limits

- The emergency-access guard resolves plan items from what the command loaded; outreach commands load the organisation's outreach document, so every item is visible to the guard. A plan-level command on a plan holding any grant-only patient is refused for that clinician, even if the other items are in normal scope.
- Retention holds outside scope still show that a hold exists, with its scope and dates; an owner can release one without seeing its reason. Whether an out-of-scope owner should release holds at all is not decided here.
- Data exit filtering keys on patient ids. Free text that names a patient without an id (a household label, a caseload transfer reason) is exported as written. An affected row's `data` text is re-serialised without the withheld entries, as in 6p.
- `blocked` is the existing EHR state for a publication stopped before sending (consent withdrawal uses it); no new state was added. A failure inside the write request itself, even one that probably did not reach the partner, stays `uncertain`.
- The callback refusal is uniform in content, not in timing: a request naming a granted organisation and connection is slower because the signature is computed. Grants are server configuration, not organisation data.
- The FHIR restriction applies to the download route. Data exit (`includeFhir`) still writes FHIR documents for restricted patients in the exporter's scope; it is an owner's organisation exit, recorded in the audit chain.
- The ABHA neutral refusal does not open a task for an identity steward; the worker is told to ask one.
- These fixes have not been independently reviewed. BR-SEC-11, BR-SEC-09, BR-OPS-07, BR-OPS-08, BR-INT-04, BR-INT-06, BR-SEC-10, BR-ID-08 and BR-INT-14 stay partial.
