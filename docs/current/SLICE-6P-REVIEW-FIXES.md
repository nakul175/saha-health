# Development slice 6p — fixes for defects found by an independent review

30 September 2026 (IST). Builds on slices 6m (data exit), 6j (audit chain), 6k (reconciled exports), 2d (fixture migration), 5b (provider sandbox) and 1e (delegation). Synthetic data only; formal acceptance unchanged. No route, command or migration is added; route count stays 40 and certified patient commands stay 45.

These are defects that a reviewer who did not write the code found after the slices above were built, tested and documented. Each was reproduced on the base (`ea83d24`) before it was fixed, with the reviewer's scripts. The earlier slice documents carry a dated correction; their original text is kept.

## What the review found, and the fix

1. **Data exit leaked out-of-scope patients through organisation documents (high).** Slice 6m tagged outreach, governance and retention as organisation tables and exported their JSON documents whole. Those documents hold patient-linked entries: `governance.safety[]` (patient, visit, free-text clinical summary), `governance.shadows[].results[]` (patient, visit, assistant output), `outreach.plans[].items[]` (patient, reason, notes), `outreach.messages[]` (patient, message body) and `retention.holds[]` with a patient (reason). An owner whose care scope excluded a patient still received that patient's safety summary, outreach reason and message and hold reason; an owner with the administrator role received all of them; the manifest could still say complete.
   *Reproduction:* reviewer's `exit-leak.mjs` on the base printed `LEAK SECRET-SAFETY in tables/governance.jsonl`, `LEAK SECRET-MSG` and `LEAK SECRET-OUTREACH-REASON in tables/outreach.jsonl`, `LEAK SECRET-HOLD in tables/retention.jsonl` and the patient's name in two files, with the patient row itself correctly withheld.
   *Fix:* `scopeEntries` in `lib/saha/data-exit.ts` walks every organisation table's `data` document and leaves out any entry, at any depth, whose `personId` is outside the exported patient set (an array element is removed, an object property is removed). Entries without a patient (organisation holds, templates, plan headers, incidents, budgets, delegations, fixture batches, training records) are kept. The data text is re-serialised only when something was left out; otherwise it stays exactly as stored. Each organisation file in the manifest carries `withheldEntries`; `totals.withheldEntries` and `scope.entriesWithheld` sum them; `scope.complete` is true only when no row and no entry is withheld; the file note says how many entries were left out. The export's audit event names the withheld entries and says complete only when the manifest does.
   *Other organisation tables checked:* `integrations` (connector configuration), `operations` (incidents, rates, acknowledgements, budgets, fixture batches, delegations), `pilot` (configuration, training records by member, aggregate measurements, evidence, decisions) and `expansions` (specifications, evidence, reviews) hold no `personId` today; the same walk runs over them, so an entry added later with a patient is filtered too. `organisations`, `teams`, `memberships`, `team_members`, `invitations`, `legacy_migrations` and `request_metrics` have no JSON document with patient content. Governance evaluations run on the fixed synthetic corpus, not patients. Households and caseload transfers are team-scoped rows (unchanged).
   *Verifier:* `scripts/verify-export.mjs` now adds withheld entries to its totals check, fails a manifest whose completeness claim disagrees with the files, and resolves every `personId` inside organisation documents against the exported patients (so an archive with the pre-6p shape fails the relationships check).
2. **Exports failed with 409 if any command saved while they were built (medium).** Data exit, the audit-chain export and the operations CSV/support export committed their own audit event against the state read at the start, and the commit guard requires the organisation and patient revisions unchanged; one ASHA visit save during a long export discarded the whole export.
   *Reproduction:* reviewer's `export-race.mjs` on the base: `export refused: 409 A teammate changed this organisation.` after a concurrent patient-scoped commit.
   *Fix:* `lib/saha/export-audit.ts` (`recordExportAudit`) still writes the event through `persist`, so the audit hash chain is unchanged. On a 409 only, it reads the current state again, repeats the authority check on it, and commits the same event (same id and detail, carrying the checksums of the content actually exported from the first snapshot); at most three attempts. The authority check on the fresh state is: data exit — still an active owner with the same role and teams (the exported scope depended on them); audit-chain export — still an owner or administrator with the same role (the redaction depended on it); operations CSV — not an administrator, support — owner or administrator, same role. Any other error, a failed check, or a conflict on every attempt is returned and nothing is delivered.
3. **Fixture migration reversal ignored care scope (medium).** Apply was limited to the owner's care scope, but reversal removed `synthetic` from every record in the batch, so owner B could unmark records only owner A may access, lifting the slice 6n synthetic-record barrier for them.
   *Reproduction:* reviewer's `fixture-revert.mjs` on the base: `B (no access to team default) reverted 6 records; synthetic flags now: false,false,false,false,false,false`.
   *Fix:* reversal removes only the marks on records the reverting owner may normally access (`normallyAllowed`, the dry-run and apply scope). Others keep their mark and are reported (`outOfScope`); if none of the batch's marked records is in scope the command is refused (409) and nothing changes. *Decision:* a partly reversed batch can be reversed again by another owner (or the same owner after a scope change) for the remainder. Each mark is removed at most once, because its batch link goes with it. Each partial reversal is appended to the batch's `reverts` list and audited; the batch records `revertedAt` only when no record keeps its mark, after which it cannot be reversed again. The owner panel shows "partly reversed" with the counts.
4. **Provider sandbox import was an existence and sandbox oracle (low).** `sandboxSource` read the whole named organisation before the importer's ownership was checked, and the handler answered 404 (not found), 409 (not a sandbox) or 403 (not yours).
   *Fix:* the server checks the importer's active owner membership of the named organisation and its sandbox declaration with two small queries before reading its state, and answers one 404 with one message (`Provider sandbox not found or unavailable. …`) for not found, not a sandbox and not the importer's own. The handler repeats the same checks in the same order on the state read. Importing from the current organisation still answers 409 (the caller already knows it).
5. **Lower-priority items.** The delegation limit (`MAX_RECORDS`, 200) counted revoked and ended delegations, so grants were refused forever after 200; it now counts only delegations not yet ended or revoked (records are kept, with their audit events). Data exit patient scope and the audit-chain export visibility query excluded administrators but not the sandbox `provider` role; both now exclude it (defence in depth — a sandbox holds no patients). The archive path check allowed `..` segments; `safePath` now also refuses empty, `.` and `..` segments.

## Regression tests

Each reproduction is now a permanent test that fails on the base and passes after the fix. No existing assertion was removed or loosened; two provider-sandbox assertions changed their expected status from 403 and 409 to the uniform 404, which is the intended stricter behaviour.

- `tests/review-fixes-contract.mjs` (new, in the CI contract loop; real migrations in SQLite through the D1 shim). Run against the base with the new helper copied in, each block fails: block 1 at "no trace of the out-of-scope patient anywhere in the archive", block 2 at the source guard (the export routes still call `persist` directly) and "a provider sees none", block 3 at "expected 409" (the base reverted every mark), block 5 with "Delegation record limit reached". It checks: the reviewer's organisation exported by an owner whose scope excludes one patient carries no trace of that patient in any file; five entries withheld, counted per file and in the totals, `complete` false; in-scope entries, plan headers and organisation holds kept; the offline verifier passes the real archive, fails the same archive with an out-of-scope safety case put back and resealed, and fails a manifest that claims completeness; administrator and provider exports withhold every patient and all eight entries; `safePath` cases; a single-attempt audit commit after a concurrent patient save is refused (the reviewer's 409), while `recordExportAudit` commits after one fresh read, keeps the concurrent save and leaves the chain intact; an owner demoted meanwhile gets 403 and no event; a conflict on every attempt stops after three; the three export routes call the helper and never `persist`; the provider role sees no patient-linked audit content while a clinician in the team does; the reviewer's fixture scenario refuses B's reversal and keeps every mark; a split batch is partly reversed by one owner, refused a second time for the same owner, and completed by another; a grant succeeds after 200 ended or revoked delegations and is refused at 200 in force.
- `tests/data-exit-smoke.mjs`: on the shared HTTP test organisation, the withheld-entry count in the manifest equals an independent count over the stored documents in D1, the archive's organisation documents contain no out-of-scope entry, and `complete` agrees.
- `tests/provider-sandbox-smoke.mjs`: not a sandbox, not found and not the importer's own (a separate owner of another organisation) all answer 404 with the same message.
- `tests/provider-sandbox-contract.mjs`: not the importer's own and not a sandbox answer 404 at the handler.
- `tests/fixture-migration-contract.mjs` unchanged and passing (its whole-batch reversal is by an owner whose scope covers the batch).

## Limits

- The data exit filter is keyed on `personId`. Free text that names a patient without a `personId` — an outreach plan title or criteria, an incident title, a governance change summary — is exported as written. Pilot measurements are aggregate counts for the selected teams, not filtered by the exporter's scope.
- Filtering changes the exported `data` text of an affected organisation row: it is re-serialised without the withheld entries, so it no longer matches the stored text byte for byte (the file note says so). Unaffected rows stay exact.
- The export retry keeps the content read at the start. A record changed during the export may appear in its older or newer state, as slice 6m already stated; the retry only stops a concurrent save from discarding the export. After three conflicting attempts the export is still refused.
- The retry checks role and teams for data exit and role for the other exports; it does not re-verify delegations for a delegated CSV report.
- Ended and revoked delegations are kept and the operations document grows by one record per grant; there is no archive or pruning.
- The sandbox import still refuses import into the current organisation with 409, and the provider sandbox view lists only sandboxes the owner owns (unchanged).
- The reviewer's findings are fixed; no further independent review of these fixes has taken place. BR-OPS-07, NFR-22, BR-DATA-11, BR-AI-11, BR-ID-02 and BR-ID-09 stay partial.

## Correction — 30 September 2026 (slice 6q)

A second independent review found two gaps in this slice. The export audit retry for the audit-chain and operations exports re-checked role and operator status only, not the care scope or, for the operations CSV, the reporting reach (the limit above says so for delegations; it was a defect, not only a limit). And with ended and revoked delegations no longer counted toward the 200-record limit, the stored delegation records were unbounded. Slice 6q refuses the export on retry if the care scope or reporting reach changed, and caps stored delegation records at 1,000 without deleting evidence. See [SLICE-6Q-SECOND-REVIEW-FIXES.md](SLICE-6Q-SECOND-REVIEW-FIXES.md). The text above is kept as written.
