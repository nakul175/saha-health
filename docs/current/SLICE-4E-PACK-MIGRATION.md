# Development slice 4e — reviewed migration of open programme episodes to a new pack version

1 October 2026 (IST). Part of slice 4 of the development-completion plan (NEXT-DELIVERY row 4: pack migration and installation). Synthetic data only; formal acceptance unchanged. The second maternal pack version added here is illustrative and not clinically approved.

## What changed

- **The need.** Every programme episode is pinned to the pack version it opened on, and every visit keeps its own copy of the pack version it captured under. Until now the catalogue held one version of each pack, so nothing could move an open episode to a newer version and nothing decided which version a new episode opens on. BR-PROG-07 asks for reviewed open-episode migration and coordinated version changes.
- **A second maternal version.** `lib/saha/programmes.ts` now carries `maternal` v2, a synthetic revision that renames `maternal_contact` to `appointment_discussed` (and relabels it), adds a required `danger_signs_reviewed` question, and describes an illustrative schedule and escalation (text only; nothing is scheduled or escalated automatically). It declares a reviewed mapping from v1 (`migratesFrom: [1]`); a renamed question names its earlier id (`renamedFrom`). TB and hypertension still have one version.
- **Adopted version.** New episodes open on the organisation's adopted version of a pack (`operations.packVersions`), v1 until an owner applies a migration of that pack. An adopted version missing from the catalogue falls back to v1. `enrolProgramme` uses it.
- **What changes between versions.** `packChanges(from,to)` lists questions added (with whether they are required), removed, renamed (and whether the label changed) and redefined (label, unit, fact, options, condition or required flag changed), the schedule and escalation text before and after, the version's change note, and whether the target declares a reviewed mapping from the earlier version.
- **Dry run.** `GET /api/programme-migration` (owners and clinicians; asha, supervisor, administrator and non-members are refused) returns the pack catalogue (versions, adopted, latest) and, for each pack with open episodes or new-episode use on an older version, a dry run over the open episodes on older versions: those in the reader's normal care scope are either candidates (person id, episode id, record version, from-version, open follow-ups carried over unchanged, recorded visits that keep their version) or blocked with a code and reason; the rest are counted as outside scope. It returns ids, versions, counts and reasons, never names or episode labels. The plan hash covers the pack, the target and adopted versions, whether applying adopts, and each listed episode's person id, episode id, record version and from-version (or blocking code).
- **Episodes that cannot migrate automatically** stay on their version and are listed in every later dry run for manual action: an open visit capturing the episode (confirm or discard it first, the same rule as closing an episode), a record merged into another (its open items belong to the slice 1c merge impact queue), processing restricted under a rights request, no reviewed mapping declared from the episode's version, and a version missing from the catalogue. The last two cannot occur with the current catalogue and are covered by the contract test directly.
- **Apply.** `programmeMigrationApply` (`packId`, `targetVersion`, `planHash`, reason of at least 10 characters) recomputes the dry run for the applier and refuses with a 409 unless the target is still the latest version and the plan hash matches, so only the exact reviewed plan is applied and any change to a listed patient record since the dry run forces a new one. Each candidate episode moves to the target version and appends `{batchId, from, to, at, by, reason, planHash}` to its own `migrations` list; the patient record carries `packMigration` (batch, episode, pack, from, to, time) so the record revision shows the from/to versions as changed fields. The store writes one revision per migrated episode with the reason. When the applier is an owner, the target becomes the adopted version so open and new work move together; a clinician who is not an owner migrates episodes in their scope and leaves the adopted version unchanged (the dry run says so). One batch record (pack, from- and to-versions, plan hash, examined, migrated, blocked, outside scope, whether adopted and the previous adopted version; no record ids) and one audit event with the counts are written. The stored command result carries counts and the batch id only, so a replay by key returns no record ids; the role check runs again on replay.
- **History kept.** Visits and submissions are not touched: a confirmed visit keeps the copy of the pack version it was captured under and the programme evidence on it still shows that version. Open follow-ups stay open and keep their episode link. Closed episodes keep their version.
- **Screen.** Organisation & team gains a "Programme pack versions" panel for owners and clinicians: catalogue, dry run with the changes between versions, the episodes that would move and those left for manual action (names resolved in the browser from the people it already holds), apply with a reason, and the batch list. A migrated episode on the patient screen shows "(migrated from v1)".
- The command follows the maintenance rule (paused while the organisation is paused) and loads the whole organisation like the other migration commands.

## Reversal

A batch is not reversible by command. Moving an episode back is itself a version change that needs a reviewed mapping, and v1 declares none from v2: the renamed question reads as one removed and one added, and answers captured under v2 after the batch (the new danger-sign question) have no place in v1. A reverse would therefore be a new reviewed migration in the opposite direction, declared by a pack version that maps from the newer one, through the same dry run and apply; the episode's `migrations` list and the record revisions keep both changes. The contract test records that `packChanges(v2, v1)` is not a reviewed mapping. An adopted version can only move forward through apply.

## Limits

- One illustrative second version. There are no institution-approved pack versions, no clinical review workflow for a pack version itself (the `migratesFrom` declaration stands in for that review), no translated content and no per-team adoption: adoption is organisation-wide.
- Migration moves whole episodes between versions of one pack; it does not migrate answers, recompute schedules or create follow-ups from the new schedule text, and it does not install new packs. Open follow-ups are carried over as they are.
- Episodes outside the applier's care scope are counted but not moved; an owner whose care teams cover them, or a clinician in those teams, can run another dry run.
- Episodes blocked by a restriction or an open visit need the restriction lifted or the visit finished before a later dry run picks them up; there is no command to migrate a single reviewed episode by hand.
- No reversal command (see Reversal).

## Notes for new-pack installation (next round)

Installing a new pack (BR-PROG-08) would need: a pack definition stored as data rather than in `PACKS` (the catalogue is compiled into the Worker today), validated against the question schema and the shared fact keys; a governed review of the pack by a clinician other than its author (the slice 5d capability lifecycle and the governance review packages are the nearest pattern) before it can be adopted; `PackId` and the `enrolProgramme`/`programmeMigrationApply` schemas widened from the fixed three ids to installed ids; programme names added to `Programme` and the MIS mappings that route programmes to destinations; adoption per organisation through the same `operations.packVersions` record; and a rule for what happens to installed packs on data export and restore. The plan-hash dry run and apply here can then move open episodes between installed versions unchanged.
