# Development slice 5c — conflicting assistant values and inability to assess

30 September 2026 (IST). Stacked on slice 5b. Synthetic data only; formal acceptance unchanged.

## What changed

- **Unable to assess (BR-AI-06).** The agent output contract (`saha-agent-1.2.0`) has an `assessment` member: either null, or `unable_to_assess` with a reason (`noisy_input`, `unsupported_case` or `insufficient_input`), a detail and a retry instruction. An answer that says it cannot assess must propose no values; one that does is rejected as a contract violation (502). The OpenAI and Saha agent API schemas and the provider instructions now ask for it ("Never report an unreadable measurement as absent or normal"). The agent version moved from 1.1.0 to 1.2.0 because the instructions and schema changed, so capability packages pinned to 1.1.0 need a new revision and evaluation.
- **Local rules provider.** Before extracting, the local provider checks the note. A measurement clause with an unreadable value (`5?`, `120/?`, `3_7`, `[inaudible]`, `[unclear]`, `[illegible]` or a replacement character) is `noisy_input`; a measurement in pounds, Fahrenheit or inches is `unsupported_case`; a note that mentions no supported measurement is `insufficient_input`. In each case the whole note is withheld, including clauses that were readable, and nothing is proposed. A stated absence ("Weight not measured") is still an assessed result with no values. Summary and programme-review tasks are unchanged.
- **Shown as such.** The result keeps status "review" so a person closes or records a decision on it, but it carries the assessment, its message starts "Unable to assess" and says it is not a normal or negative result, the visit assistant shows an "Unable to assess" tag with the reason and retry instruction, and applying it is refused (409).
- **Conflicts (BR-AG-08).** When a result arrives, every open extraction on the visit is compared with the recorded draft facts and with the other open extraction results for the same visit version. A proposed value that differs from a recorded value, or from another open result, is stored on both results as a conflict (field, kind, both values, the other result and provider) and listed in the result's warnings. Nothing is averaged, merged or chosen automatically.
- **Explicit choice.** Applying a field that has a conflict is refused (409) unless the requesting worker names it in `resolve` and gives a `conflictReason` (10–500 characters); naming a field that is not selected or has no conflict is refused (422). The applied result records each resolution (field, chosen value, the values it was chosen over, reason, person and time), the audit line names them, and the replaced recorded value stays in the revision history. The competing result keeps its original output but becomes stale when the visit changes, so it cannot be applied afterwards.
- **Review task.** The patient's action plan shows one "Assistant results disagree" item per visit while two or more open results on the current visit version disagree with each other, listing every original value with its provider, owned by the requesting worker. It disappears when one is applied (the others go stale), dismissed or reviewed.
- **Screen.** The visit assistant shows each conflict under the proposed value, a separate "Use … despite the conflict" choice for a selected conflicting field, and a reason box; the apply button stays disabled until every selected conflicting field is chosen explicitly with a reason.

- 50 contract assertions (`tests/agent-quality-contract.mjs`): five noisy, three unsupported and two insufficient notes classified, six assessable notes (including a stated absence, Hindi and a question mark outside a measurement) not; the legible weight in a partly noisy note withheld; summary unaffected; the output validator rejects values with an unable-to-assess answer and unknown reasons or statuses, and accepts null; schema and instructions; an HTTP provider fixture's unable-to-assess answer carried through, and one with values rejected; the English synthetic corpus still passes with the noisy and unsupported cases reported explicitly; conflicts with a recorded value and between two results marked on both sides; an unassessed result has no conflicts; one action-plan task with both values and no average; applying refused without a choice, with a choice for an unselected or unconflicted field, without a reason and for an unassessed result, with no change made; applied with a reason, resolution and audit recorded; the competing result kept and refused as stale; the task closed; an equal value is not a conflict.
- 42 HTTP/D1 assertions (`tests/agent-quality-smoke.mjs`), in a fresh organisation with the local rules provider over the Worker: the three unable-to-assess reasons with no values and apply refused; a recorded weight and two disagreeing results flagged on both sides; the action-plan task with both values; apply refused without a choice or reason and for another clinician; applied with a reason; the other output kept and refused as stale; the task gone; the replaced value in the revision history.
- Browser check (headless Chromium, built Worker, synthetic owner): the visit assistant showed "Unable to assess · Noisy or illegible input", the recorded-value and other-request conflicts under the proposed 58 kg and no averaged value; apply stayed disabled until the explicit choice and a reason were given, then applied 58 kg with the resolution recorded; axe-core found no WCAG A/AA violations in the assistant panel; no console errors. `tests/evidence/slice-5c/agent-quality-browser.json`.
- Existing suites pass, including the governance evaluation (English pass, Hindi failure) with the new agent version; `tests/agent-smoke.mjs` pins the agent version and was updated to 1.2.0.

## Limits

- Quality checks are text rules over typed notes. There is no signal or media quality check (audio, photo or cough recording), no confidence score and no per-field "unable to assess"; a noisy clause withholds the whole note.
- Conflicts compare exact values of open extraction results on the same visit version and the recorded draft facts. Earlier confirmed visits, units that differ only in formatting, applied or dismissed results and summaries are not compared, and there is no validated composition policy or routing beyond the requesting worker and the action plan.
- Only extraction proposes values. There are no risk scores in the current product to average, so "no averaging" is tested on extraction values only.
- Live providers stay disabled; the HTTP provider path is covered with a mock transport.
- BR-AG-08 and BR-AI-06 stay partial.
