# Protect the expected criteria source and its pins
The offline checker intentionally checks consistency, not independent authority. Re-pinning a narrowed source and register can produce a consistent report. Adoption for real release decisions requires an enforced external control on the expected population.

## Default adoption route: actual human review
1. Merge adoption/github/CODEOWNERS.template into the real product repository's .github/CODEOWNERS. Replace placeholders with real human source/control owners who have required repository permissions; confirm any team contains the intended human reviewers. Customize the exact criteria-source and scope paths. The template is inactive and is not an installed protection.
2. Protect the source snapshot and scope.json together. Also protect CODEOWNERS itself, workflow/checker/schema controls and any source/export logic so an implementation agent cannot remove the validation in the same change. Check for later patterns overriding ownership or protected files outside the pattern.
3. In the actual protected branch/ruleset, require PR reviews **and review from Code Owners**. Dismiss stale approvals on new changes and require approval of the latest reviewable push where configured. Require the QA status check from the appropriate trusted integration; restrict bypass/direct push/force push according to actual repository policy and inspect administrative bypass permissions.
4. Review the complete canonical scope against the source export, including exclusions and applicability changes, before approving population/hash changes. A valid checksum is not that review. Do not add implementation agents/bots as the sole authoritative scope reviewers.
5. Validate enforcement with safe test PRs and fill templates/source-protection-verification.md. A PR narrowing both source and register may pass offline checks but must remain unmergeable without the actual required owner review. New reviewable changes must require the configured fresh approval.

A CODEOWNERS file alone does not require approval; the actual branch/ruleset setting must enforce it. Repository features/permissions vary. Verify the real configuration and record its evidence instead of treating this package as enforcement. GitHub documentation: [Code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

## Alternative route: independent source reconciliation
A trusted CI service can fetch the canonical Linear/PM scope using read-only access, apply the independently controlled scope-selection rules, export the complete AC ID/version/applicability set and compare to the candidate snapshot and pins. It must not use the PR's self-authored register/export as the authority. Protect the workflow, credentials, selection logic and canonical scope-change approval. Decide and document how legitimate proposed PM changes become approved; fail closed on unavailable source or inconsistent revisions. Preserve canonical source revision and reconciliation evidence without exposing credentials.

This package supplies no live export integration or GitHub configuration. Record control status as NOT_CONFIGURED until actual setup is verified. A real release remains blocked on unverified required scope protection even when the offline record gate exits 0. Keep this separate from the checker's bounded exit-code contract.
