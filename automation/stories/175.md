# D02 / #175 — My assigned work and the correct record

Status: specification seed for Product/UX refinement; NOT implemented/accepted under the reset.
Original owners: SAHA-001,002,007,011,102. Keep the existing issue and earlier evidence. Specification changes below narrow the first delivery boundary explicitly; unimplemented parent scheduling/UX remains in the original scope register, not silently removed.

## User outcome
As a signed-in ASHA, I can see my assigned work on a minimal phone-first Today view and open the correct existing person's read-only context, without navigating programme or provider apps.

## Required scope
An authenticated synthetic/training ASHA with assigned records; real server-authorised list/read/audit operations; one main next-record action and remaining records in their existing source order. Do not invent today's schedule, clinical priority or completion. Preserve IDs and source labels. When no true dated daily list exists, label the list accurately rather than falsely claiming the records are all due today.

Start with a minimal active runtime/entry. Old visit editing, incentives, Academy, provider tools, supervisor administration and offline capture are not activated by this story. Existing identity, server-side authority, safe record reads and audit remain necessary foundations. Unselected functionality must not be reachable through the new app's routes/actions, not merely hidden by CSS. Legacy runtime remains preserved separately; do not switch the default hosted experience destructively as part of this story.

## Functional/UX
Define the exact entry route and capability boundary after inspecting current route contracts. Reuse inspected portions of #184, not its full editor or My Space catalogue. Show loading, no assignments, unavailable source, permission refusal and unsupported workspace shape as distinct states. Names alone are not identity: show village and stable short record reference. Selecting an item opens that record's clearly labelled read-only context and offers return to Today. Keep permissions on the server; navigation parameters are not authority. Refresh/account change must clear previously visible protected content as required by the actual identity change.

A paged source must remain usable through authorised continuation or an explicit unsupported state chosen before coding; do not silently show a partial list as complete. No AI, microphone, geolocation, additional approval or mandatory worker training is needed. The online-only first-story boundary is explicit; absent network must show unavailable, not fake offline support. Later offline stories retain the core product offline-first objective.

## Data and API work
Product/Engineer must inspect actual existing identity, workspace, record-read and audit contracts and specify their exact reuse points. No parallel person database, new clinical observation or new visit is required. Opening a record may append the existing necessary read audit; it must not create a visit or change programme facts. No plaintext patient data in localStorage/public caches. Preserve tenant/assignment restrictions and current record history. State explicitly whether the new entry requires a read projection/capability adapter; do not pretend a smaller API already exists.

## Applicable non-functional requirements
Phone viewport 360x640 plus taller fixture; no horizontal page overflow; primary targets at least 44 CSS px; readable at 200% text; keyboard focus/labels/back handling; real permission and failure cases. Test English and clearly labelled draft Hindi if exposed. No unverified physical-phone, clinical or government acceptance. Local-save latency is not applicable to this read-only story, but is NOT waived for later capture stories.
