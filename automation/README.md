## Coordination protocol (mandatory)

Roles are allowed to act only at their stage: Product at `specify` or `done`; Engineer at `build`; QA at `qa`; Reviewer at `review`; Release at `release` or `deploy`. All other invocations exit without code writes. The role selected in control.json acquires a lease by ONE optimistic update_file of that file using its freshly read blob SHA, a unique run ID and a UTC expiry (90 minutes maximum). Re-read to confirm ownership. A 409/422, changed state, active other lease or uncertain write means stop and reconcile; never force-push. Do not launch parallel writes. CAS is a coordination convention, not a replacement for GitHub branch protection.

Before every source push, state transition or merge, re-read control, stop requests, remote source head and lease. Retain the expected source parent. Renew a lease before it expires. On stale lease: first reconcile existing PR heads, comments, merge results and CI to establish whether the previous action happened; do not blindly repeat a merge/push or steal work from a known active writer. Release the lease and record an actual checkpoint at the end. Existing CI may continue read-only after a run; do not queue another run for unchanged source. A run must do useful bounded work or name a blocker, not append empty heartbeat comments.

## Roles and handoffs

**Product/UX:** Own specification only, not production code. Inspect actual source before defining reuse. For the active story, finish requirements, complete mobile UI behaviour, data/API delta, applicable NFRs, positive/adverse/rejection criteria, test plan and release/rollback conditions. Separate pre-merge criteria from post-deployment criteria so release does not require its own deployment before merge. Pin specification version/hash and chosen main SHA. Put the canonical story specification on its one fresh branch from main, link the existing issue, and register one focused PR when a meaningful specification/change is available. Move to build only when its bounded demo scope is implementation-ready. Keep unsupported departmental policy explicit; no new worker obligations.

**Engineer:** Sole product-code writer. Read the complete pinned specification; create/update only its one branch/PR. Reuse verified old code selectively; no old monolithic worker workspace enabled as a shortcut. Implement UI, backend/data and tests for the full story. Preserve original tests and minimum assertions. Run author checks with exact commands/exits. Record current head and base, then freeze code and move to QA. A fix changes the head and invalidates ALL old QA/review approvals. Do not edit merge-gate policy to pass it.

**QA:** Different scheduled run from the author. Execute the story end to end against the built synthetic backend, inspect resulting data/audit where applicable, negative authorisation/input/network states and affected regressions of previously completed stories. Read the raw outputs, not just green step summaries; cancelled/skipped/action_required is not success. Use fresh head and actual test environment. Add failure evidence and return to build when needed; do not repair implementation or weaken tests yourself. Record an acceptance-criterion matrix and signed-off role receipt with task/run ID, head/base/spec hashes, commands, evidence locations and limitations. Only all required criteria passing can move to review.

**Reviewer:** Read the exact diff, complete affected code and QA evidence in a separate scheduled run, including runtime exposure, privacy, authorisation, data history, manifests and deployment implications. Do not author a code fix and approve it in the same review. Request changes to build or QA when needed. Record a distinct review receipt on the same head/base/spec and move to release only with no unresolved blocking findings. This is agent review, not human/ASHA/clinical acceptance. Never impersonate a different GitHub reviewer; a rule requiring independent human approval remains a blocker.

**Release:** Sole merger and dashboard publisher. Re-read live PR/head/base, repository-enforced checks and QA/review receipts. Inspect exact-source CI logs/artifacts. Execute `automation/gate.py` on a freshly assembled factual release packet, then honour any additional server-side protection; the helper cannot independently attest facts. Merge the one eligible story PR into main using merge_pull_request with expected_head_sha. Do not direct-push main, bypass protection, disable checks, force ready/approval or batch old PRs. If a main update changes the review base, return for requalification. On uncertain merge response, query PR/main before another attempt.

Merges can invoke the already documented DigitalOcean synthetic updater; preserve `SAHA_DEPLOY_FREEZE`, provider-off and synthetic settings. Do not create another host, modify credentials or enable an alternative deploy target. Record merged SHA separately from deployed SHA. Then verify the actual hosted build and story smoke test using existing authorised access; a Git push, CI browser or HTTP 200 alone is not a deployed demo. If host access/status is unavailable, record `deploy` plus exact blocker, not Done; revisit/reconcile without repeated empty notifications. Do not start the next product story until the current story's declared demo delivery gate clears. A source revert is not a data rollback: preserve queued work and migrations.
